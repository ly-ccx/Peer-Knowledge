# GPT 推理摘要：产品命名与说明口径

> 关联诊断：`knowledge/experience/gpt-reasoning-summary-glued-display-root-cause.md`  
> 创建时间：2026-07-28  
> 最后更新：2026-07-28  
> 边界：**只定文案与预期**；不改现有 thinking 拼接/展示实现

## 1. 产品结论（一句话）

用户在 GPT 思考区看到的，多数是 **推理摘要（reasoning summary）**——模型对外暴露的短状态句，**不是**完整内部思维链（full chain-of-thought）。

短语偶发粘连，是摘要流式吐出时边界不完整 + 客户端原样拼接的结果；**当前产品选择保持原样，不靠启发式自动断句**。

## 2. 命名对照

| 场景 | 推荐用语 | 避免用语 |
|------|----------|----------|
| UI 折叠/区块标题 | **推理摘要** / **思考摘要** | 完整思考、深度思维链、CoT 全文 |
| 英文 UI（若需要） | **Reasoning summary** | Full thinking / Private CoT |
| 内部工程 | `reasoning summary` / `thinking channel` | 把 summary 与完整 `reasoning_text` 混称为同一种产物 |
| 空态/加载 | 正在生成推理摘要… | 正在完整思考… |

**默认推荐对外中文：`推理摘要`。**  
「思考中」可用作过程态动词；落定内容区标题优先「推理摘要」，避免暗示完整 CoT。

## 3. 用户可见说明（可直接复用）

### 3.1 短说明（Tooltip / 折叠副标题）

> 此处展示模型提供的**推理摘要**（简短状态），不是完整内部思考过程。

### 3.2 稍长说明（设置/帮助/首次展开）

> 部分模型只会返回**推理摘要**：若干短句描述当前在规划、排查或修改什么。  
> 摘要按流式原样拼接，句与句之间可能没有空格或换行，这是上游输出形态，不是对话内容丢失。

### 3.3 粘连被问及时的客服/研发口径

> 看起来「粘在一起」，通常是因为模型吐出的是多条**无分隔的状态短句**，客户端按原样连接，没有做自动断句。  
> 我们刻意不按大写字母硬拆，以免把 `setState` 这类标识符拆碎。内容本身仍是摘要，不是残缺的完整 thinking。

## 4. 预期管理（Do / Don’t）

**Do**

- 明确区分：**推理摘要** vs **最终回复**  
- 承认限制：能否看到更多细节取决于模型与 API，不保证完整 CoT  
- 若未来做展示优化，优先「可视化分段 / 列表」，并继续标注为摘要  

**Don’t**

- 不要写「展示 AI 的完整思考过程」类承诺  
- 不要把粘连说成「bug 导致思考丢失」  
- 不要在未改产品决策前，暗示「马上会自动断句成优美段落」  

## 5. 与实现的关系（刻意不动）

| 项目 | 现状 | 文案侧态度 |
|------|------|------------|
| 事件源 | `reasoning_summary_text`（主）+ 可能的 `reasoning_text` | 对外统称「推理摘要」即可；有完整 reasoning 时仍不必改称「完整 CoT」除非产品单独立项 |
| 拼接 | 朴素 `+` | 不在文案中承诺「已智能排版」 |
| 启发式断句 | 已还原，不默认启用 | 不写进功能卖点 |

## 6. 可选后续（非本次范围）

仅作产品 backlog 备忘，**不代表已排期**：

1. 思考区标题默认改为「推理摘要」  
2. 首次展开时的一行说明  
3. 若 API 同时提供 summary 与更长 reasoning，再讨论是否分栏——需单独设计，不静默改拼接  

## 7. 验收口径（文案）

- 对内文档与对外文案一致使用 **推理摘要**  
- 任何 UI 文案不得把当前 GPT 思考区描述为完整 CoT  
- 粘连问题的解释指向「摘要形态 + 原样拼接」，不指向「用户消息坏了」
