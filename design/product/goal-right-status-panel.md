# Goal 右侧状态区产品与交互设计

创建时间：2026-07-22
最后更新：2026-07-22

## 1. 文档定位

本文定义 Peer Agent 桌面端与 CLI/TUI 端 Goal UI 的产品定位、信息架构和交互规则。

核心结论：**Goal 是主交互区右侧持续可见或可快速唤出的客户端式状态区，不是聊天流中的一组工具调用消息。** 用户应该通过右侧状态区掌握目标、进度、当前工作、阻塞和验收结果；聊天流只保留对协作有意义的自然语言结论、提问和关键事件。

桌面端的 GoalView 是 [`right-workbench-panel.md`](./right-workbench-panel.md) 中 Workbench 的专题设计。Workbench 负责窗口级容器、开合、宽度和 Tab 切换；本文负责 GoalView 内部的信息层级、状态反馈、操作和聊天流降噪。CLI/TUI 端复用同一套 Goal 信息层级和状态源，但采用本文定义的终端双区布局与窄终端降级规则，并与 [`tui-interaction-design.md`](./tui-interaction-design.md) 保持一致。

## 2. 背景与问题

当前 Goal 工具执行信息可能以如下形式出现在聊天流：

- `Create(goal, successCriteria, tasks)`；
- `Update(planId, taskId, status)`；
- `{"ok":true,"planId":"...","status":"accepted"}`；
- 本地 store 路径、内部 ID、任务计数和截断后的 payload。

这些内容属于工具协议和调试数据，不是面向用户的产品信息。直接展示会造成以下问题：

1. 用户误以为 Goal 内容被压缩、损坏或出现乱码；
2. 连续更新挤占聊天流，破坏对话上下文；
3. `planId`、`taskId`、store 路径等实现细节盖过真正重要的目标和进度；
4. 状态分散在多条历史消息中，用户无法一眼判断“现在做到哪一步”；
5. Goal 被误解为一次性聊天卡片，而不是持续运行的客户端任务。

因此，Goal 状态必须从“按时间堆叠的消息”迁移为“按当前状态组织的右侧状态区”。

## 3. 产品目标

### 3.1 目标

- 让用户在不翻聊天记录的情况下，3 秒内理解当前 Goal、进度、当前任务和是否阻塞；
- 让 Goal 像桌面客户端的任务状态面板一样持续更新，而不是反复新增消息；
- 将自然语言协作与机器执行协议分层；
- 与 Workbench 的 Terminal、Browser、Files 共同构成稳定的右侧工作区；
- 保留必要的证据、失败详情和高级诊断入口，但默认不制造噪音。

### 3.2 非目标

- 本文不重新定义 Goal Runner、任务调度、证据注册或完成门禁；
- 本文不取代 Plan/Goal 的生命周期规范；
- 本文不把右侧状态区设计成第二个聊天窗口；
- 本文不要求默认展示完整工具参数、工具返回值或原始 JSON；
- 本文不定义 Terminal、Browser、Files 子视图的内部交互。

## 4. 总体布局

### 4.1 桌面客户端

```text
┌──────── 左侧导航 ────────┬──────────── 主聊天区 ────────────┬──────── Workbench ────────┐
│ 会话 / 工作区             │ 用户与 Agent 的自然语言协作       │ Goal                    │
│                          │ 关键决策、提问、阶段性结论         │ 目标标题与状态            │
│                          │                                  │ 总进度                    │
│                          │                                  │ 当前任务                  │
│                          │                                  │ 任务列表                  │
│                          │                                  │ 验收标准 / 阻塞 / 证据     │
└──────────────────────────┴──────────────────────────────────┴──────────────────────────┘
```

桌面端区域职责：

| 区域 | 回答的问题 | 内容特征 |
| --- | --- | --- |
| 左侧导航 | “我要进入哪个会话或工作区？” | 导航与资源切换、可收起 |
| 主聊天区 | “我们在讨论什么、需要我决定什么？” | 自然语言、低频、可追溯 |
| Goal 右侧状态区 | “目标是什么、现在做到哪、有没有问题？” | 结构化、实时、可扫读 |
| 终端/浏览器/文件 | “执行现场和产物是什么？” | 专业工作视图、按需切换 |

桌面端 GoalView 必须位于 [`right-workbench-panel.md`](./right-workbench-panel.md) 定义的 Workbench Panel 内。不得另建与 Workbench 并列的永久右栏，也不得继续依赖聊天区域内的 portal 作为最终形态。

### 4.2 CLI/TUI

CLI/TUI **不设常驻左侧导航**，不能照搬桌面端三栏。标准终端只分为主交互区和 Goal 状态区：

```text
┌────────────── 主交互区 ──────────────┬──────── Goal 状态区 ────────┐
│ 对话记录 / 命令输入 / 执行输出          │ 目标标题与状态               │
│                                       │ 总进度                       │
│                                       │ 当前任务                     │
│                                       │ 任务 / 验收 / 阻塞 / 证据     │
└───────────────────────────────────────┴────────────────────────────┘
```

CLI/TUI 区域职责：

| 区域 | 回答的问题 | 内容特征 |
| --- | --- | --- |
| 主交互区 | “正在交互和执行什么？” | 对话、Composer、命令与执行输出 |
| Goal 状态区 | “目标推进到哪、是否需要我介入？” | 结构化、实时、可聚焦、可折叠 |

会话和工作区不占用永久列宽：

- 当前工作区显示在顶部或底部紧凑状态行；
- 会话通过 `/session`、命令面板或 Session Picker 新建、浏览和切换；
- 工作区通过 `/workspace`、命令面板或 Workspace Picker 切换；
- Picker 是临时 Surface，关闭后焦点回到原主交互区或 Goal 状态区。

CLI/TUI 的 Goal 状态区不是 Desktop Workbench 的逐像素复制。两端共享信息层级、状态语义和 Runtime 状态源，但终端端采用键盘优先、低装饰、可折叠的呈现。

## 5. 信息架构

右侧状态区从上到下分为六层。

### 5.1 状态头部

固定展示：

- Goal 标题：一至两行，人类可读，不显示 `planId`；
- 总体状态：准备中、执行中、等待用户、已阻塞、已完成、已取消、失败；
- 总进度：`已完成任务数 / 总任务数` 与进度条；
- 最近更新时间：弱化显示，用于判断状态是否停滞。

状态颜色只能作为辅助，必须同时有图标和文字。

### 5.2 当前工作

这是默认视觉焦点，展示：

- 当前任务标题；
- 一句话说明 Agent 正在做什么；
- 运行状态或持续时间；
- 当前步骤需要用户输入时，展示明确的问题和操作入口。

不得用 `goal_update_task(planId, taskId, status)` 替代用户可读描述。

### 5.3 任务列表

任务按原顺序展示，并使用统一状态：

- `pending`：待处理；
- `running`：进行中；
- `completed`：已完成；
- `waiting_user`：等待用户；
- `failed`：失败；
- `cancelled`：已取消。

默认全部可见；任务较多时，已完成任务可折叠为“已完成 N 项”，当前任务和异常任务始终展开。每项主行只展示标题和状态，结果摘要、失败原因和证据放在展开区。

### 5.4 验收标准

展示 Definition of Done：

- 每条标准的说明和验证状态；
- 自动验证项区分“未运行、通过、失败”；
- 手动验收项提供明确的确认入口；
- 失败项可展开查看可读错误摘要与证据引用。

验收标准不能只显示内部 criterion ID。

### 5.5 阻塞与待确认

只在存在相关状态时出现，并置于当前工作之后：

- 等待用户回答；
- 权限或凭证缺失；
- 高风险、不可逆或范围扩张确认；
- 连续失败形成的阻塞；
- 手动验收确认。

待确认内容必须说明“为什么现在需要用户”“不确认会怎样”，并提供清晰主次操作。确认动作仍受 Goal/Plan 治理规范约束，状态区只是承载位置。

### 5.6 证据与诊断

默认折叠，提供两级信息：

1. 用户层：文件、测试、命令结果、截图等可读证据；
2. 诊断层：工具名、调用参数、原始返回、`planId`、`taskId`、artifact ref 等技术详情。

诊断层只在用户主动展开“查看技术详情”时显示，并允许复制。原始 JSON 不得作为默认内容。

## 6. 状态与生命周期交互

### 6.1 Goal 创建

当当前会话从无 Goal 变为有 Goal：

1. Workbench 自动展开；
2. 自动切换到 Goal tab；
3. 状态区先展示标题、目标和任务骨架；
4. 创建成功后原位更新为“执行中”；
5. 聊天流不新增 Goal 工具原始返回卡片。

用户手动关闭或切走 Workbench 后，不因普通进度更新反复抢焦点。

### 6.2 执行中

状态更新必须在同一 GoalView 原位发生，不为每次 `goal_update_task` 新增一张卡片。进行中任务有且只有一个主要视觉焦点；并行子任务可作为当前任务下的次级活动展示。

### 6.3 等待用户

当 Goal 需要实质性输入时：

- Goal tab 显示提醒标记；
- Workbench 已打开时切换或聚焦待确认区，但不覆盖用户正在输入的文本；
- 聊天流允许出现一条自然语言问题，保证关闭右栏时仍能发现；
- 用户可从聊天问题或状态区操作，二者共享同一状态，不得产生两个独立确认流程。

### 6.4 完成、失败与取消

- 完成：显示完成摘要、任务进度、验收结果和主要产物；
- 失败：显示可读失败原因、已完成范围和下一步建议；
- 取消：保留只读快照，明确“已取消”而不是显示为失败；
- 终态 Goal 不自动关闭，用户可主动收起或切换 Workbench tab；
- 历史 Goal 的浏览入口可后续设计，当前视图优先展示本会话最近的活跃 Goal。

## 7. 聊天流降噪规则

### 7.1 禁止默认展示的内容

聊天流不得直接展示 Goal 工具原始 JSON，也不得默认展示：

- `goal_create_plan`、`goal_update_task`、`goal_get_plan` 的完整参数和返回值；
- `Create(goal, successCriteria, tasks)`、`Update(planId, taskId, status)` 等协议式标题；
- `planId`、`taskId`、revision、store 路径；
- `ok: true`、`accepted` 等只有实现语境才成立的字段；
- 高频的逐任务状态变更；
- 因容器高度不足而截断的 JSON 片段。

### 7.2 聊天流应保留的内容

聊天流只保留对协作有意义的事件：

- Goal 已建立的一句确认（可选，避免与状态区重复）；
- 需要用户回答的问题或高风险确认；
- 目标发生实质性变更的说明；
- 关键阶段结论；
- 最终完成、失败或取消摘要。

推荐文案示例：

```text
已开始执行“Goal 右侧状态区设计”，进度可在右侧 Goal 面板查看。
```

不推荐：

```text
Create(goal, successCriteria, tasks)
{"ok":true,"planId":"...","status":"accepted"}
```

### 7.3 降级策略

当 Workbench 因小窗口、平台限制或渲染异常不可用时，聊天流可以显示一张紧凑 Goal 摘要卡，但必须满足：

- 只展示标题、状态、进度和当前任务；
- 不展示原始 JSON；
- 卡片是降级视图，不与右侧状态区同时重复出现；
- 提供恢复或打开 Goal 状态区的入口。

## 8. 与 Workbench 及其他状态入口的关系

### 8.1 与 right-workbench-panel 的关系

[`right-workbench-panel.md`](./right-workbench-panel.md) 是上位容器规范：

- 它定义 Workbench 的窗口级入口、Tab Rail、开合、尺寸、拖拽和持久化；
- 本文定义 `GoalView` 内部内容与交互；
- 两份文档冲突时，容器行为以 `right-workbench-panel.md` 为准，Goal 内容和聊天降噪以本文为准；
- 新 Goal 自动展开 Workbench 的规则沿用上位规范，本文补充自动展开后的内容呈现。

### 8.2 与底部状态栏/任务中心的关系

[`status-bar-task-center.md`](./status-bar-task-center.md) 负责跨会话、跨任务的全局轻量提醒；Goal 右侧状态区负责当前会话、当前 Goal 的完整状态。

底部状态栏只能显示简短聚合，例如“1 个 Goal 执行中”或“等待确认”，点击后打开对应会话和 GoalView。不得在底部状态栏复制完整任务列表。

### 8.3 与 Goal 工作流规范的关系

[`goal-mode-codex-cc-workflow.md`](./goal-mode-codex-cc-workflow.md) 定义运行治理、确认类型和完成门禁；[`goal-runner-explorer-task-list.md`](./goal-runner-explorer-task-list.md) 定义 Runner/Explorer 的执行细节；[`15-goal-plan-lifecycle-governance.md`](../../knowledge/specifications/15-goal-plan-lifecycle-governance.md) 约束 Goal 生命周期治理。

本文不改变这些规则，只规定它们如何以用户可理解的方式呈现。

## 9. 响应式与窗口行为

### 9.1 桌面客户端

- 标准宽度：沿用 Workbench 的宽度配置；
- 较窄宽度下，优先保留状态、当前任务和进度，次要元数据折叠；
- 主窗口不足以容纳三栏时，按 Workbench 规范吸附收起右侧栏；
- 收起后运行继续，Tab 提醒和全局状态入口保持可见；
- 面板滚动位置按会话保留，但当前任务或待确认发生变化时，应确保关键区可见；
- 用户展开证据详情时，不因后台状态刷新强制折叠或跳回顶部。

### 9.2 CLI/TUI

CLI/TUI 根据可用列宽逐级降级，不因维持双栏而压坏主交互区：

| 可用宽度 | Goal 状态区形态 |
| --- | --- |
| ≥120 列 | 主交互区 + 右侧 Goal 状态区并排；状态区可聚焦、折叠 |
| 80–119 列 | 默认单栏主交互区；Goal 通过快捷键或命令切换为覆盖式右侧抽屉 |
| 60–79 列 | Goal 使用全宽临时视图，与主交互区通过 Tab/快捷键切换 |
| 40–59 列 | 底部只保留 `Goal n/m · 状态` 紧凑摘要；详情进入全屏 Goal 视图 |
| <40 列 | 保留状态、待确认与错误恢复；提示终端过窄并建议扩宽 |

降级时遵守以下优先级：

1. 始终保留总体状态、总进度、当前任务、待用户确认和错误恢复动作；
2. 任务描述、时间、证据摘要等次要信息先折叠；
3. 原始 ID、工具参数和诊断数据只在技术详情中展示；
4. Goal 状态区隐藏或切换视图不影响 Runner 继续执行；
5. 不使用水平滚动承载 Goal 的关键状态和确认操作；
6. 抽屉或全屏 Goal 视图关闭后，焦点回到原 Composer 或执行记录位置。

## 10. 视觉与可用性原则

- 视觉角色是“客户端状态检查器”，不是消息气泡；
- 使用稳定分区、紧凑列表和原位更新，避免卡片无限堆叠；
- 标题和当前任务优先于 ID、时间戳和实现字段；
- 进行中状态允许克制的动态反馈，但不得持续闪烁；
- 状态不能只靠颜色表达；
- 技术详情使用等宽字体，普通状态信息使用界面字体；
- 键盘可遍历任务、验收项、确认按钮和折叠区；
- 屏幕阅读器只播报有意义的状态跃迁，不播报每次轮询或时间更新。

## 11. 数据映射原则

UI 应消费稳定的 Goal 视图模型，而不是直接渲染工具返回 payload。

建议的视图模型至少包含：

```ts
type GoalStatusViewModel = {
  id: string
  title: string
  goal: string
  status: 'preparing' | 'running' | 'waiting_user' | 'blocked' | 'completed' | 'failed' | 'cancelled'
  progress: { completed: number; total: number; percent: number }
  currentTask?: GoalTaskViewModel
  tasks: GoalTaskViewModel[]
  criteria: GoalCriterionViewModel[]
  pendingAction?: GoalPendingActionViewModel
  evidenceSummary?: GoalEvidenceSummaryViewModel
  updatedAt: number
}
```

映射层负责：

- 将内部状态转换为用户文案；
- 将空值、`0/0` 和初始化中状态区分开；
- 从工具结果中提取证据，而不是将整段结果 stringify；
- 屏蔽 store 路径、内部 revision 和无用户价值的字段；
- 保证右侧状态区和聊天流摘要来自同一份状态源。

## 12. 异常与边界场景

| 场景 | 预期表现 |
| --- | --- |
| 创建中尚无任务 | 显示“正在整理目标”，不得显示 `0/0 tasks accepted` |
| Goal 标题缺失 | 使用目标摘要生成可读回退标题，不使用 plan ID |
| 同一会话多个 Goal | 活跃 Goal 优先；历史终态 Goal 收入切换入口，不并排堆叠 |
| 状态更新乱序 | 以 store 的权威 revision 为准，UI 不回退到旧状态 |
| 工具结果解析失败 | 状态区显示“状态同步异常”，技术详情可查看原始错误 |
| 用户关闭 Workbench | Goal 继续运行，仅重要事件通过提醒暴露 |
| 小窗口无法显示右栏 | 使用紧凑摘要降级，不展示原始 JSON |
| Goal 被取消 | 保留只读任务和证据快照，主状态明确为“已取消” |

## 13. 验收标准

### 13.1 布局与定位

- [ ] 有活跃 Goal 时，主要状态展示位于界面右侧 Workbench 的 GoalView；
- [ ] Goal 不再以聊天流主内容或连续工具卡片存在；
- [ ] 新 Goal 可按 Workbench 规范自动展开并切换到 Goal tab；
- [ ] 用户手动关闭后，普通进度更新不会反复抢焦点。

### 13.2 信息可读性

- [ ] 用户无需展开技术详情即可看到标题、状态、总进度和当前任务；
- [ ] 任务、验收标准、阻塞原因均使用人类可读文案；
- [ ] 创建阶段不会出现“`0/0 tasks accepted`”这类误导状态；
- [ ] `planId`、`taskId` 和 store 路径不作为主界面内容。

### 13.3 聊天流降噪

- [ ] 聊天流不得直接展示 Goal 工具原始 JSON；
- [ ] `goal_update_task` 的普通状态更新只刷新右侧状态区，不新增消息；
- [ ] 只有用户提问、风险确认、重要变更和终态摘要进入聊天流；
- [ ] 降级摘要卡与右侧状态区不重复出现。

### 13.4 状态与操作

- [ ] 进行中、等待用户、阻塞、完成、失败、取消均有文字状态；
- [ ] 待确认可从状态区完成，且与聊天流问题共享同一状态；
- [ ] 自动验收项能区分未运行、通过和失败；
- [ ] 证据默认以可读摘要展示，原始数据只在技术详情中出现。

### 13.5 响应式与无障碍

- [ ] 面板收起或窗口过窄时，Goal 继续执行且重要提醒不丢失；
- [ ] 键盘可访问所有操作，焦点状态清晰；
- [ ] 状态变化不只依赖颜色；
- [ ] 屏幕阅读器不会被高频进度刷新持续打断。

## 14. 落地优先级

### P0：纠正产品形态

1. 将 Goal 主视图放入 Workbench 的 GoalView；
2. 停止在聊天流默认渲染 Goal 工具原始 JSON；
3. 展示标题、状态、进度、当前任务和任务列表；
4. 支持等待用户、完成、失败、取消等关键状态；
5. 确保 Goal 更新原位刷新。

### P1：完善可操作状态

1. 验收标准与证据摘要；
2. 阻塞、手动验收和风险确认；
3. Goal tab 徽标与底部状态栏联动；
4. 历史 Goal 切换；
5. 技术详情与复制诊断信息。

### P2：体验增强

1. 并行子任务和 Explorer 活动；
2. 阶段耗时与停滞提示；
3. 更完善的小窗口降级视图；
4. Goal 完成摘要与产物导航。

## 15. 已确认决策

1. Goal UI 的主要位置是界面右侧状态区；
2. GoalView 属于 Workbench，不另建第四栏；
3. Goal 状态原位更新，不在聊天流逐条堆叠；
4. 聊天流不得直接展示 Goal 工具原始 JSON；
5. 原始工具数据只进入主动展开的技术详情；
6. 主聊天区只保留需要协作的提问、决策、关键事件和最终摘要；
7. Workbench 关闭时 Goal 继续运行，并通过轻量提醒暴露重要状态；
8. CLI/TUI 不设常驻左侧导航，只保留主交互区与可折叠或可切换的 Goal 状态区；
9. CLI/TUI 的会话和工作区通过紧凑状态行、命令与临时 Picker 管理；
10. 窄终端依次降级为覆盖式抽屉、全宽临时视图和底部紧凑摘要，不用水平滚动承载关键状态。
