## 一、方案摘要

Peer Agent Desktop 在 macOS 状态栏常驻一个图标，将后台任务的**执行进展**与需要用户处理的**未读结果**集中到一个随时可达的任务中心。

用户不必切回主窗口，即可回答四个问题：

1. 现在有没有任务在执行？
2. 有多少任务需要我处理？
3. 有多少新结果还没看？
4. 点击后能否直接回到对应任务继续处理？

一句话定义：

> 状态栏任务中心是后台任务的轻量状态投影和回流入口，不是另一套任务系统，也不是主窗口的完整缩小版。

MVP 推荐采用“**图标表达最高优先级状态，数字表达待处理总量，面板展示分类明细**”的方式。不要在 macOS 菜单栏狭小空间里同时堆叠任务总数、执行中数和未读数。

## 二、背景与现状

### 2.1 用户问题

Peer Agent 可以在后台推进 Goal、执行工具、等待用户确认并产出结果。主窗口不在前台时，用户难以判断：

- 应用是否仍在工作，还是已经停住；
- 有几个任务正在执行；
- 哪些任务正在等待输入或授权；
- 哪些任务已完成但结果尚未查看；
- 失败发生在哪个会话，是否需要立即介入。

如果只发系统通知，通知容易消失且无法形成持续状态；如果只在 Dock 上显示数字，又无法区分“正在执行”和“需要处理”。因此需要一个常驻、低干扰、可展开的状态入口。

### 2.2 已有能力与缺口

结合当前 `peer_agent` 代码能力：

- 已有 `GoalPlan`、`GoalRunnerState`、`GoalProgress` 和 `ExecutionStatus` 等状态事实；执行状态包含 `pending`、`running`、`completed`、`failed`、`cancelled`、`waiting_user`。
- Goal 数据由主进程持久化，并通过 `goalPlans:changed` 广播驱动界面刷新，可作为状态栏聚合更新的事件来源之一。
- 已存在 Quick Chat/Popover 独立 `BrowserWindow` 的窗口治理基础，可参考其窗口定位、失焦收起和主窗口回流方式。
- 当前未发现 Electron `Tray` 常驻实现。
- 当前未发现统一的 `unreadCount`、`markAsRead` 或 `lastRead` 阅读回执模型。

因此，本方案不是简单增加图标，而是需要补齐一层**主进程统一任务投影**与**按任务记录的阅读状态**。状态栏只能消费统一事实，不能自行拼接多份 renderer 局部状态。

## 三、产品目标与非目标

### 3.1 产品目标

1. **一眼感知**：用户无需点击即可知道是否有任务执行中或需要处理。
2. **一次展开**：点击图标即可看到执行中、待处理、未读结果的数量与任务列表。
3. **一次回流**：点击列表项可打开主窗口并定位到对应工作区、会话及 Goal/任务。
4. **状态可信**：数字和状态来自持久化的统一任务事实，应用重启后不凭空丢失或重复。
5. **低打扰**：常态保持安静，仅在需要用户行动时提高视觉优先级。

### 3.2 非目标

MVP 不做：

- 在状态栏面板中完整查看会话或编辑 Goal 计划；
- 在菜单栏直接呈现进度条、token、耗时等全部运行细节；
- 用状态栏建立一套独立于主窗口的任务生命周期；
- 跨设备或跨账号同步未读状态；
- 将普通聊天的每条 assistant 消息都计为一项任务；
- 在面板内直接取消、重试、批准高风险操作。

## 四、核心概念与统计口径

### 4.1 聚合对象：任务卡（Task Item）

状态栏统计的最小对象是“任务卡”，而不是 Goal 子任务、工具调用或消息条数。

MVP 中：

- 一个可独立打开和处理的后台 Goal/运行实例，对应一个任务卡；
- 同一 Goal 下的多个 `GoalTask` 仅用于计算进度，不分别计数；
- Explorer、Verifier、工具调用是任务内部执行细节，不增加任务总数；
- 普通前台问答若没有形成可后台追踪的运行实例，不进入任务中心。

这样可以避免“一个用户任务拆成 6 个子任务，菜单栏却显示 6”的认知膨胀。

### 4.2 状态归一

任务卡状态统一映射为：

| 产品状态 | 底层状态示例 | 是否活跃任务 | 是否待用户处理 | 说明 |
|---|---|---:|---:|---|
| 排队中 | `pending`、Runner `queued` | 是 | 否 | 已接收，等待资源或调度 |
| 执行中 | `running`、Runner `running` | 是 | 否 | 当前正在推进 |
| 等待用户 | `waiting_user`、Runner `waiting_user` | 是 | 是 | 需要输入、确认、授权或选择 |
| 已完成 | `completed`、Runner `completed` | 否 | 仅未读时 | 结果已产生 |
| 失败 | `failed`、Runner `failed` | 否 | 是，直到查看 | 无法继续，需要用户查看或重试 |
| 已取消 | `cancelled`、Runner `cancelled` | 否 | 否 | 终止态，仅保留在近期记录 |
| 暂不可用 | 应用离线、状态读取失败 | 不确定 | 视情况 | 不把未知误报为 0 |

若计划状态与 Runner 状态短暂不一致，以更具体且更新时间更晚的持久化执行事实为准；聚合层必须输出 `updatedAt`，避免 renderer 自行猜测。

### 4.3 四个核心数字

#### A. 任务总数 `activeCount`

定义：所有**尚未进入终态**的任务卡数量。

```text
activeCount = queuedCount + runningCount + waitingUserCount
```

- 包含排队中、执行中、等待用户；
- 不包含已完成、失败、取消；
- 这是“当前仍占用用户心智的活跃任务”，不是历史任务累计数。

#### B. 执行中 `runningCount`

定义：当前真实处于 `running` 的任务卡数量。

- 不包含排队中；
- 不包含等待用户，因为等待用户时 Agent 已暂停推进；
- 子任务并行时仍按外层任务卡计 1，不按并发 worker 数计数。

#### C. 待处理 `actionRequiredCount`

定义：当前需要用户采取动作才能继续或收敛的任务卡数量。

```text
actionRequiredCount = waitingUserCount + unreadFailedCount
```

- `waiting_user` 立即进入待处理；
- 失败任务在用户打开对应任务前计入待处理；
- 已查看但尚未重试的失败任务不再显示未读红点，但仍可保留在“失败”筛选中；
- MVP 不把普通已完成未读计入“待处理”，避免把阅读结果误解为阻塞。

#### D. 未读 `unreadCount`

定义：产生了用户尚未查看的新终态结果或新阻塞请求的任务卡数量。

- 一张任务卡最多贡献 1 个未读，不按消息数累加；
- 首次进入 `waiting_user`、`completed` 或 `failed` 时生成新的 `attentionVersion`；
- 当 `attentionVersion > lastReadAttentionVersion` 时，该任务为未读；
- 任务从等待用户恢复执行后，该次等待请求视为已处理；后续再次等待会生成新的版本并重新未读；
- 应用重启保留阅读回执。

`unreadCount` 可拆分为：

```text
unreadCount = unreadWaitingCount + unreadCompletedCount + unreadFailedCount
```

### 4.4 “已读”的明确触发

以下行为标记单个任务已读：

1. 从状态栏面板点击任务并成功定位到主窗口对应会话；
2. 用户已在主窗口打开对应会话，且该任务的目标卡片进入可视区域；
3. 在后续版本中，用户显式点击“标记已读”。

以下行为**不**自动标记全部已读：

- 仅展开状态栏面板；
- 仅把 Peer Agent 主窗口置前；
- 收到系统通知；
- 点击“查看全部任务”但未打开具体任务。

MVP 不提供“全部已读”，避免误清除等待授权或失败等高优先级事项。

### 4.5 数字封顶与复数规则

- 菜单栏数字：`1–9` 原样显示，超过 9 显示 `9+`；
- 面板分组数字：显示真实数量；
- 同一任务同时处于“等待用户且未读”时，可同时计入 `activeCount`、`actionRequiredCount` 和 `unreadCount`，但任务列表只出现一次；
- 各数字回答不同问题，不要求相加等于任务总数。

## 五、信息优先级

从高到低：

1. **等待用户**：任务无法继续，用户动作价值最高；
2. **失败**：任务已中断，需要查看原因；
3. **执行中**：需要持续感知，但不要求立即操作；
4. **已完成未读**：有新结果可查看；
5. **排队中**：已接收但尚未执行；
6. **已读终态**：仅在近期任务或筛选中出现。

当多个状态同时存在，图标只表达最高优先级，数字表达对应的首要行动量；完整数量放入面板，避免菜单栏信息过载。

## 六、状态栏常驻图标方案

### 6.1 图标结构

使用 macOS Template Image，适配浅色、深色和高对比度菜单栏。图标由两部分组成：

- 左侧：Peer Agent 单色标识/任务环；
- 右侧：可选数字文本，最多两字符宽（`9+`）。

不建议同时放置三个数字，也不建议靠多种品牌色区分状态；菜单栏以形状、动效和数字为主，颜色只作辅助。

### 6.2 状态映射

| 场景 | 图标表现 | 菜单栏数字 | Tooltip 示例 |
|---|---|---|---|
| 无活跃、无未读 | 静态常规图标 | 无 | `Peer Agent · 暂无待处理任务` |
| 有排队，无执行 | 图标带小空心点 | 活跃任务数 | `3 个活跃任务，等待执行` |
| 有执行中 | 任务环低频旋转/呼吸 | `runningCount` | `2 个任务执行中` |
| 有完成未读，无更高状态 | 静态图标带实心点 | `unreadCount` | `3 个新结果` |
| 有等待用户 | 图标带感叹标记，停止运行态动效 | `actionRequiredCount` | `2 个任务等待你处理` |
| 有失败 | 警示形态 | `actionRequiredCount` | `1 个任务失败` |
| 状态暂不可用 | 图标降级为斜线/空心态 | 无 | `任务状态暂不可用` |

优先级：`等待用户 > 失败 > 执行中 > 完成未读 > 排队 > 空闲`。

若等待用户与失败并存，统一显示“待处理”形态和待处理总数；在面板中分别标明原因。

### 6.3 动效与可访问性

- 执行中动效周期建议 1.6–2.0 秒，避免高频闪烁；
- “减少动态效果”开启时，改为静态双环或小点，不旋转；
- 状态变化不通过闪烁吸引注意；
- Tooltip 必须提供完整文字，不能只靠颜色；
- 系统离线不应继续展示旋转动效。

### 6.4 Dock 与状态栏关系

MVP 以状态栏为主：

- Dock Badge 可同步 `actionRequiredCount + unreadCompletedCount`，但默认可关闭；
- Dock Badge 和状态栏必须消费同一聚合快照；
- 菜单栏图标常驻不意味着隐藏 Dock 图标，应用仍是标准桌面应用；
- “关闭主窗口”默认只关闭窗口，不退出应用，状态栏任务继续更新。

## 七、下拉面板交互

### 7.1 打开与关闭

- 单击状态栏图标：打开锚定在图标下方的 Popover；再次点击关闭；
- 点击面板外部或按 `Esc`：关闭；
- 面板打开时主窗口不自动抢焦点；
- 右键 MVP 与左键行为一致，后续可扩展原生快捷菜单；
- 若主窗口已退出但后台运行仍存在，状态栏继续可用。

建议尺寸：宽 360–400 pt，高度按内容自适应，最大约 560 pt，超出后列表滚动。

### 7.2 面板信息架构

```text
┌────────────────────────────────────┐
│ Peer Agent                  [设置] │
│ 2 执行中 · 1 待处理 · 3 未读       │
├────────────────────────────────────┤
│ 需要你处理（1）                    │
│ ! 发布前确认权限                    │
│   等待确认 · peer_agent · 2 分钟   │
├────────────────────────────────────┤
│ 执行中（2）                        │
│ ◌ 状态栏任务中心产品方案       33% │
│   peer-knowledge · 刚刚更新        │
│ ◌ 修复构建错误                  …  │
├────────────────────────────────────┤
│ 新结果（3）                        │
│ ✓ 单元测试修复完成                 │
│ × O2 发布任务失败                  │
├────────────────────────────────────┤
│ [打开 Peer Agent]     [查看全部任务]│
└────────────────────────────────────┘
```

### 7.3 分组规则

面板按以下固定顺序展示：

1. **需要你处理**：等待用户、未读失败；
2. **执行中**：running；
3. **排队中**：pending/queued，仅有时出现；
4. **新结果**：completed/failed 的未读结果；
5. **近期任务**：MVP 可不展示，后续加入。

同一任务只出现在最高优先级分组。例如失败未读进入“需要你处理”，不再在“新结果”重复展示。

每组默认最多 5 项，超出显示“还有 N 项”，点击进入主窗口完整任务页。

### 7.4 任务卡内容

每项最多三行：

- 第一行：状态图标 + 任务标题 + 可选进度百分比；
- 第二行：状态文案 + 工作区名称；
- 第三行（按需）：更新时间或等待原因摘要。

标题回退顺序：Goal 标题 → 会话标题 → 用户首条任务摘要 → `未命名任务`。

执行进度：

- 有可靠 `GoalProgress.percent` 时展示百分比；
- 无可靠进度时展示不定态图标，不伪造百分比；
- `waiting_user` 展示具体动作，如“等待确认”“等待授权”“等待补充信息”。

### 7.5 点击行为

点击任务项：

1. 关闭状态栏面板；
2. 显示并聚焦 Peer Agent 主窗口；
3. 切换到任务所属工作区；
4. 打开对应会话；
5. 定位并高亮对应 Goal/待确认卡片；
6. 确认定位成功后写入该任务阅读回执。

若工作区路径失效或会话已删除：

- 不清未读；
- 主窗口显示可恢复错误：“原工作区不可用，任务记录仍可查看”；
- 提供“重新选择工作区”或“仅查看记录”。

底部操作：

- **打开 Peer Agent**：仅打开主窗口当前页面，不清未读；
- **查看全部任务**：打开主窗口任务中心/Goal 列表；
- **设置**：进入通知与状态栏设置。

### 7.6 空状态

无活跃、无未读时：

```text
一切就绪
当前没有执行中或待处理的任务。
[发起新任务]  [打开 Peer Agent]
```

“发起新任务”复用 Quick Chat 入口，而不是在状态栏面板内再造输入框。

## 八、状态变化与通知策略

> **完整规格**见《任务完成系统通知方案》`design/product/task-completion-system-notification.md`。  
> 本节只保留任务中心视角的摘要；发送决策、前台抑制、权限、文案与点击回流以该文档为准。系统通知由主进程 Notification Broker 统一发出，状态栏与 Quick Chat **不得**各自再发一套。

### 8.1 何时只更新图标

以下变化默认静默更新状态栏，不发系统通知：

- 排队 → 执行中；
- 进度百分比变化；
- 用户正在查看对应会话时任务完成；
- 已取消；
- 短暂断网后自动恢复且任务未失败。

### 8.2 何时发系统通知

默认通知：

- 首次进入等待用户；
- 后台任务完成且主窗口不在前台（或前台但当前会话不是该任务）；
- 后台任务失败。

通知去重：同一任务、同一 `attentionVersion` 最多发一次。点击通知与点击状态栏任务项走同一深链和已读规则。启动重算不回放历史通知。

### 8.3 连续状态合并

- 任务在 2 秒内从 running 直接 completed，可不闪现中间菜单栏数字；
- 多个任务在短时间内完成，可合并为“3 个任务已完成”（通知侧合并为 V1.1，见系统通知方案 §8.3）；
- waiting_user 不与普通完成通知合并；
- 更新采用事件触发 + 启动时全量重算，不依赖高频轮询。

## 九、异常与边界状态

| 异常 | 产品表现 | 处理原则 |
|---|---|---|
| 应用刚启动、数据加载中 | 图标静态，不显示 0 | 未知不是空闲 |
| 主进程聚合读取失败 | 降级图标 + “状态暂不可用” | 保留上次快照但标记过期，不继续动效 |
| 网络离线但本地任务仍可执行 | 面板顶部轻提示“网络不可用” | 不笼统将所有任务判失败 |
| 任务长时间无更新 | 显示“最后更新于…” | MVP 不自动判定卡死 |
| 应用崩溃后重启 | 从持久化事实恢复 | running 若无存活执行，应归一为中断/失败，不继续假运行 |
| 会话或工作区被删除 | 卡片保留，深链失败提示 | 不静默清未读 |
| 通知权限关闭 | 状态栏仍完整工作 | 设置页提示，不反复弹系统授权 |
| 图标资源加载失败 | 使用文字/备用模板图标 | 保证入口可点击 |
| 数量快速波动 | 100–200 ms 合并刷新 | 防止图标抖动 |
| 系统进入睡眠 | 不累积动画 | 唤醒后全量重算快照 |

## 十、与 Quick Chat 任务卡协同

状态栏任务中心与 Quick Chat 输入框下方任务卡是同一任务系统的两个投影，不各自维护列表或统计：

- **状态栏任务中心**负责全局感知与完整分组，回答“整体有多少任务、哪些需要处理”；
- **Quick Chat 任务卡**负责高频接续与低风险快捷操作，回答“我现在能否立即完成这个选择”；
- **主窗口**负责完整上下文、长结果审阅、高风险确认和复杂恢复。

三者统一消费 `TaskCenterSnapshot`，共享 `taskId`、归一状态、排序基础、`attentionVersion` 和阅读回执。Quick Chat 的展示是任务中心全集的有意裁剪：优先展示全部等待用户任务；无等待时只展示最近的一个执行中或完成未读任务；已读终态与已处理失败不进入 Quick Chat。

跨入口规则：

1. 状态栏点击某任务可按任务能力选择打开 Quick Chat 或主窗口；需要简短选择时优先 Quick Chat，需要审阅上下文时打开主窗口；
2. Quick Chat 中完成选择后，状态栏的待处理数与未读数立即更新；
3. 状态栏只展开面板不批量清除未读，Quick Chat 只显示卡片也不清除未读；
4. 任一入口展示完整的对应版本内容或成功提交动作后，写入同一阅读回执；
5. 同一动作被其他入口处理后，所有入口立即失效旧按钮并显示最新状态；
6. 高风险、不可逆、线上发布、批量授权和复杂表单不得在 Quick Chat 或状态栏面板内执行，必须深链主窗口。

Quick Chat 任务卡的布局、任务选择器、快捷操作和安全边界以《快速会话浮窗（Quick Chat）产品与交互方案》的“输入框下方任务卡”章节为准。本方案负责统一数据与跨入口规则，避免出现数字不一致、重复提醒或已处理动作仍可点击的问题。

## 十一、产品数据模型建议

主进程维护只读聚合投影，示意如下：

```ts
type TaskCenterItem = {
  taskId: string;
  conversationId: string;
  goalPlanId?: string;
  workspacePath?: string;
  title: string;
  status: 'queued' | 'running' | 'waiting_user' | 'completed' | 'failed' | 'cancelled';
  progressPercent?: number;
  attentionVersion: number;
  lastReadAttentionVersion: number;
  attentionReason?: 'input' | 'confirmation' | 'permission' | 'completed' | 'failed';
  updatedAt: string;
};

type TaskCenterSnapshot = {
  activeCount: number;
  runningCount: number;
  waitingUserCount: number;
  actionRequiredCount: number;
  unreadCount: number;
  generatedAt: string;
  stale: boolean;
  items: TaskCenterItem[];
};
```

约束：

- `taskId` 必须稳定，不能用列表索引或临时 renderer ID；
- 阅读回执由主进程持久化；
- Tray、Popover、Dock Badge、系统通知消费同一 `TaskCenterSnapshot`；
- renderer 不独立计算总数；
- 聚合器订阅 Goal/运行/会话状态变化，应用启动、唤醒及异常恢复时做全量重算；
- 对历史数据缺少阅读版本时，迁移默认设为已读，避免升级后瞬间出现大量旧未读。

## 十二、MVP 范围

### 12.1 MVP 必须包含

1. macOS 状态栏常驻 Template Image 图标；
2. 空闲、执行中、待处理、未读、状态不可用五类视觉状态；
3. 菜单栏最多显示一个数字，按优先级展示待处理数、执行中数或未读数；
4. 下拉面板展示总览、需要处理、执行中、新结果三类核心分组；
5. `activeCount`、`runningCount`、`actionRequiredCount`、`unreadCount` 的统一统计口径；
6. 单任务阅读回执持久化；
7. 点击任务深链到主窗口对应工作区/会话/Goal；
8. waiting、completed、failed 的系统通知与去重；
9. 启动、退出主窗口、睡眠唤醒、聚合失败时的状态恢复；
10. “退出 Peer Agent”明确入口，避免用户误以为关闭窗口等于退出后台任务。

### 12.2 MVP 明确不包含

- 面板内输入消息、批准权限、重试、取消任务；
- 自定义排序、筛选器与搜索；
- “全部已读”；
- 近期历史任务的完整浏览；
- 多账号、跨设备同步；
- 每个子 Agent/工具调用的并发数字；
- 用户自定义菜单栏指标；
- Windows/Linux 系统托盘适配。

### 12.3 后续迭代

**与近期会话 Tray 的合并顺序**

- P0 菜单栏优先落地 Codex 式「近期会话原生 Menu」，见 `design/product/menu-bar-tray-recent-sessions.md`。
- 本任务中心方案作为同一菜单栏槽位的后续演进：任务态图标/数字 + 点击展开任务 Popover；避免并排第二个 Peer 图标。
- 合并前两者可并行设计，但实现上应共用主进程 Tray 生命周期，不可各建一套互斥 Tray。

**V1.1：快捷处理**

- 对低风险 `waiting_user` 在面板内提供批准/拒绝；
- 失败任务提供重试；
- 单项标记已读/未读；
- 任务完成合并通知。

**V1.2：任务管理**

- 搜索、筛选与近期历史；
- 暂停、取消、调整优先级；
- 按工作区分组；
- 展示预计剩余时间（仅有可靠估算时）。

**V2：跨平台与同步**

- Windows/Linux Tray；
- 多设备阅读状态同步；
- 团队任务与远程执行节点。

## 十三、产品验收标准

### 13.1 图标与数字

1. 启动 Peer Agent 后，macOS 状态栏出现可点击的常驻图标。
2. 无活跃、无未读时不显示数字，Tooltip 明确显示暂无待处理任务。
3. 有 2 个运行任务且无更高优先级状态时，图标展示运行态，数字为 `2`。
4. 同时存在 2 个运行任务和 1 个等待用户任务时，图标优先展示待处理态，数字为 `1`；面板总览仍显示“2 执行中 · 1 待处理”。
5. 数量大于 9 时菜单栏显示 `9+`，面板显示真实数量。
6. 开启“减少动态效果”后，执行态不使用旋转或呼吸动画。

### 13.2 统计口径

7. 一个 Goal 含 6 个子任务时，活跃任务数只增加 1。
8. 一个任务有 3 个并行 Explorer 时，执行中任务数只增加 1。
9. `waiting_user` 计入活跃任务和待处理，但不计入执行中。
10. 已完成任务不计入活跃任务；结果未读时计入未读。
11. 同一失败任务无论产生多少错误事件，未读数最多增加 1，除非产生新的 `attentionVersion`。
12. 应用重启后，已读任务不重新变为未读。

### 13.3 面板与回流

13. 单击图标打开面板，再次点击、点击外部或按 `Esc` 均可关闭。
14. 面板按“需要你处理 → 执行中 → 排队中 → 新结果”的顺序展示，空分组不出现。
15. 同一任务不在多个分组重复出现。
16. 点击等待用户任务后，主窗口打开并定位到对应会话和待处理卡片；定位成功后该任务未读消除。
17. 仅打开面板不会清除任何未读；仅点击“打开 Peer Agent”也不会批量清除未读。
18. 工作区失效时点击任务得到明确错误和恢复入口，未读不被清除。

### 13.4 生命周期与异常

19. 关闭主窗口后状态栏仍存在，后台任务状态继续更新。
20. 从状态栏选择“退出 Peer Agent”后应用进程退出；若有运行任务，先明确提示影响。
21. 应用启动加载或聚合失败时不错误显示“0 个任务”。
22. 系统睡眠唤醒后 2 秒内完成一次全量快照重算，并显示与持久化事实一致的状态。
23. 崩溃重启后，不存在实际运行实例的旧 `running` 任务不得继续显示旋转执行态。
24. 同一任务、同一注意版本最多产生一次系统通知。

### 13.5 性能与可访问性

25. 任务状态变化后，状态栏与面板在正常本地条件下 500 ms 内完成可见更新。
26. 100 个任务卡的聚合更新不阻塞主窗口输入，面板首屏只渲染必要条目。
27. 浅色、深色、高对比度菜单栏下图标均清晰可辨。
28. 所有状态都有文字说明，不依赖颜色作为唯一信息载体。

## 十四、埋点与效果判断

建议事件：

- `task_center_tray_clicked`
- `task_center_item_opened`（携带状态类型，不携带任务正文）
- `task_center_deep_link_succeeded/failed`
- `task_center_notification_clicked`
- `task_center_attention_time`（进入待处理到用户打开的时长）
- `task_center_snapshot_stale`

核心指标：

1. 等待用户任务的中位响应时间是否下降；
2. 后台完成任务在 24 小时内被打开的比例；
3. 深链成功率；
4. 状态数量与主窗口事实不一致的错误率；
5. 用户关闭状态栏图标或通知的比例。

不采集任务标题、消息正文、工作区路径等敏感内容。

## 十五、待评审决策

1. 菜单栏数字是否默认遵循本方案的动态优先级，还是固定只显示待处理数？
2. Dock Badge 是否默认开启，还是仅状态栏展示数字？
3. “失败已查看但未重试”是否继续保留在待处理分组？本方案建议移出待处理，保留在失败筛选。
4. 主窗口是否已有统一任务中心页面可承接“查看全部任务”；若没有，MVP 可先落到 Goal 列表。
5. 用户选择“退出”且有运行任务时，是阻止退出、二次确认后中止，还是允许后台辅助进程继续？需要结合运行架构确定。

## 十六、实现边界建议

后续进入技术设计时，应坚持：

1. 主进程是任务聚合、阅读回执、Tray 生命周期和通知去重的唯一事实源。
2. 状态栏面板只读消费快照并发起深链，不直接改 Goal 状态。
3. 复用现有 Goal 持久化与 `goalPlans:changed` 等事件，不从 UI DOM 反推任务状态。
4. 复用 Quick Chat 已有窗口治理经验，但任务中心使用独立受控 Popover，避免相互抢焦点。
5. 阅读回执必须与具体任务的 `attentionVersion` 绑定，不能只保存一个全局最后打开时间。
6. 先建立状态归一和可测试聚合器，再接 Tray 图标；否则图标数字会成为新的局部真相。
