## 0. 一句话

打开一个项目，你面对的是这个项目的代理。你发的每条消息都会被它接住：能直接答的直接答，要干活的就锚定这条消息单独开一个任务去做，做完把关键信息整理成一条「回复你那条消息」的回答。任务跑着你随时可以插话，代理自己判断是并入、停掉重开还是另开一条。

> 把工作交给 Peer，只在真正需要你的时候回来。——这句话从此有了一个具体的「对面」。

---

## 1. 为什么改

原型 A 下，用户要自己开任务、切任务、去工作台雷达看哪条线要处理。用户仍在当项目经理，只是工具更好用了。

项目代理把「拆几条任务、先做哪条、哪条卡住了、要不要换方案」交给 Peer。用户保留三件事：给目标和边界、处理例外（权限、决策）、签收结果。

参照：Grok Bot 的「总管常驻、按需派人、只在要判断时拉你」；Grok Build 的「子会话独立上下文、嵌套深度固定」。我们只取委托结构，不取「一群常驻 bot 互相聊天」的团队形态。

## 2. 用户看到什么

### 2.1 信息架构

```text
左栏：项目列表
      每个项目一行：项目名 · 代理状态（空闲 / 推进中 N 条） · 角标（需要你 N · 待验收 M）
      底部：全局收件箱（跨项目的需要你 / 待验收）

主区：当前项目的代理对话（锚定回复模式，见 §2.3）
      你的消息：带处理状态标记（处理中 · 需要你 · 已回复）
      代理的回复：顶部引用它回应的那条消息，正文是整理后的结论，附来源与卡片

右栏：本项目的任务
      进行中 · 需要你 · 待验收 · 已结束（折叠）
      点一条 → 只读查看任务现场 → 可「直接介入」
```

### 2.2 旧概念去向

| 原型 A | 项目代理模式 |
|---|---|
| 侧栏 Workspace + 任务树 | 侧栏项目列表；任务移到右栏 |
| 主区 = 当前任务 | 主区 = 项目代理对话；进入任务是「介入」 |
| 「新建任务」按钮 | 取消。和代理说话，代理决定开不开任务 |
| 工作台雷达页 | 降级为侧栏角标 + 全局收件箱；独立页进入退场评估 |
| Agent / Plan 模式切换器 | 从代理输入框退场。要不要先批计划，由代理判断后递批准卡 |
| 验收抽屉 | 保留，从代理对话的待验收卡或右栏打开 |
| 任务内 Goal 面板、Explorer / Verifier | 保留，在任务现场里看 |
| 「任务」称谓 | 保留。代理开出的执行单位就叫任务 |

### 2.3 锚定回复模式（核心交互）

代理对话不是一问一答的流水，而是「每条消息都被接住、被回应」：

```text
你发一条消息 M
  → 代理接住 M（M 上出现处理状态标记）
  → 代理结合上下文判断：直接回答 / 开任务 / 并入已有任务 / 停掉旧任务改开新任务
  → 开任务时：任务锚定在 M 上，带着 M 的原话、代理写的任务说明、截至 M 的对话上下文快照
  → 任务在后台跑，关键信息结构化交回
  → 代理把交回的信息重新整理，发一条「回复 M」的消息：顶部引用 M，正文是结论
```

一条消息的三种样子：

| 元素 | 长什么样 | 数据 |
|---|---|---|
| 你的消息 | 右下角状态标记：`● 处理中 · 用量面板按天分组`、`需要你`、`已回复`、`已并入「…」`、`已被新消息取代` | 消息的处置记录（§运行时契约 2.4） |
| 代理的回复 | 顶部灰色引用条显示被回复消息的前一行，点击跳回原消息；正文；底部「来源：任务 X」芯片；需要时附卡片 | `replyTo`、`sourceSessionIds` |
| 进度 | 不刷消息。任务进度只体现在你那条消息的状态标记和右栏 | `WorkSession` 投影 |

插话：任务跑着的时候你随时可以继续发消息。

- **不引用直接发**：代理结合正在跑的任务自己判断这条新消息和哪件事有关，决定怎么处置（§3.5）。
- **引用某条消息再发**（复用输入框已有的引用能力）：明确指定「我说的是这件事」，代理只在这条消息对应的任务上做处置，不再猜。

代理的每一个处置都写在你那条消息的状态标记上，停掉旧任务时还会给「恢复原任务」的入口，所以它自己拿主意，你随时能看见、能撤回。

### 2.4 内联卡片

卡片附在代理的回复里，不单独刷屏。

| 卡片 | 什么时候出现 | 主动作 | 真源 |
|---|---|---|---|
| 任务已开出 | 只在代理的回复里需要说明时出现；平时由消息状态标记表达 | 查看任务 | `WorkSession` 投影 |
| 计划待批准 | 代理判断任务需要先批计划 | 批准 / 修改成功标准 / 拒绝 | 任务 GoalPlan |
| 需要你 | 任务请求权限、需要决策或补充信息 | 批准 / 拒绝 / 回答 | main 里同一条待处理请求 |
| 待验收 | 任务机器完成 | 查看依据（打开验收抽屉） | GoalPlan 关闭闸门 |
| 任务失败 / 停滞 | 任务失败或长时间无进展 | 代理给出建议；用户可让它重试或取消 | GoalPlan + blockerAudit |

卡片只是同一事实的另一个出口。在代理对话里批准和在任务里批准，解决的是同一条请求。

## 3. 典型动线

### 3.1 纯问答

```text
你：登录模块的 token 过期时间在哪配？
代理：（读文件、搜索）在 xxx.ts 第 42 行，默认 7 天……
```

不开任务，不进待验收。

### 3.2 一件要做的事

```text
你：把设置页的用量面板改成按天分组                        [● 处理中 · 用量面板按天分组]
…（你可以离开；进度在状态标记和右栏）
代理：┃ 回复「把设置页的用量面板改成按天分组」
      要跑一次 pnpm test 验证，需要你允许。
      [卡片] 需要你：运行 pnpm test                     ← 你点允许
…
代理：┃ 回复「把设置页的用量面板改成按天分组」
      改好了。按天分组放在面板顶部，跨时区按本地日期切分；三条标准都有证据。
      改动在 feat/usage-by-day，共 4 个文件。
      来源：任务「用量面板按天分组」   [卡片] 待验收 → 查看依据
你的消息状态：[已回复]
```

### 3.3 一句话多件事

```text
你：发 0.0.18 之前把三个已知 bug 修掉，再更新 release notes   [● 处理中 · 4 条任务]
…
代理：┃ 回复「发 0.0.18 之前…」
      bug #1、#3 已修好待验收；#2 卡在复现环境，我补了复现步骤让它继续。
      release notes 等三个 bug 验收后再写。
      来源：3 条任务   [卡片] 待验收 ×2
```

一条消息可以对应多条任务。代理可以在关键节点先回一次，全部结束后再回一次总的；都挂在同一条消息下。

### 3.4 直接介入

你在右栏点开「bug #2」任务，看到它的对话和 Goal 面板，直接发一句「别改 API，改调用方」。代理下次回合能看到你介入过，不会覆盖你的指令。

### 3.5 插话：代理自主处置

任务跑着时你发了新消息 N，代理在五种处置里选一种，并把结果写在 N 的状态标记上：

| 处置 | 什么时候 | 例子 | N 的状态标记 |
|---|---|---|---|
| 直接回答 | N 是提问，不影响任何任务 | 「现在用的是哪个图表库？」 | 已回复 |
| 并入 | N 是对某条在跑任务的补充或纠偏，目标没变 | 「顺便把周视图也加上」 | 已并入「用量面板按天分组」 |
| 取代 | N 改变了某条在跑任务的目标，继续跑是浪费 | 「算了，不按天，改成按模型分组」 | 已停掉「按天分组」，改开「按模型分组」· 恢复原任务 |
| 并行 | N 是另一件独立的事 | 「另外把登录页的文案也改一下」 | 处理中 · 登录页文案 |
| 停止 | N 明确叫停 | 「先别弄了」 | 已停掉「用量面板按天分组」 |

还有一种是「排队」：N 依赖某条在跑任务的结果（「做完之后再把文档也更新」），代理开出新任务但挂上依赖，等前一条完成后才开始。

取代时，新任务继承旧任务的上下文：旧任务的报告、已读过的材料、任务分支（代理判断改动还能用时继承分支，否则从源头重新拉）。旧任务停下但分支保留，「恢复原任务」就是让它接着跑。

你引用了某条消息再插话时，代理只在那条消息对应的任务上选「并入 / 取代 / 停止」，不会误伤别的任务。

## 4. 代理说话的规矩

写进 `project-agent-source` 的角色契约，同时在产品验收里检查：

1. 每条消息都要有处置：回答、开任务、并入、取代、并行、停止、排队，七选一（可组合，例如同时并入一条、并行开一条）。不允许一条消息没有下文。
2. 能直接回答的就直接回答，不为了显得勤快而开任务。
3. 要产生任何副作用，一律开任务；任务锚定在触发它的那条消息上，带上用户原话，不只带代理的转述。
4. 回复必须挂在被回复的消息上，内容基于任务交回的关键信息重新整理：先结论，再必要细节；不照抄任务日志。说「做完了」时附待验收卡，不自己宣布完成。
5. 自主处置要留痕：并入、取代、停止都写在用户消息的状态标记上；取代必须说一句为什么。
6. 不替用户做判断：权限、范围扩大、不可逆动作、产品取舍，都递卡片。已经待验收的任务代理不能停，只能另开。
7. 过程不刷屏：任务进度只体现在消息状态标记和右栏，代理只在需要你、完成、失败或它改变了处置时开口。

## 5. 分期

### P0 文档与契约

- 修订产品对齐文档、改造总纲；新写 ADR 80、运行时文档、本文。
- 验收：评审通过，ADR 80 转 Accepted。

### P1 骨架（feature flag：`projectAgentMode`）

- 每个项目懒创建一条项目代理对话；`project_agent` 模式与白名单投影。
- 调度能力：`spawn_session`、`list_sessions`、`get_session_report`。
- 任务跑现有 Goal Runner；`session_result_ready` / `session_ended` 唤醒代理。
- 锚定回复骨架：任务锚定在触发消息上并带上下文快照；代理回复带 `replyTo` 引用条与来源芯片；用户消息的处理状态标记。
- 界面：主区代理对话、右栏任务清单、待验收卡。
- 验收：一句话 → 该消息出现「处理中」→ 任务完成 → 代理发一条引用原消息的整理回复并附待验收卡 → 你签收。代理全程无法写文件。

### P2 冒泡与插话

- `session_needs_user`：权限、决策、计划批准卡以「回复原消息」的形式冒泡到代理对话，两处同步。
- 插话处置：回答、并入（`message_session`）、停止（`cancel_session`）；引用某条消息插话时限定处置范围。
- 右栏点进任务可直接介入；`user_intervened` 事件。
- 验收：任务跑着时插话，每条插话都有可见处置；引用插话只影响对应任务；代理没有任何批准入口；介入后代理不覆盖用户指令。

### P3 并行与取代

- 多任务并发、写仓库任务自动 worktree、主工作区脏时拒绝开出。
- 插话处置补齐：并行、排队（依赖）、取代（继承旧任务上下文与可选分支）+「恢复原任务」。
- 并发上限与唤醒频率上限；代理的只读临时调研 `spawn_subagent`。
- 验收：§3.3、§3.5 场景跑通；取代后恢复原任务能接着跑；三条任务互不污染工作区。

### P4 连续性与主动性

- 代理长对话压缩 + 项目记忆（与路线图中景 #5 合流）。
- 停滞检测与主动纠偏；与 Automation 结合做定时巡检。
- 手机 / 远程入口对接项目代理（路线图中景 #4 / #4b）。

### P5 迁移与清理

- 旧会话归为项目下的「历史任务」。
- 侧栏任务树、独立工作台页、代理输入框的模式切换器退场；flag 默认开启。
- 验收：老用户升级后每个项目都能看到原有任务，且没有被改写。

## 6. 风险

| 风险 | 缓解 |
|---|---|
| 每句话多一跳，慢且贵 | 代理用快模型；纯问答直接回答；进度不唤醒代理 |
| 代理对话常驻，上下文膨胀 | 压缩必需；roster 每轮重新生成且只注入快照 |
| 代理转述丢细节 | 任务带用户原话；交回的关键信息结构化；回复带来源芯片直达任务现场与验收依据 |
| 代理误判插话，停错任务 | 处置写在消息状态标记上；取代可「恢复原任务」；引用插话限定范围；待验收任务代理不能停 |
| 并行写冲突 | 第二条写仓库任务起强制 worktree |
| 用户不信任「看不见的任务」 | 右栏常驻任务清单；任何任务一键进入现场 |
| 代理变成话痨 | §4 规矩 5；产品验收检查代理自发消息频率 |

---

## 7. 非目标

- 多个常驻专职代理、代理之间的群聊。
- 代理直接做「很小的改动」。
- 代理替用户批权限、批计划或签收结果。
- 新建 Task / Project 存储实体。
- 把工作台雷达做成更重的工单台来弥补可见性。
