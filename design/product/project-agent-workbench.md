## 0. 一句话

打开一个项目，你面对的是这个项目的代理。你发的每条消息都会被它接住：能直接答的直接答，要干活的就锚定这条消息单独开一个任务去做，做完把关键信息整理成一条「回复你那条消息」的回答。任务跑着你随时可以插话，代理自己判断是并入、停掉重开还是另开一条。

> 把工作交给 Peer，只在真正需要你的时候回来。——这句话从此有了一个具体的「对面」。

---

## 1. 为什么改

原型 A 下，用户要自己开任务、切任务、去工作台雷达看哪条线要处理。用户仍在当项目经理，只是工具更好用了。

项目代理把「拆几条任务、先做哪条、哪条卡住了、要不要换方案」交给 Peer。用户保留三件事：给目标和边界、处理例外（权限、决策）、签收结果。

参照：Grok Bot 的「总管常驻、按需派人、只在要判断时拉你」；Grok Build 的「子会话独立上下文、嵌套深度固定」。我们只取委托结构，不取「一群常驻 bot 互相聊天」的团队形态。

## 1.1 首启：没有「创建机器人」这一步

沿用首启引导「情境式、不做向导」的原则（`first-run-onboarding-guidance.md`）。每个项目自动有且只有一个项目代理，用户不需要创建它：

1. **接入模型**：至少一个。只有一个时，强 / 快 / 省 / 视觉四档都指向它（ADR 83），无需分工设置。
2. **添加项目**：选文件夹，生成稳定 `workspaceId`（ADR 81），项目代理自动就位。
3. **代理先熟悉项目**：主动开一条只读任务（目录、AGENTS.md、脚本、最近提交），把确认过的事实写进项目记忆、生成项目简报，然后用一两句话说它看到了什么，并提出一两个不确定的问题（回答记为「你说的」记忆）。零副作用。
4. **开始用**：输入框上方的建议根据刚读到的内容生成，不是通用模板。

老用户升级：已有工作区直接成为项目，代理就位后同样先熟悉项目；旧会话归为该项目的历史任务，不改写。

## 2. 用户看到什么

### 2.1 信息架构

```text
左栏：项目列表
      每个项目一行：项目名 · 代理状态（空闲 / 推进中 N 条） · 角标（需要你 N，含需要你确认的结果）
      底部：全局收件箱（跨项目的需要你）

主区：当前项目的代理对话（锚定回复模式，见 §2.3）
      你的消息：带处理状态标记（处理中 · 需要你 · 已回复）
      代理的回复：顶部引用它回应的那条消息，正文是整理后的结论，附来源与卡片

右栏：三个标签
      任务：进行中 · 需要你 · 已完成（带验证结论，折叠）；点一条 → 查看任务现场 → 可「直接介入」
      目标：持续性目标（ADR 82）：达成样子、里程碑、下次检查、最近观察、自主档位
      记忆：见 §2.3.1（ADR 81）
```

### 2.2 旧概念去向

| 原型 A | 项目代理模式 |
|---|---|
| 侧栏 Workspace + 任务树 | 侧栏项目列表；任务移到右栏 |
| 主区 = 当前任务 | 主区 = 项目代理对话；进入任务是「介入」 |
| 「新建任务」按钮 | 取消。和代理说话，代理决定开不开任务 |
| 工作台雷达页 | 降级为侧栏角标 + 全局收件箱；独立页进入退场评估 |
| Agent / Plan 模式切换器 | 从代理输入框退场。要不要先批计划，由代理判断后递批准卡 |
| 验收抽屉 / 待验收 | 不再是必经步骤。代理负责验证并汇报；验证通过且低风险的由策略代签。验收抽屉改为按需打开的「验证详情」，复用已有的自动验收报告 |
| 任务内 Goal 面板、Explorer / Verifier | 保留，在任务现场里看 |
| 「任务」称谓 | 保留。代理开出的执行单位就叫任务 |

### 2.3 锚定回复模式（核心交互）

代理对话不是一问一答的流水，而是「每条消息都被接住、被回应」：

```text
你发一条消息 M
  → 代理接住 M（M 上出现处理状态标记）
  → 代理结合上下文判断：直接回答 / 开任务 / 并入已有任务 / 停掉旧任务改开新任务
  → 开任务时：任务锚定在 M 上，带着 M 的原话、代理写的任务说明、截至 M 的对话上下文快照
  → 任务在后台跑，关键信息结构化交回
  → 代理把交回的信息重新整理，发一条「回复 M」的消息：顶部引用 M，正文是结论
```

一条消息的三种样子：

| 元素 | 长什么样 | 数据 |
|---|---|---|
| 你的消息 | 右下角状态标记：`● 处理中 · 用量面板按天分组`、`需要你`、`已完成 · 已验证`、`已回复`、`已并入「…」`、`已被新消息取代` | 消息的处置投影（运行时契约 §2.6） |
| 代理的回复 | 顶部灰色引用条显示被回复消息的前一行，点击跳回原消息；正文；底部「来源：任务 X」芯片；需要时附卡片 | `replyTo`、`sourceSessionIds` |
| 进度 | 不刷消息。任务进度只体现在你那条消息的状态标记和右栏 | `WorkSession` 投影 |

插话：任务跑着的时候你随时可以继续发消息。

- **不引用直接发**：代理结合正在跑的任务自己判断这条新消息和哪件事有关，决定怎么处置（§3.5）。
- **引用某条消息再发**（复用输入框已有的引用能力）：明确指定「我说的是这件事」，代理只在这条消息对应的任务上做处置，不再猜。

代理的每一个处置都写在你那条消息的状态标记上，停掉旧任务时还会给「恢复原任务」的入口，所以它自己拿主意，你随时能看见、能撤回。

### 2.3.1 记忆：代理记得这个项目和你

代理跨天、跨任务记得事实、决定、约定、踩过的坑、有效的做法，以及你的习惯（完整设计见 ADR 81）。

- 你说「记住：发布前一定让我看」→ 代理回一行「记住了」，以后对外发布一律先给你确认。
- 任务做完，验证过的事实（测试命令、踩过的坑）自动记下，回复下挂一个收起的「新记住 2 条」，点开可撤。
- 代理推断出你的习惯（比如几次都只要结论），攒够 3 次才生效，并告诉你一次。
- 代理引用记忆做决定时，回复下挂收起的「参考了 N 条记忆」；你问「为什么这么做」它能指出依据和来源。
- 右栏新增「记忆」标签：项目简报、事实与约定、踩过的坑、做法、你的偏好（跨项目）、最近形成 / 待确认 / 可能过期；每条能改、能撤、能固定，也能「写进 AGENTS.md」（开任务）。
- 记忆只是带来源的事实记录：不会变成系统规则，不能放宽权限或签收，只能让它们更严；文件改了相关记忆会标「可能过期」再复核。

### 2.3.2 项目目标：代理盯着持续性的事

有些事不是一句话做完的：「0.0.18 发版前把已知 bug 修掉，CI 挂了告诉我」「盯着上游 SDK，出新版就评估升级」。代理把这类话立成**项目目标**（ADR 82）：

- 目标锚定在你说的那条消息上，里程碑挂着若干任务；右栏「目标」标签能看到进度、下次检查时间、最近一次观察。
- 代理按时间表或事件（任务失败、base 分支有新提交、相关文件变化）做**只读检查**；CI、issue、依赖发布这类外部状态靠定时探测，不开入站端口。
- 只有结果和上次**不一样**才往上报；报不报给你、怎么报，看主动性档位（§2.3.3）。
- 发现问题后代理能做到哪一步由你定：只汇报 / 提议下一步（默认，点「开始」才开任务）/ 直接动手（你明说「发现就直接修」）。直接动手开出的任务照样过签收与权限。
- 每个目标有每日自动开任务数与探测次数上限；超了就停下告诉你。

### 2.3.3 主动性：值得打扰才开口

代理醒来处理事情，不等于要打扰你（ADR 80 决策 9）：

- **一定会找你**：需要你批准 / 决定、需要你确认结果、要你拍板的失败、目标临近截止的风险。
- **你让它做的事**：做完一定回你；要不要推送通知看档位。
- **它自己发现的事**（目标信号、观察、点子）：和上次一样就不说；有新内容再按重要度与档位决定是推送、进对话、进「今日小结」还是只更新右栏。
- 档位：关 / 少 / 标准 / 多，外加免打扰时段。直接对代理说「少打扰点」「依赖小版本更新别告诉我」就能改，设置页里也能改。

### 2.3.4 模型分工：谁用什么模型，你说了算

（ADR 83）

- 设置里配一次四个档位：强 / 快 / 省 / 视觉，各自指定主模型和备选。
- 每个角色默认跟随一个档位：项目代理用「快」，任务用「强」，只读探查、记忆提取、目标探测、压缩用「省」，视觉复核用「视觉」，独立复核用「强」且优先和执行模型不同源。
- 任何角色都可以改成固定模型，或设为「自动」：代理在你给的模型池里按任务难度挑，并说明理由。
- 对代理说「这个任务用 X」只影响这一次；说「以后复核都用 X」「这个项目只用本地模型」会改设置（设置页可见可撤）。项目的模型范围只能收紧，故障切换也不会越出范围。
- 任务开出时模型就定下，中途不自动换；任务现场和验证详情会标明执行模型、复核模型，以及是否同源。
- 只有一个模型时，所有档位都指向它，和今天的行为一样。

### 2.4 内联卡片

卡片附在代理的回复里，不单独刷屏。

| 卡片 | 什么时候出现 | 主动作 | 真源 |
|---|---|---|---|
| 任务已开出 | 只在代理的回复里需要说明时出现；平时由消息状态标记表达 | 查看任务 | `WorkSession` 投影 |
| 计划待批准 | 代理判断任务需要先批计划 | 批准 / 修改成功标准 / 拒绝 | 任务 GoalPlan |
| 需要你 | 任务请求权限、需要决策或补充信息 | 批准 / 拒绝 / 回答 | main 里同一条待处理请求 |
| 验证结论标记（不是卡片，是回复里的小标记） | 任务结束时 | 点开看验证详情 | `VerificationVerdict` |
| 需要你确认 | 结论没过线、有人工标准、有外部副作用、或你要求过目 | 确认 / 说「不对」 | 签收策略 + 关闭闸门 |
| 合入 | 改了代码且已签收 | 一键合入源头分支（可设为自动） | Git 交回 |
| 任务失败 / 停滞 | 任务失败或长时间无进展 | 代理给出建议；用户可让它重试或取消 | GoalPlan + blockerAudit |

卡片只是同一事实的另一个出口。在代理对话里批准和在任务里批准，解决的是同一条请求。

## 3. 典型动线

### 3.1 纯问答

```text
你：登录模块的 token 过期时间在哪配？
代理：（读文件、搜索）在 xxx.ts 第 42 行，默认 7 天……
```

不开任务，不进待验收。

### 3.2 一件要做的事

```text
你：把设置页的用量面板改成按天分组                        [● 处理中 · 用量面板按天分组]
…（你可以离开；进度在状态标记和右栏）
代理：┃ 回复「把设置页的用量面板改成按天分组」
      要跑一次 pnpm test 验证，需要你允许。
      [卡片] 需要你：运行 pnpm test                     ← 你点允许
…
代理：┃ 回复「把设置页的用量面板改成按天分组」
      改好了，按天分组放在面板顶部。测试、类型检查都过了，界面截图也核对过。
      [已验证 3/3]  来源：任务「用量面板按天分组」   [合入 develop]
你的消息状态：[已完成 · 已验证]
```

没有「待验收」这一步：验证通过、改动只在任务分支里，策略在代理汇报时代签。你只需要决定合不合入（也可以在项目设置里改成自动合入）。

### 3.2.1 追问才展开细节

```text
你：怎么验证的？
代理：┃ 回复「怎么验证的？」
      三条标准：① 用量按本地日期分组——单测 usage-by-day.test.ts 通过；
      ② 跨时区边界——补了 UTC+8 / UTC-5 两个用例；③ 面板渲染——截图与预期一致。
      改了 4 个文件，主要在 UsageStatsPanel.tsx。
你：给我看看截图和测试输出
代理：┃ 回复「给我看看截图和测试输出」
      [截图 usage-panel.png] [测试输出 pnpm test] [diff 4 files] [验证报告]
```

三层：默认一两句结论；问「怎么验证的 / 改了哪些」给细节；要证据才给证据本体。

### 3.2.2 需要你确认的情况

```text
代理：┃ 回复「把 release notes 发到 GitHub Release」
      草稿写好了，但发布是对外操作，需要你确认一下再发。内容覆盖 0.0.18 的 12 个改动。
      [需要你确认：对外发布]  [部分验证 2/3：发布页渲染未验证]
```

需要确认的只有这几类：验证没过线、有人工标准、有外部或破坏性副作用、你说过「给我看看再说」、项目设置了每次都确认。

### 3.3 一句话多件事

```text
你：发 0.0.18 之前把三个已知 bug 修掉，再更新 release notes   [● 处理中 · 4 条任务]
…
代理：┃ 回复「发 0.0.18 之前…」
      bug #1、#3 已修好并验证；#2 卡在复现环境，我补了复现步骤让它继续。
      release notes 等三个 bug 都完成后再写。
      [已验证 ×2]  来源：3 条任务
```

一条消息可以对应多条任务。代理可以在关键节点先回一次，全部结束后再回一次总的；都挂在同一条消息下。

### 3.4 直接介入

你在右栏点开「bug #2」任务，看到它的对话和 Goal 面板，直接发一句「别改 API，改调用方」。代理下次回合能看到你介入过，不会覆盖你的指令。

### 3.5 插话：代理自主处置

任务跑着时你发了新消息 N，代理在五种处置里选一种，并把结果写在 N 的状态标记上：

| 处置 | 什么时候 | 例子 | N 的状态标记 |
|---|---|---|---|
| 直接回答 | N 是提问，不影响任何任务 | 「现在用的是哪个图表库？」 | 已回复 |
| 并入 | N 是对某条在跑任务的补充或纠偏，目标没变 | 「顺便把周视图也加上」 | 已并入「用量面板按天分组」 |
| 取代 | N 改变了某条在跑任务的目标，继续跑是浪费 | 「算了，不按天，改成按模型分组」 | 已停掉「按天分组」，改开「按模型分组」· 恢复原任务 |
| 并行 | N 是另一件独立的事 | 「另外把登录页的文案也改一下」 | 处理中 · 登录页文案 |
| 停止 | N 明确叫停 | 「先别弄了」 | 已停掉「用量面板按天分组」 |

还有一种是「排队」：N 依赖某条在跑任务的结果（「做完之后再把文档也更新」），代理开出新任务但挂上依赖，等前一条完成后才开始。

取代时，新任务继承旧任务的上下文：旧任务的报告、已读过的材料、任务分支（代理判断改动还能用时继承分支，否则从源头重新拉）。旧任务停下但分支保留，「恢复原任务」就是让它接着跑。

你引用了某条消息再插话时，代理只在那条消息对应的任务上选「并入 / 取代 / 停止」，不会误伤别的任务。

## 4. 代理说话的规矩

写进 `project-agent-source` 的角色契约，同时在产品验收里检查：

1. 每条消息都要有处置：回答、开任务、并入、取代、并行、停止、排队，七选一（可组合，例如同时并入一条、并行开一条）。不允许一条消息没有下文。
2. 能直接回答的就直接回答，不为了显得勤快而开任务。
3. 要产生任何副作用，一律开任务；任务锚定在触发它的那条消息上，带上用户原话，不只带代理的转述。
4. 回复必须挂在被回复的消息上，内容基于任务交回的关键信息重新整理，不照抄任务日志。
5. 验证是代理的活：开任务时就定好怎么验证；结果回来觉得不够就追加核验；汇报前自己确认验证充分。
6. 默认只说结论：一两句话说做成了什么、验证了什么、还有什么没验证。用户追问才给细节，要证据才给证据。没过线或有没验证的地方，第一句就要说出来，不能藏在细节里。
7. 自主处置要留痕：并入、取代、停止都写在用户消息的状态标记上；取代必须说一句为什么。
8. 不替用户做判断：权限、范围扩大、不可逆动作、对外操作、产品取舍，都递卡片。等你确认或已签收的任务代理不能停，只能另开。
9. 过程不刷屏：任务进度只体现在消息状态标记和右栏，代理只在需要你、完成、失败或它改变了处置时开口。
10. 主动开口过门槛：自己发现的事，没有新内容不说；有新内容按重要度与主动性档位送达（推送 / 对话 / 今日小结 / 只更新右栏）。必达项永远送达。

## 5. 分期

### P0 文档与契约

- 修订产品对齐文档、改造总纲；新写 ADR 80、运行时文档、本文。
- 验收：评审通过，ADR 80 转 Accepted。

### P1 骨架（feature flag：`projectAgentMode`）

- 每个项目懒创建一条项目代理对话；`project_agent` 模式与白名单投影。
- 调度能力：`spawn_session`、`list_sessions`、`get_session_report`。
- 任务跑现有 Goal Runner；`session_result_ready` / `session_ended` 唤醒代理。
- 锚定回复骨架：任务锚定在触发消息上并带上下文快照；代理回复带 `replyTo` 引用条与来源芯片；用户消息的处理状态标记。
- 验证与签收：运行时算验证结论与签收策略；低风险任务在代理汇报时策略代签；需要确认的附确认卡；回复带结论标记。
- 界面：主区代理对话、右栏任务清单、结论标记、需要你确认卡、合入动作。
- 验收：一句话 → 该消息出现「处理中」→ 任务完成 → 代理发一条引用原消息的一两句结论回复，带「已验证」标记 → 任务自动结束，不需要你签收；构造一个有外部副作用的任务，确认卡正确出现。代理全程无法写文件。

### P2 冒泡与插话

- `session_needs_user`：权限、决策、计划批准卡以「回复原消息」的形式冒泡到代理对话，两处同步。
- 插话处置：回答、并入（`message_session`）、停止（`cancel_session`）；引用某条消息插话时限定处置范围。
- 右栏点进任务可直接介入；`user_intervened` 事件。
- 按需披露：`get_verification_detail` 与证据芯片；代理追加核验 `verify_session`。
- 主动性档位与 SurfacingPolicy、每日小结。
- 验收：任务跑着时插话，每条插话都有可见处置；引用插话只影响对应任务；代理没有任何批准入口；介入后代理不覆盖用户指令；追问「怎么验证的」「给我看证据」能逐层展开。

### P3 并行与取代

- 多任务并发、写仓库任务自动 worktree、主工作区脏时拒绝开出。
- 插话处置补齐：并行、排队（依赖）、取代（继承旧任务上下文与可选分支）+「恢复原任务」。
- 并发上限与唤醒频率上限；代理的只读临时调研 `spawn_subagent`。
- 验收：§3.3、§3.5 场景跑通；取代后恢复原任务能接着跑；三条任务互不污染工作区。

### P4 连续性与主动性

- 代理长对话压缩 + 记忆体系（ADR 81，MM1–MM5；MM1 可在 P2 期间并行开工，与路线图中景 #5 合流）。
- 停滞检测与主动纠偏；项目目标与定时 / 事件驱动推进（ADR 82，OB1–OB3；与 Automation 共用 Scheduler）。
- 手机 / 远程入口对接项目代理（路线图中景 #4 / #4b）。

### P5 迁移与清理

- 旧会话归为项目下的「历史任务」。
- 侧栏任务树、独立工作台页、代理输入框的模式切换器退场；flag 默认开启。
- 验收：老用户升级后每个项目都能看到原有任务，且没有被改写。

## 6. 风险

| 风险 | 缓解 |
|---|---|
| 每句话多一跳，慢且贵 | 代理用快模型；纯问答直接回答；进度不唤醒代理 |
| 代理对话常驻，上下文膨胀 | 压缩必需；roster 每轮重新生成且只注入快照 |
| 代理转述丢细节 | 任务带用户原话；交回的关键信息结构化；回复带来源芯片直达任务现场与验收依据 |
| 代理误判插话，停错任务 | 处置写在消息状态标记上；取代可「恢复原任务」；引用插话限定范围；等确认或已签收的任务代理不能停 |
| 代理报喜不报忧 | 结论标记由运行时渲染，代理文字与标记冲突以标记为准；没过线时不能代签；未验证项必须出现在第一层 |
| 代签后发现有问题 | 说「不对」即开派生任务修正；代签记录保留可追溯；合入默认仍需一键确认 |
| 并行写冲突 | 第二条写仓库任务起强制 worktree |
| 用户不信任「看不见的任务」 | 右栏常驻任务清单；任何任务一键进入现场 |
| 代理变成话痨 | §4 规矩 5；产品验收检查代理自发消息频率 |

---

## 7. 非目标

- 多个常驻专职代理、代理之间的群聊。
- 代理直接做「很小的改动」。
- 代理替用户批权限、批计划或签收结果。
- 新建 Task / Project 存储实体。
- 把工作台雷达做成更重的工单台来弥补可见性。
