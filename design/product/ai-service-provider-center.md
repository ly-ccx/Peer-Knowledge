## 0. 文档目的与决策口径

### 0.1 本文要解决什么

当前 Provider 功能的问题不是“下拉框里的服务商不够多”，而是用户面对的仍然是一组工程配置：Provider、协议、Base URL、API Key、模型 ID 混在同一条路径中。用户无法清楚回答：

1. 我应该接入哪一种服务？
2. 这个服务应该登录、填 Key，还是连接本地运行时？
3. 我是否已经接入成功？
4. 它能用哪些模型、支持哪些 Agent 能力？
5. 登录过期、额度耗尽或协议不兼容时，我应该怎么修？

本文把这块能力重新定义为一个完整的 **AI 服务接入与治理系统**，并给出产品定位、概念模型、信息架构、页面形态、关键流程、状态体系、渠道差异、异常处理、分期与验收标准。

### 0.2 一句话定义

> Peer Agent 的服务商中心，是用户发现、连接、验证和管理 AI 服务的统一入口；它不是 Provider 下拉框，也不是把底层 API 参数原样暴露出来的高级设置页。

### 0.3 核心产品决策

| 事项 | 决策 |
|---|---|
| 用户管理的核心对象 | **服务连接（Service Connection）**，不是 Provider 枚举值 |
| 设置导航名称 | **服务商**；页面动作使用“添加服务”“已连接服务” |
| 添加入口 | 独立的“添加服务”目录页，不在下拉框里罗列全部渠道 |
| 分类方式 | 首先按接入方式分组，再以品牌卡片供用户选择 |
| 多账号/多地址 | 同一服务商允许建立多个独立连接 |
| 模型与服务关系 | 模型归属于服务连接；跨服务模型在独立“模型”页统一管理 |
| 高级字段 | 默认隐藏；只在自定义兼容、云平台或排障时展开 |
| 可用性判断 | 以“凭据 + 端点 + 模型 + 最小能力验证”的结果为准，不以“已保存”代替“可用” |
| 状态表达 | 图标 + 明确文案 + 最近检查时间，不只依靠颜色 |
| 支持承诺 | 明确区分原生适配、验证兼容和自定义兼容，不把“可能能请求”表述为“完整支持” |

### 0.4 非目标

本方案当前不包含：

- 在应用内购买第三方模型额度或代付账单；
- 首期建设 Provider 插件市场；
- 首期自动在不同服务商之间做成本路由或故障切换；
- 把所有底层协议、Header、请求体参数暴露到默认路径；
- 仅通过扩充现有下拉框完成改版；
- 本轮直接修改 `peer_agent` 代码或输出高保真视觉稿。

## 1. 问题定义

### 1.1 当前产品层问题

现有体验把不同层级的概念压在一个设置表单中：

```text
服务品牌       OpenAI / Anthropic / DeepSeek / Gemini …
接入渠道       官方 API / 订阅账号 / 云平台 / 中转 / 本地运行时
鉴权方式       API Key / OAuth / 本机登录 / 云凭据
传输协议       OpenAI Chat / Responses / Anthropic Messages / Gemini …
模型           远端模型 ID / 固定套餐模型 / 本地模型
```

这些概念在工程上都合理，但如果在用户界面中并列，就会产生以下问题：

- 用户必须先理解协议兼容关系，才能开始配置；
- 同一品牌的订阅账号和 API Key 被误认为同一种服务；
- “保存成功”与“真的可用”没有建立可靠对应；
- 连接、模型、额度和故障信息散落，无法形成服务全貌；
- 新增 Provider 时只能继续堆选项，系统复杂度线性转嫁给用户；
- 不同渠道虽然字段不同，交互却被迫使用同一张通用表单。

### 1.2 用户真正要完成的任务

用户不是来配置 Provider 枚举的，而是要完成以下任务：

1. **发现**：找到自己已有账号、API Key、云凭据或本地模型对应的入口；
2. **理解**：在点击前知道接入方式、适用区域、是否需要订阅以及大致能力；
3. **连接**：只填写该服务真正需要的内容；
4. **验证**：确认凭据、网络、模型和基础 Agent 能力可以工作；
5. **选择**：决定启用哪些模型，以及默认使用哪个模型；
6. **维护**：查看账号、额度、模型、最近状态并更新凭据；
7. **修复**：出现问题时看到影响、原因和下一步动作，而不是原始错误码。

### 1.3 根因与修复方向

根因不是 Provider 清单不足，而是缺少一个稳定的产品对象和完整生命周期。

修复方向为：

```text
服务模板
  ↓ 用户选择接入方式
服务连接（单一事实源）
  ├─ 凭据 / 登录会话
  ├─ 接入地址 / 区域 / 项目
  ├─ 可用模型
  ├─ 能力与限制
  ├─ 额度与用量摘要
  └─ 健康状态与诊断结果
```

## 2. 产品目标与成功指标

### 2.1 产品目标

1. 新用户不理解 API 协议，也能独立完成首次服务接入；
2. 常见官方服务走最短路径，自定义兼容服务仍保留足够扩展能力；
3. 用户始终知道一个服务当前是可用、部分可用、需要操作还是不可用；
4. 服务接入、模型启用和聊天模型选择使用同一份事实数据；
5. 新增渠道主要通过服务模板和适配能力扩展，而不是继续增加通用表单分支；
6. 凭据、诊断与导出流程默认保护敏感信息。

### 2.2 核心指标

| 指标 | 定义 | 建议目标 |
|---|---|---:|
| 首次可用时间 | 从点击“添加服务”到至少一个模型可选择 | 常见 API Key 路径中位数 ≤ 2 分钟 |
| 首次接入成功率 | 开始配置后在同一会话完成验证的比例 | ≥ 85%（排除主动取消） |
| 默认路径字段数 | 官方 API Key 路径首屏必填项 | ≤ 2 项 |
| 可诊断率 | 连接失败后能给出明确原因分类和下一步动作 | ≥ 95% 已知错误 |
| 模型可用一致性 | 服务详情、模型页、聊天选择器对可用状态判断一致 | 100% |
| 敏感信息泄露 | 日志、诊断复制和界面中出现完整密钥 | 0 |
| 迁移无损率 | 旧配置升级后无需重新输入凭据即可继续使用 | 100% 可识别配置 |

指标用于评估方向，不要求 P0 一次建立完整数据分析平台。

## 3. 产品概念模型与术语

### 3.1 用户可见对象

#### 服务商（Provider Brand）

用户熟悉的品牌或服务主体，例如 OpenAI、Anthropic、DeepSeek、Google、Azure、本地 Ollama。它用于发现和识别，不直接等同于一份可用配置。

#### 接入方式（Access Method）

同一服务商可有多种接入方式，例如：

- 订阅账号登录；
- 官方 API Key；
- 云平台凭据；
- 第三方中转；
- 本地应用或 CLI 登录；
- 本地 HTTP 运行时。

#### 服务连接（Service Connection）

用户真正管理的对象。它代表“我的某个账号/密钥/地址已经接入 Peer”。同一服务商可以有多个连接，例如：

```text
OpenAI · 个人订阅
OpenAI API · 工作项目
DeepSeek · 国内直连
OpenAI Compatible · 公司网关
Ollama · 本机
```

服务连接拥有独立名称、凭据、端点、模型、状态和使用信息。

#### 模型（Model）

隶属于某个服务连接的可调用能力。即使模型 ID 相同，只要服务连接不同，也视为两个可独立选择和诊断的模型实例。

### 3.2 仅内部使用的对象

以下术语用于协议和运行时，不进入普通用户默认路径：

- Channel
- Wire Protocol
- Adapter
- Legacy Provider Type
- Reasoning Param Style
- Custom Header Schema

只有在高级配置或诊断详情中确有必要时，才使用经过翻译的表达，例如“兼容协议：OpenAI”。

### 3.3 推荐界面文案

| 工程词 | 默认用户文案 |
|---|---|
| Provider | 服务商 / 服务 |
| Provider Config | 服务连接 |
| Channel | 接入方式（默认不展示 Channel） |
| API Base URL | API 地址 |
| API Key | API Key（保留行业通用称呼） |
| Fetch Models | 同步模型 |
| Test Connection | 测试连接 |
| OAuth Session Expired | 登录已过期，请重新登录 |
| Unsupported Wire | 当前接入方式与该模型不兼容 |
| Remove Provider | 移除服务 |

## 4. 服务支持分级

服务目录不能把“存在一个预设地址”和“做足适配”混为一谈。每个接入入口必须标注支持级别。

| 级别 | 用户标签 | 产品承诺 | 典型形态 |
|---|---|---|---|
| L1 | 原生适配 | 独立接入流程、字段说明、模型目录、能力映射、诊断和错误指引均经过验证 | OpenAI、Anthropic 等重点渠道 |
| L2 | 验证兼容 | 使用兼容协议，但默认地址、鉴权、模型同步和核心能力已验证 | 常见国内模型 API、中转平台预设 |
| L3 | 自定义兼容 | 用户自行提供地址和模型；Peer 验证基础通信，不承诺全部高级能力 | OpenAI Compatible、Anthropic Compatible |
| L4 | 实验性 | 功能可能变化，明确显示限制和反馈入口 | 新协议、社区适配 |

### 4.1 “原生适配”最低门槛

一个服务只有满足以下条件，才可标记为“原生适配”：

- 有独立品牌卡片和准确的接入说明；
- 根据接入方式只展示必要字段；
- 能完成凭据或登录态验证；
- 模型列表有明确来源，并处理空列表、固定模型和刷新失败；
- Streaming、Tool Calling、Vision、Reasoning 等关键能力有真实映射；
- 常见错误有面向用户的原因、影响和修复动作；
- 已覆盖密钥失效、额度不足、限流、模型无权、网络失败等测试；
- 服务详情能展示最近状态和支持范围。

仅仅“请求返回 200”不构成原生适配。

## 5. 整体产品形态

### 5.1 设置中心信息架构

P0 在设置中心形成两个稳定入口：

```text
设置
├─ 通用
├─ 外观
├─ 服务商          ← 接入和管理账号、密钥、端点、额度与健康状态
├─ 模型            ← 跨服务管理可用模型和默认模型
├─ 提示词
├─ MCP
├─ 插件
└─ 高级
```

“健康检查”和“用量统计”在 P0 先作为服务详情中的能力，不新增一级导航；当全局诊断和成本治理达到独立使用价值后，再升级为单独页面。

### 5.2 路由结构

```text
/settings/providers                         服务商中心
/settings/providers/add                     添加服务目录
/settings/providers/add/:templateId          连接配置流程
/settings/providers/:connectionId            服务详情 / 概览
/settings/providers/:connectionId/models     该服务的模型
/settings/providers/:connectionId/connection 连接与凭据
/settings/providers/:connectionId/diagnostics 诊断
/settings/models                             全局模型中心
```

这是产品级路由关系，不约束前端必须使用何种路由库。

### 5.3 五个核心界面

1. **服务商中心**：查看所有已连接服务及状态；
2. **添加服务**：从按接入方式组织的目录中发现服务；
3. **连接配置流程**：按所选渠道完成登录或凭据配置；
4. **服务详情**：查看概览、模型、连接和诊断；
5. **模型中心**：跨服务管理启用模型和默认模型。

### 5.4 与主聊天界面的关系

主聊天模型选择器只消费“已启用且可选择”的模型：

- 没有任何服务：显示“连接 AI 服务”，进入添加服务；
- 有服务但没有启用模型：显示“选择可用模型”，进入对应服务模型页；
- 当前模型连接需要操作：保留当前选择但显示状态提示，并提供“立即修复”；
- 用户成功添加首个服务后：返回原发起位置，并自动选中推荐模型；
- 不在聊天模型选择器里新增、编辑或输入 Provider 参数。

## 6. 页面一：服务商中心

### 6.1 页面目标

让用户在一个页面中回答：

- 我已经连接了哪些服务？
- 哪些可用，哪些需要处理？
- 每个服务使用什么方式接入？
- 有多少模型、当前默认是什么？
- 账号或套餐额度是否正常？
- 下一步最应该做什么？

### 6.2 页面结构

```text
┌──────────────────────────────────────────────────────────────────┐
│ 服务商                                            [＋ 添加服务] │
│ 管理通过订阅、API Key、云平台、中转或本地运行时接入的 AI 服务   │
│                                                                  │
│ [全部 5] [需要处理 1]                              [搜索服务]   │
│                                                                  │

│ │ ◉ Codex 账号                         ✓ 可用       [断开]     │ │
│ │   订阅登录 · Pro · 2 个模型                                   │ │

│                                                                  │
```

### 6.3 页头

- H1：`服务商`
- 辅助说明：`管理通过订阅、API Key、云平台、中转或本地运行时接入的 AI 服务`
- 主操作：`＋ 添加服务`
- 当存在异常连接时，在主操作下方或筛选栏展示 `需要处理 N`，而不是全屏告警。

### 6.4 分组规则

已连接服务默认按真实接入方式分组：

1. 授权登录；
2. 官方 API（直连）；
3. 云平台；
4. 第三方与兼容服务；
5. 本地服务。

空分组不展示。组内排序：需要操作优先，其次用户手动排序，再按最近使用时间。

### 6.5 服务卡片信息

每张卡片最多包含三层信息：

**第一层：识别与动作**

- Logo、连接名称；
- 主状态；
- 与状态匹配的首要动作；
- 更多操作菜单。

**第二层：关键摘要**

- 接入方式标签；
- 账号/套餐或区域（可用时）；
- 启用模型数量；
- 默认模型。

**第三层：运营与诊断摘要**

- 额度进度、重置时间；或
- API 地址域名、最近检查时间；或
- 当前异常原因的一句话摘要。

卡片不直接展示完整 API Key、完整 Token、自定义 Header 值和协议内部字段。

### 6.6 卡片操作

| 状态 | 主操作 | 次操作 |
|---|---|---|
| 可用 | 编辑 / 查看 | 测试连接、同步模型、停用、移除 |
| 部分可用 | 查看问题 | 管理模型、测试连接 |
| 需要操作 | 立即修复 | 诊断详情、停用、移除 |
| 不可用 | 重新测试 | 编辑连接、诊断详情、移除 |
| 已停用 | 启用 | 编辑、移除 |

对于授权登录使用“断开账号”；对于 API 或本地连接使用“移除服务”。破坏性动作均进入确认流程。

### 6.7 空状态

```text
还没有连接 AI 服务

连接订阅账号、API Key、云平台或本地模型，
即可在 Peer 中选择模型并开始工作。

[添加第一个服务]

已有自定义地址？ [添加兼容服务]
```

从聊天首屏进入时，文案改为“先连接一个 AI 服务，再把任务交给 Peer”，并在成功后返回聊天。

## 7. 页面二：添加服务目录

### 7.1 页面目标

用户在填写任何字段前，就能理解可选服务、接入方式和差异。目录首先服务“找到正确入口”，而不是追求一次展示最多 Logo。

### 7.2 产品形态

采用设置窗口内的独立详情路由，不使用狭窄下拉框，也不把长目录塞入小弹窗。页面有返回动作，保留设置窗口关闭能力。

```text
┌──────────────────────────────────────────────────────────────────┐
│ ← 返回                                                           │
│                                                                  │
│ 添加服务                                                         │
│ 通过订阅、API Key、第三方中转或本地模型接入新服务                │
│                                                                  │
│ [搜索服务、平台或接入方式____________________]                   │
│ [全部] [授权登录] [官方 API] [云平台] [兼容服务] [本地]          │
│                                                                  │
│ 推荐                                                             │
│ ┌───────────────────────────┐ ┌───────────────────────────────┐ │
│ │ OpenAI                    │ │ Anthropic                     │ │
│ │ 订阅登录或官方 API        │ │ 官方 API                      │ │
│ │ 原生适配                  │ │ 原生适配                      │ │

│ 授权登录                                                         │
│ ┌───────────────────────────┐ ┌───────────────────────────────┐ │
│ │ Codex 账号                │ │ Google 账号                   │ │
│ │ 使用现有订阅，无需 API Key │ │ OAuth 登录                    │ │
│ └───────────────────────────┘ └───────────────────────────────┘ │

│ 官方 API（直连）                                                 │

│ [OpenAI 兼容] [Anthropic 兼容] [Ollama] [本地 CLI]               │
└──────────────────────────────────────────────────────────────────┘
```

### 7.3 分类体系

#### 推荐

根据平台、地区、当前已安装运行时和产品支持级别展示，不根据商业返佣排序。推荐必须可解释，例如“已检测到本机 Ollama”或“原生适配”。

#### 授权登录

适用于订阅账号、OAuth 或本机已登录工具。卡片明确说明“无需 API Key”以及订阅要求。

#### 官方 API（直连）

服务商直接提供的 API。卡片说明认证方式、地区和是否可自动同步模型。

#### 云平台

Azure OpenAI、AWS Bedrock、Google Vertex 等需要项目、区域、部署或云凭据的服务。不能伪装成普通 API Key 表单。

#### 编程套餐与第三方服务

Coding Plan、聚合平台和中转服务。必须标记运营主体、支持区域、模型范围是否固定，以及是否属于第三方。

#### 本地服务

Ollama、LM Studio、本地 CLI 或其他运行时。卡片展示“本机运行”“数据不离开本机”等可验证属性；未安装时显示安装指引而不是配置输入框。

其中「本地 CLI 登录」类渠道（当前唯一实例：Qoder 私有接口 `qoder-local`）依赖本机已安装并登录的 qodercli，请求发往 Qoder 私有端点而非本机运行时；卡片必须展示「需先安装并登录 Qoder CLI」这一前提，连接流程见 8.8，完整说明见 `knowledge/architecture/qoder-private-channel.md`。

#### 自定义兼容

始终放在目录末尾作为专业入口：

- OpenAI 兼容；
- Anthropic 兼容；
- 其他已支持协议的自定义地址。

### 7.4 服务卡片

每张卡片必须回答四件事：

1. 这是什么服务；
2. 如何接入；
3. 适合谁或有什么限制；
4. Peer 对它的支持程度。

推荐信息结构：

```text
[Logo] DeepSeek                         [原生适配]
       DeepSeek 官方 API
       API Key · 中国区 / 国际区可选
```

可选标签包括：`原生适配`、`验证兼容`、`无需 API Key`、`本机`、`中国区`、`国际区`、`Beta`。单卡标签不超过 2 个，更多信息进入详情。

### 7.5 搜索与筛选

- 可按品牌名、别名、服务类型和接入方式搜索；
- 支持中文与英文别名，例如“智谱 / GLM”；
- 搜索结果仍显示所属分类和接入说明；
- 无结果时提供“添加自定义兼容服务”；
- 已连接的模板显示“已连接 N 个”，但仍允许新增另一连接；
- 键盘可遍历卡片，回车进入配置，Esc 返回。

### 7.6 目录内容治理

服务目录是产品资产，不能由前端散落常量随意堆叠。每个服务模板至少包含：

- 稳定 ID、品牌名、Logo、简介和搜索别名；
- 所属类别、地区与支持级别；
- 可选接入方式及其前置条件；
- 默认 API 地址和是否允许编辑；
- 凭据字段及帮助链接；
- 模型来源：自动同步、内置固定或手动添加；
- 已验证能力和已知限制；
- 测试策略、错误指引和敏感字段定义；
- 文档版本与最近验证时间。

## 8. 页面三：连接配置流程

### 8.1 设计原则

连接流程不是一张万能表单，而是由服务模板决定的短流程。原则如下：

1. **先选择服务，再显示字段**：用户不需要先猜协议；
2. **常见路径最短**：官方 API 默认只要求 API Key，预设地址隐藏；
3. **边填边保存草稿，完成验证后才建立可用连接**；
4. **帮助贴近字段**：获取 Key、区域说明和权限要求在对应位置解释；
5. **验证有进度与阶段**：不使用无限转圈；
6. **成功之后明确去向**：选择模型、设为默认或返回发起位置；
7. **高级设置按接入方式出现**：官方服务不展示无意义的 Header 和协议选择。

### 8.2 通用流程骨架

```text
选择服务模板
  → 选择接入方式（模板只有一种时跳过）
  → 填写凭据 / 完成登录 / 检测本地运行时
  → 测试连接
  → 获取或确认模型
  → 选择启用模型
  → 完成
```

页内步骤最多 4 步；实现可将“测试连接”和“选择模型”合并，不为形式强制使用 Stepper。

### 8.3 官方 API Key 路径

```text
┌────────────────────────────────────────────────────────────┐
│ ← 添加服务                                                 │
│                                                            │
│ [Logo] DeepSeek                                            │
│        官方 API · 原生适配                                 │
│                                                            │
│ 连接名称  [DeepSeek________________________]               │
│ API Key   [••••••••••••••••••••••••] [显示]               │
│           [在哪里获取 API Key？]                           │
│                                                            │
│ 高级设置 ▸                                                 │
│                                                            │
│                    [取消] [测试并继续]                     │
└────────────────────────────────────────────────────────────┘
```

行为要求：

- 连接名称预填，可修改；
- 官方 API 地址使用服务模板默认值，不在首屏展示；
- API Key 粘贴后保留在内存中的时间应最短；
- 已保存连接再次编辑时不回显完整 Key，只显示“已配置”及更新动作；
- `测试并继续` 依次验证认证、服务可达和模型目录；
- 模型接口不可用但已知固定模型可请求时，允许进入“部分可用”，并解释影响。

### 8.4 授权登录路径

```text
[Logo] Codex 账号
使用 ChatGPT Plus/Pro 账号授权，无需 API Key

1. 点击 [登录 OpenAI]
2. 在浏览器完成授权
3. 返回 Peer，自动验证账号和套餐

登录中… / 已登录：a***@example.com · Pro

[取消] [完成连接]
```

要求：

- 在跳转浏览器前说明会打开的域名和需要的权限；
- 明确反馈“等待浏览器授权”“正在交换凭据”“正在读取账号信息”；
- 用户取消、端口占用、超时和状态不匹配均有独立错误文案；
- 成功后展示脱敏账号、套餐、可用模型和额度（服务支持时）；
- 一个授权账号默认形成一个服务连接；多账号需明确“添加另一个账号”；
- 断开登录不删除历史会话，但相关模型变为不可用。

### 8.5 云平台路径

云平台必须使用专属字段集合，不套用普通 API Key 页面。

| 平台类型 | 典型必要字段 |
|---|---|
| Azure OpenAI | Endpoint、API Key / Entra、API Version、Deployment |
| AWS Bedrock | Region、Credential Source / Profile、可用模型权限 |
| Google Vertex | Project、Location、Google 登录或服务账号 |

设计要求：

- 首先选择推荐的凭据来源，例如“使用本机 AWS Profile”；
- 自动检测本机已有配置，并显示只读摘要，不复制长期密钥；
- 项目、区域和部署间存在依赖时使用级联选择，不让用户手填组合；
- 测试结果区分“凭据可用但无模型权限”和“网络不可达”；
- 云平台连接名称默认包含项目/区域，便于多连接识别。

### 8.6 第三方中转与 Coding Plan

必须先说明：

- 运营方是谁；
- 凭据由谁签发；
- 数据会经过第三方；
- 模型范围是动态同步还是套餐固定；
- 是否存在区域或套餐限制。

若服务要求固定协议或固定模型，界面不允许用户选择无效组合。对于名称类似官方品牌但实际由第三方运营的入口，卡片和详情中必须持续显示“第三方服务”。

### 8.7 本地运行时路径

```text
[Logo] Ollama

✓ 已检测到本机服务       http://127.0.0.1:11434
  发现 4 个模型

[选择模型并完成]

未检测到时：
未发现 Ollama
[打开安装指南] [重新检测] [手动填写地址]
```

要求：

- 优先自动发现，不先要求用户填写 URL；
- 区分“未安装”“未启动”“端口不可达”“没有模型”；
- 可以展示“数据在本机处理”，但只有端点确认是本机时才能使用此表述；
- 远程局域网地址被视为自定义本地服务，提醒网络和数据边界；
- 模型拉取/删除属于本地运行时管理，若 Peer 暂不支持，不提供假按钮。

### 8.8 本地 / 私有路径（Qoder 私有接口）

本路径覆盖「本地 / 私有」接入分类，当前唯一实例是 `qoder-local`（用户可见名称「Qoder 私有接口」，channelId `qoder`，wire `qoder-private`，默认端点 `https://api2-v2.qoder.sh/model/v1`）。

它和 8.7 的「本地运行时」不同：Ollama / LM Studio 的模型和数据都在本机；而 Qoder 私有接口是**复用本机 Qoder CLI（qodercli）的登录态，请求仍然发往 Qoder 的私有推理端点**。它不是填 API Key 的公开服务，也不在应用内走 OAuth，而是把「这台电脑上已经登录过的 qodercli」当作凭据来源。

前提条件（缺一不可，界面必须在进入流程前展示）：

1. 本机已安装 Qoder CLI（qodercli 可执行文件）——Peer 需要从它提取登录凭据与请求签名能力；
2. 已用 qodercli 完成登录，且登录态未过期——凭据保存在 `~/.qoder/.auth/`，登录态过期会直接报错；
3. （可选）已配置 `QODER_ACCESS_TOKEN` / `QODER_PERSONAL_ACCESS_TOKEN` / `QODER_PAT` 环境变量，可替代本机登录文件提供 token，但不能替代安装 qodercli。

流程骨架：

```text
选择 Qoder 私有接口
→ 前提检查：是否检测到本机 qodercli？是否已有登录态？
  ├─ 未安装 → 提示安装 qodercli（给安装指引，不给输入框）
  ├─ 未登录 / 已过期 → 提示先在终端运行 qodercli 登录
  └─ 满足 → 读取本机登录态与模型目录缓存
→ 展示从本机缓存解密得到的模型列表（缓存不可用时回退最小目录）
→ 测试连接（鉴权有效 + 最小请求）
→ 保存连接
```

要求：

- 入口文案必须写明「依赖本机已安装并登录的 Qoder CLI」，不能只写「Qoder 私有接口」让用户无从理解；
- 不提供密钥输入框；这不是 api_key 渠道；
- 错误必须翻译成人话并给出恢复动作：未装 CLI → 安装 qodercli；未登录/过期 → 打开终端登录 qodercli；模型缓存不可用 → 确认已登录或存在可用缓存；
- 「本地 / 私有」分类不得与真本地运行时混用「数据不离开本机」表述；本链路数据会发往 Qoder 端点。

完整技术说明（凭据链路、模型目录来源、错误码表）见 `knowledge/architecture/qoder-private-channel.md`。

### 8.9 自定义兼容路径

这是唯一默认允许用户选择兼容协议并填写 API 地址的路径：

必填：

- 连接名称；
- 兼容协议；
- API 地址；
- 鉴权方式和凭据；
- 至少一个模型来源（同步或手动模型 ID）。

高级设置：

- 自定义 Header；
- API 路径覆盖；
- 请求超时；
- 能力声明覆盖；
- TLS / 代理相关选项（产品真正支持后才展示）。

保存前必须明确：

> Peer 只验证当前请求链路；自定义兼容服务不保证所有模型能力与官方实现一致。

能力覆盖不能让用户在不知情时“声明即真实”。界面应标注其来源为“手动设置”，并允许随时恢复为自动探测结果。

### 8.10 测试过程与结果

连接测试应呈现阶段，而不是只返回“成功/失败”：

```text
测试连接
✓ 地址可达
✓ 凭据有效
✓ 获取到 12 个模型
✓ 最小文本请求成功
! 工具调用尚未验证

连接可用，部分高级能力将在首次使用时继续验证。
```

失败示例：

```text
无法验证 API Key
服务返回 401，当前 Key 无效或已被撤销。

[更新 API Key] [复制诊断信息]
```

“复制诊断信息”必须自动脱敏。

### 8.11 完成页

```text
✓ DeepSeek 已连接

已发现 3 个模型，并启用推荐的 2 个模型：
✓ DeepSeek Chat（已设为默认）
✓ DeepSeek Reasoner
□ 旧版模型

[完成] [管理模型]
```

若连接流程由聊天空状态发起，主按钮改为 `开始使用`，完成后回到聊天并选中推荐模型。

## 9. 页面四：服务详情

### 9.1 页面目标

服务详情是一个连接的管理主场，而不是重新展示添加表单。用户先看到健康和使用摘要，再按需进入模型、连接和诊断。

```text
┌──────────────────────────────────────────────────────────────┐
│ ← 服务商                                                     │
│ [Logo] DeepSeek                  ✓ 可用   [测试连接] [•••]  │

```

授权登录连接额外展示：

- 脱敏账号；
- 套餐；
- 登录方式；
- 额度窗口、已用比例和重置时间；
- `重新登录` / `断开` 操作。

### 9.4 连接页

按连接类型展示对应字段：

- 连接名称；
- 账号或凭据状态；
- API 地址 / 项目 / 区域 / 本地端点；
- 代理或 Header 等高级设置；
- 支持级别、最近验证版本；
- 保存、测试和撤销未保存修改。

安全要求：

- 密钥不回显，不提供“复制现有密钥”；
- 更新密钥使用独立动作；
- 切换地址或凭据后，状态立即变为“尚未验证”；
- 未通过测试也可以保存草稿，但不能无提示覆盖当前可用配置；
- 可用连接编辑失败时，提供“恢复上次可用配置”。

### 9.5 诊断页

诊断页包含：

1. 当前总体状态和影响；
2. 分阶段检查结果；
3. 最近检查时间与触发来源；
4. 最近若干次状态变化；
5. 修复建议与直接动作；
6. 脱敏诊断信息复制。

示例：

```text
需要操作
登录会话已过期，使用此连接的 2 个模型暂时无法发送消息。

✓ 本地网络正常
✓ 服务地址可达
× 登录会话无效                         [重新登录]
— 模型与工具能力未继续检查

最近状态
今天 09:20  会话过期
昨天 18:10  自动检查成功
```

诊断页不显示完整 Prompt、消息正文、密钥或 Authorization Header。

### 9.6 服务级更多操作

- 重命名；
- 复制连接配置（不复制凭据，用户须重新授权）；
- 停用 / 启用；
- 设为首选服务（P1，可选）；
- 导出脱敏诊断；
- 移除服务。

移除服务时说明影响：将停用哪些模型、哪些会话仍会保留，以及是否同时清除本机凭据。模型当前被默认策略引用时，先要求选择替代模型或明确进入无默认模型状态。

## 10. 页面五：模型中心

### 10.1 页面定位

服务商页回答“我连接了什么”，模型页回答“Peer 实际可以使用什么”。两者不能合并成一张超长设置页。

### 10.2 页面结构

```text
模型
管理 Peer 可选择的模型、能力和默认项

[搜索模型] [全部服务 ▾] [能力 ▾] [状态 ▾]

默认模型
通用任务：Claude Sonnet 4 · Anthropic              [更改]

已启用模型
┌──────────────────────────────────────────────────────────────┐
│ Claude Sonnet 4       Anthropic       ✓ 可用     [默认]     │
│ 推理 · 图像 · 工具 · 200K 上下文                             │
├──────────────────────────────────────────────────────────────┤
│ DeepSeek Reasoner     DeepSeek        ✓ 可用      [•••]     │
│ 推理 · 工具 · 64K 上下文                                     │
└──────────────────────────────────────────────────────────────┘

未启用模型（8） ▾
```

### 10.3 模型信息

每个模型可展示：

- 产品显示名和真实模型 ID；
- 所属服务连接；
- 可用状态；
- 上下文窗口与最大输出；
- 图像、推理、工具调用、Prompt Cache 等能力；
- 价格或套餐属性（数据可靠时）；
- 元数据来源与完整度；
- 模型选项，如 Reasoning Effort 或上下文档位；
- 是否启用、是否为默认。

### 10.4 元数据来源

用户能够区分：

- 服务商同步；
- Peer 内置目录；
- 自动探测；
- 手动设置。

手动值覆盖自动值时显示“已自定义”，并提供“恢复推荐值”。未知能力不显示为“不支持”，而是显示“未确认”或不展示。

### 10.5 模型操作

- 启用 / 停用；
- 设为默认；
- 修改显示名；
- 调整模型选项；
- 复制模型 ID；
- 测试模型；
- 从手动目录移除；
- 回到所属服务。

模型停用不会删除历史会话。正在被默认项引用时，需要先变更默认或明确确认。

### 10.6 默认模型策略

P0 只提供一个全局默认模型，并允许新建会话时手动选择。P1 再考虑：

- 通用任务默认；
- 深度推理默认；
- 轻量/快速默认；
- 图像任务默认；
- 自动回退。

在没有可解释路由和失败治理前，不引入“自动选择最优模型”的黑盒开关。

## 11. 各类服务差异化产品模板

### 11.1 模板矩阵

| 类型 | 主要认证 | 模型来源 | 详情重点 | 必测能力 |
|---|---|---|---|---|
| 订阅账号 | OAuth / 本机登录 | 账号套餐固定或远端同步 | 账号、套餐、额度、过期 | 登录态、模型权限、额度 |
| 官方 API | API Key | 远端同步 / 官方固定 | 地址、Key 状态、模型、限流 | 认证、模型列表、文本、工具 |
| 云平台 | 云凭据 | 项目/区域/部署目录 | 项目、区域、部署、权限 | 凭据链、区域、部署权限 |
| Coding Plan | Token / OAuth | 套餐固定 | 套餐、区域、额度、模型范围 | 凭据、套餐模型、额度 |
| 第三方中转 | API Key | 聚合目录 | 运营方、地址、兼容级别 | 认证、模型、协议差异 |
| 本地运行时 | 无 / 本地令牌 | 本机目录 | 运行状态、地址、硬件提示 | 进程、端口、模型、流式 |
| 自定义兼容 | 用户自定 | 同步 / 手动 | 协议、地址、Header、能力来源 | 最小请求及已声明能力 |

### 11.2 区域差异

同品牌中国区和国际区如果具有不同域名、账号体系、数据处理主体或模型目录，应建成不同服务模板或先选择区域，不能只在名称后加 `(CN)` 而缺少解释。

区域切换属于连接身份变更：

- 不自动沿用无法确认通用的凭据；
- 重新测试模型和能力；
- 页面持续展示当前区域；
- 帮助链接指向对应区域文档。

### 11.3 协议兼容差异

“OpenAI Compatible”不是一个服务商，而是一种专业接入模板；“DeepSeek 使用 Anthropic 兼容协议”也不等于 Anthropic 服务。界面分别表达：

```text
服务：DeepSeek
接入方式：官方 API
兼容协议：Anthropic（仅在高级信息或能力说明中展示）
```

用户识别服务与信任边界，运行时负责协议选择。

## 12. 状态体系与生命周期

### 12.1 为什么要独立状态模型

“已保存”“已连接”“模型可用”和“服务健康”不是同一个状态。产品必须避免用一个绿色圆点掩盖多层事实。

服务连接至少包含四组内部事实：

1. 配置是否完整；
2. 凭据或登录态是否有效；
3. 端点和模型是否可达；
4. 当前模型能力是否满足 Peer 使用要求。

界面再把这些事实归纳为少量用户状态。

### 12.2 用户可见主状态

| 状态 | 含义 | 页面行为 |
|---|---|---|
| 配置中 | 尚未完成必要字段或验证 | 仅在草稿/添加流程中展示 |
| 正在检查 | 正在登录、同步或测试 | 显示当前阶段，可取消 |
| 可用 | 核心连接和至少一个启用模型可用 | 正常使用 |
| 部分可用 | 可完成核心请求，但模型目录或部分能力异常 | 可继续使用，并明确限制 |
| 需要操作 | 凭据过期、额度耗尽、配置变更未验证等可由用户修复 | 提供唯一首要修复动作 |
| 不可用 | 端点持续失败、认证拒绝、没有任何可用模型 | 阻止新请求，保留历史 |
| 已停用 | 用户主动关闭该连接 | 不自动检查、不出现在默认选择器 |

网络短时波动不应立即把状态从“可用”改为“不可用”。后台检查应采用失败阈值和最近成功事实，页面可表达“暂时无法确认”。

### 12.3 生命周期

```text
草稿
  → 待验证
      → 可用
      → 部分可用
      → 需要操作
      → 不可用

可用 / 部分可用 / 需要操作 / 不可用
  ↔ 已停用
  → 已移除
```

关键转换：

- 新建并验证成功：`待验证 → 可用/部分可用`；
- 更新凭据或地址：立即进入 `待验证`，保留上次可用配置直到新配置验证成功或用户确认覆盖；
- 授权过期：`可用 → 需要操作`；
- 额度耗尽且请求被拒：`可用 → 需要操作`；
- 单个模型失效：连接可保持 `部分可用`，该模型单独不可用；
- 用户停用：进入 `已停用`；
- 移除：清理服务凭据和模型绑定，保留历史会话内容。

### 12.4 模型状态

| 模型状态 | 含义 |
|---|---|
| 可用 | 所属连接可用，模型已启用且最近验证成功或可信目录确认 |
| 未验证 | 已发现/手动添加，但尚未完成最小请求 |
| 受限 | 当前账号或区域无权使用，或仅部分能力可用 |
| 不可用 | 模型不存在、已下线或所属连接不可用 |
| 已停用 | 用户选择不在 Peer 中使用 |

### 12.5 状态新鲜度

所有健康信息均携带：

- `lastCheckedAt`；
- 检查来源（用户触发、后台检查、实际请求）；
- 最近成功时间；
- 最近失败分类；
- 结果适用的配置版本。

配置改变后，旧诊断不得继续显示为当前配置“可用”。

## 13. 健康检查与错误恢复

### 13.1 检查层次

| 层次 | 检查内容 | 触发时机 |
|---|---|---|
| L0 配置检查 | 必填字段、地址格式、凭据引用 | 输入时即时 |
| L1 连通性 | DNS、网络、端点响应 | 添加、手动测试、后台检查 |
| L2 认证 | Key/OAuth/云凭据有效 | 添加、凭据更新、实际失败后 |
| L3 目录 | 模型列表、账号权限、套餐范围 | 添加、手动同步、周期刷新 |
| L4 最小推理 | 最小文本流式请求 | 首次连接、模型测试 |
| L5 Agent 能力 | 工具调用、图像、推理参数等 | 原生适配验收或按需验证 |

不应每次打开设置都发起计费推理请求。后台检查优先使用低成本接口；L4/L5 由用户主动触发、首次启用或版本变更时执行。

### 13.2 错误分类与产品文案

| 错误分类 | 用户标题 | 关键说明 | 首要动作 |
|---|---|---|---|
| credential_missing | 缺少登录凭据 | 尚未提供该服务需要的凭据 | 添加凭据 / 登录 |
| credential_invalid | 凭据无效 | Key 被拒绝、撤销或格式错误 | 更新凭据 |
| auth_expired | 登录已过期 | 当前账号需要重新授权 | 重新登录 |
| endpoint_unreachable | 无法连接服务 | 地址、网络、代理或服务状态异常 | 重新测试 / 编辑地址 |
| rate_limited | 请求过于频繁 | 服务暂时限流，并给出可用重试时间 | 稍后重试 |
| quota_exhausted | 额度已用完 | 当前套餐/余额不能继续请求 | 查看服务商 / 更换模型 |
| permission_denied | 没有模型权限 | 凭据有效，但无该模型或项目权限 | 选择其他模型 / 检查权限 |
| model_not_found | 模型不存在 | 模型已下线、改名或地址不匹配 | 同步模型 |
| protocol_mismatch | 服务响应不兼容 | 当前协议与服务实现不匹配 | 更换兼容协议 / 查看诊断 |
| capability_mismatch | 模型不支持此任务 | 例如任务要求工具调用但模型不支持 | 更换模型 |
| local_runtime_stopped | 本地服务未运行 | 已检测安装，但端口没有响应 | 启动服务 / 重新检测 |
| timeout | 服务响应超时 | 网络或服务负载异常 | 重试 / 调整高级设置 |
| unknown | 无法确认问题 | 保留请求 ID 和脱敏上下文 | 复制诊断信息 |

### 13.3 错误展示原则

每个错误至少回答：

1. **发生了什么**；
2. **影响什么**；
3. **用户现在能做什么**。

不把 `401`、`ECONNREFUSED` 或 SDK 堆栈直接作为主文案；可以在折叠的技术详情中展示脱敏错误码和请求 ID。

### 13.4 自动检查策略

建议：

- 应用启动后延迟检查需要维护的授权连接；
- 授权类服务按 Token 过期时间提前刷新或提示；
- 订阅额度按服务允许的频率刷新；
- API Key 服务不做高频主动请求，优先将真实调用结果更新为健康事实；
- 设置页获得焦点时只刷新过期数据；
- 离线状态下暂停检查，并显示“设备离线，状态可能不是最新”；
- 采用退避和抖动，避免多个连接同时打爆服务端。

### 13.5 修复闭环

从聊天发送失败进入修复时：

```text
发送失败
  → 对话内简短说明
  → [立即修复]
  → 打开对应服务详情/修复步骤
  → 完成测试
  → 返回原会话
  → 用户确认后重试（不擅自重复产生费用）
```

如果存在同等能力的可用模型，可提供“改用其他模型”，但不默认静默切换，避免成本、隐私和输出行为在用户不知情时改变。

## 14. 数据、安全与隐私体验

### 14.1 凭据安全

产品层必须保证：

- 长期凭据存入系统安全存储或受保护的凭据层，不作为普通配置明文持久化；
- UI、日志、分析事件和错误上报不记录完整密钥；
- 已有密钥只显示 `已配置` 或不可逆脱敏摘要；
- 复制诊断自动移除 Authorization、Cookie、自定义敏感 Header 和完整账号标识；
- 删除服务时明确是否清除凭据；
- 导入/导出默认不包含凭据，迁移凭据必须是独立受控流程。

### 14.2 第三方数据路径说明

对于中转、云平台和远程本地地址，页面应明确请求将发送到谁。最低展示：

- 服务运营主体；
- 当前 API 主机名；
- 区域或项目；
- 是否为官方直连、第三方或本机；
- 相关隐私政策/文档入口。

不要在没有技术证据时承诺“数据不会用于训练”或“完全本地”。

### 14.3 遥测边界

可以采集：

- 使用了哪类连接模板；
- 流程在哪一步退出；
- 脱敏错误分类；
- 测试阶段耗时；
- 模型数量等聚合数据。

不得采集：

- API Key、Token、Cookie；
- 完整 Base URL 查询参数或自定义 Header 值；
- Prompt、响应正文；
- 未经脱敏的账号、项目和组织标识。

## 15. 视觉与交互规范

### 15.1 整体形态

沿用 Peer Frost 设计语言，但以信息清晰为先：

- 设置窗口 Chrome 层可使用毛玻璃；
- 主内容区使用稳定、可阅读的低噪音表面；
- 服务卡片是分组信息容器，不做悬浮大阴影的营销卡；
- 卡片密度支持纵向扫描，一屏能看到多个连接；
- 添加目录可使用两列卡片，连接详情以单列窄表单为主；
- 页面标题使用产品规范中的中文展示字体，表单正文使用 UI 字体；
- 圆角、阴影和模糊仅使用现有 Token，不创建局部视觉体系。

### 15.2 状态视觉

状态必须使用三种信号组合：

```text
图标 + 文案 + 辅助色
```

例如：`✓ 可用`、`! 需要操作`、`× 不可用`。不允许只用绿色/红色圆点表达。

### 15.3 响应式行为

- 主内容推荐宽度 760–1040px；
- 添加服务卡片在宽度不足时由两列降为一列；
- 服务卡片动作在窄宽度折叠到更多菜单，但修复主动作始终可见；
- 页面内部滚动，标题和关键主操作可保持可见；
- 不使用横向滚动承载基础设置。

### 15.4 动效与反馈

- 卡片 Hover 仅轻微改变表面/边框；
- 测试阶段使用逐项进度，不做长时间无信息动画；
- 保存、复制、同步完成使用短暂 Toast；
- 关键成功页保留静态确认信息，不能只闪 Toast 后消失；
- 遵循 `prefers-reduced-motion` 和透明度降级。

### 15.5 键盘与无障碍

- 所有卡片、Tab、菜单和按钮可键盘访问；
- 焦点顺序与视觉顺序一致；
- 服务 Logo 必须有可读名称；
- 状态不能只靠颜色；
- 密钥显示按钮有明确可访问名称；
- 错误信息与对应字段建立语义关联；
- 长列表支持搜索，不能要求用户仅滚动查找。

## 16. 关键端到端用户流程

### 16.1 首次接入官方 API

```text
聊天空状态点击“连接 AI 服务”
  → 添加服务目录
  → 选择 DeepSeek
  → 粘贴 API Key
  → 测试地址、认证、模型目录、最小请求
  → 勾选推荐模型
  → 设首个推荐模型为默认
  → 返回聊天
```

成功标准：用户不需要填写默认地址、选择协议或输入模型 ID。

### 16.2 添加订阅账号

```text
服务商 → 添加服务 → Codex 账号
  → 阅读订阅要求
  → 浏览器授权
  → 返回 Peer
  → 展示账号、套餐、额度和模型
  → 完成连接
```

成功标准：授权过程的每个阶段有明确反馈，失败不会遗留半连接对象。

### 16.3 添加公司兼容网关

```text
添加服务 → 自定义 → OpenAI 兼容
  → 命名连接
  → 填 API 地址、Key
  → 尝试同步模型
  → 同步失败时允许手动模型 ID
  → 最小请求验证
  → 能力标记为自动探测/未确认
  → 完成
```

成功标准：专业用户有足够控制，但产品不虚构完整兼容性。

### 16.4 登录过期修复

```text
聊天请求前检测登录过期
  → 对话内显示“Codex 登录已过期”
  → 点击重新登录
  → 完成 OAuth
  → 测试原模型
  → 返回会话
  → 用户确认重试
```

成功标准：不要求用户删除并重新添加服务，不丢失模型选择和连接名称。

### 16.5 模型下线

```text
模型请求返回 model_not_found
  → 标记该模型不可用
  → 连接状态为部分可用（若有其他模型）
  → 提示同步模型
  → 展示替代模型
  → 用户确认变更默认项
```

成功标准：不把整个服务误判为失效，不静默替换默认模型。

### 16.6 移除服务

```text
服务详情 → 更多 → 移除服务
  → 显示影响：N 个模型、默认模型、历史会话
  → 如为默认模型，先选择替代或确认清空
  → 二次确认
  → 删除凭据与连接
  → 历史会话保留只读模型标识
```

## 17. 跨界面规则

### 17.1 首次使用引导

与 `first-run-onboarding-guidance.md` 对齐：

- 没有模型时才强引导连接；
- 不弹出独立安装向导巡礼；
- 添加成功后回到用户原任务；
- 若用户取消，聊天输入保持可编辑但发送动作说明缺少服务；
- 不在每次启动时重复弹窗。

### 17.2 聊天模型选择器

模型项至少展示：

```text
Claude Sonnet 4
Anthropic · 工作账号                  ✓ 可用
```

同名模型必须显示连接名称或服务来源。不可用模型留在“最近使用”时应显示原因，不能点击后才失败。

### 17.3 运行时与任务绑定

会话保存稳定的模型实例引用和当时显示信息。连接重命名不破坏历史；连接移除后，历史会话仍可说明曾使用何种模型。任务重放前重新解析当前可用连接，不持久化明文凭据。

### 17.4 CLI/TUI

本文 P0 聚焦 Desktop，但概念应可复用：

- `service list` 对应服务连接；
- `model list` 对应模型实例；
- 缺凭据时进入 Provider setup 子流程；
- Desktop、CLI/TUI 最终共享同一事实源，不维护两套互相漂移的配置。

具体 CLI/TUI 交互由对应产品文档另行定义。

- 凭据引用与普通配置分离；
- 模板默认值、远端发现值和用户覆盖值保留来源；
- 诊断结果绑定配置版本，防止旧结果污染新配置。

## 19. 旧配置迁移方案

### 19.1 迁移原则

- 用户升级后不应重新输入可识别凭据；
- 旧 Provider 配置转换为 Service Connection；
- 原模型绑定转换为 Model Instance 引用；
- 无法明确识别的兼容地址迁入“自定义兼容”，不错误贴官方品牌；
- 迁移不在后台悄悄改变 API 地址、模型 ID或协议；
- 首次打开新版页面时只解释必要变化，不要求逐项确认。

### 19.2 映射口径

```text
旧 provider config
  id             → connection.id（或保留迁移映射）
  display name   → connection.userVisibleName
  provider type  → serviceTemplateId / legacy hint
  channel id     → access method / adapter binding
  auth method    → authReference type
  base URL       → endpoint
  models[]       → model instances
  default model  → global default reference
```

### 19.3 模糊配置处理

- 官方品牌 + 官方默认地址：映射到对应官方模板；
- 官方品牌 + 非官方地址：映射到自定义兼容，并保留原显示名；
- 找不到模板：创建“已迁移的自定义服务”；
- 缺失模型 ID：连接状态设为“需要操作”，引导同步/添加模型；
- 凭据无法迁移：保留连接和模型信息，提示更新凭据；
- 多个旧配置指向同一服务：保持多个连接，不自动合并。

### 19.4 迁移验证

升级测试至少覆盖：

- API Key 官方服务；
- 自定义 Base URL；
- OAuth/本机授权；
- 多 Provider、多模型、默认模型；
- 无凭据配置；
- 已删除/未知渠道；
- 中英文显示名；
- 回滚兼容或明确不可回滚策略。

## 20. 分阶段落地范围

### 20.1 P0：从下拉框升级为完整接入闭环

目标：用户能发现、接入、验证、管理并修复主流服务。

必须包含：

1. Service Template、Service Connection、Model Instance 基础概念；
2. 设置导航拆分为“服务商”和“模型”；
3. 服务商中心及分组服务卡片；
4. 独立添加服务目录、搜索和分类；
5. 三条可用接入路径：官方 API Key、现有授权登录、自定义兼容；
6. 服务详情的概览、模型、连接、诊断；
7. 测试连接阶段化结果和错误分类；
8. 模型同步、手动添加、启用/停用、全局默认；
9. 状态体系：可用、部分可用、需要操作、不可用、停用；
10. 聊天空状态和模型选择器闭环；
11. 旧配置无损迁移；
12. 密钥脱敏、安全存储和诊断脱敏；
13. 至少为当前已有重点服务模板建立真实适配说明和验收用例。

P0 不以“支持多少 Logo”为目标，而以三条主链路完成度为目标。

### 20.2 P1：渠道适配做深

- 云平台专属配置流程；
- 本地运行时自动发现；
- 第三方/Coding Plan 的套餐和额度展示；
- 多账号、多区域和多项目体验完善；
- 模型能力探测、元数据来源和覆盖治理；
- 健康历史和主动过期提醒；
- 配置复制与脱敏诊断导出；
- 更完整的服务模板远端更新机制；
- 首选服务和轻量回退建议。

### 20.3 P2：服务治理系统

- 全局健康检查页；
- 跨服务用量、成本和额度统计；
- 任务类型默认模型；
- 经用户授权的自动回退策略；
- 团队策略、共享模板和企业网关；
- Provider Adapter 扩展机制或受治理的社区模板；
- 服务状态公告和兼容性回归数据。

### 20.4 明确不做的伪进度

以下内容不应被视为阶段完成：

- 只把旧下拉框换成 Logo 网格；
- 添加大量未经验证的预设地址；
- 所有渠道继续复用同一张万能表单；
- 只测试模型列表，不测试最小请求；
- 在界面上写“完整支持”，但没有能力矩阵和回归验证；
- 增加健康状态颜色，却没有错误分类和修复动作。

## 21. P0 验收标准

### 21.1 产品与交互验收

- [ ] 设置中存在独立“服务商”和“模型”入口；
- [ ] 服务商首页首先展示已连接服务，不是服务商下拉框；
- [ ] “添加服务”打开独立目录页，服务按接入方式组织并可搜索；
- [ ] 同一服务商可以添加两个以上独立连接；
- [ ] 官方 API Key 默认路径不要求输入官方 API 地址和协议；
- [ ] 授权登录路径显示登录阶段、账号摘要、过期与重新登录动作；
- [ ] 自定义兼容入口明确支持边界并允许地址、协议和手动模型；
- [ ] 添加成功后能启用模型、设置默认，并返回原发起场景；
- [ ] 服务详情能查看概览、模型、连接和诊断；
- [ ] 聊天模型选择器只展示可选择模型，并能解释不可用状态；
- [ ] 删除服务前明确影响默认模型和历史会话；
- [ ] 所有状态由图标、文案和颜色共同表达。

### 21.2 功能验收

- [ ] 测试连接至少区分配置、网络、认证、模型和最小请求阶段；
- [ ] 401、403、404/model、429、额度、超时、本地服务未启动能映射到明确错误类别；
- [ ] 单模型失效不会错误禁用仍有可用模型的整个连接；
- [ ] 更新连接配置后旧健康状态不会继续被当作当前事实；
- [ ] 模型同步失败时可保留上次有效目录，并显示数据新鲜度；
- [ ] 配置失败不会破坏上次可用连接，或提供明确恢复路径；
- [ ] 连接、模型页和聊天选择器对可用性判断一致；
- [ ] 旧配置迁移后连接、模型和默认项保持可用。

### 21.3 安全验收

- [ ] 界面不回显完整长期凭据；
- [ ] 普通配置文件、日志和分析事件不包含完整凭据；
- [ ] 复制诊断对凭据、Cookie、账号和自定义敏感 Header 脱敏；
- [ ] 移除连接能清理对应凭据引用；
- [ ] 第三方服务明确展示运营方和请求主机；
- [ ] 授权登录具备 state/回调校验及取消、超时处理；
- [ ] 导出与复制默认不包含 Prompt 和响应正文。

### 21.4 可访问性与视觉验收

- [ ] 添加目录、服务卡片、Tab、菜单均可键盘操作；
- [ ] 焦点态清晰，错误与字段具备语义关联；
- [ ] 状态不只通过颜色表达；
- [ ] 两列目录在窄宽度自动降为单列，无横向滚动；
- [ ] 视觉实现使用现有 Frost Token，主内容区保持可读性；
- [ ] 减少动态效果和透明度偏好得到尊重。

### 21.5 Provider 上线验收模板

每新增一个“原生适配”服务，必须完成：

- [ ] 服务卡片、接入说明、地区和运营主体准确；
- [ ] 必填字段和默认地址经过官方文档核验；
- [ ] 凭据错误、权限不足、限流和额度错误有映射；
- [ ] 模型目录来源和刷新策略明确；
- [ ] 文本流式请求通过；
- [ ] Tool Calling、Vision、Reasoning 等声称支持的能力逐项验证；
- [ ] 固定套餐模型、已知限制和下线策略已记录；
- [ ] 脱敏日志与诊断快照通过检查；
- [ ] 记录最近验证时间和适配版本。

## 22. 测试场景矩阵

| 场景 | 预期结果 |
|---|---|
| 新用户无服务 | 空状态引导添加，完成后返回聊天 |
| 官方 API Key 正确 | 自动使用默认地址、发现模型、完成最小请求 |
| API Key 错误 | 显示“凭据无效”，聚焦更新 Key |
| 自定义地址无 `/v1` | 按模板规范处理或给出具体地址提示，不模糊失败 |
| 模型目录接口缺失 | 进入部分可用，允许固定/手动模型，不谎报完整同步 |
| OAuth 用户取消 | 回到登录页，连接不进入可用状态 |
| OAuth 过期 | 页面和聊天均显示重新登录，修复后恢复原模型 |
| 配额耗尽 | 显示套餐/额度问题，不误导更新 API Key |
| 429 | 显示限流与重试时间，不标记凭据失效 |
| 单模型 404 | 仅模型不可用，其他模型继续工作 |
| 本地服务未启动 | 显示启动/重检，不要求重输地址 |
| 本地服务无模型 | 显示安装/拉取模型指引（产品支持时） |
| 同品牌两个连接 | 模型选择器能区分来源，状态互不污染 |
| 编辑可用连接失败 | 保留或可恢复上次可用配置 |
| 删除默认服务 | 要求替代默认或明确清空 |
| 应用离线 | 暂停主动检查，显示状态可能过期 |
| 旧配置迁移 | 无需重输凭据，模型和默认项保持 |
| 深色/浅色与降透明 | 信息层级、状态、焦点均可辨识 |

## 24. 待产品评审决策

以下事项不阻塞本文成为产品基线，但进入研发拆解前需要定案：

| 决策 | 推荐方向 |
|---|---|
| 设置一级导航最终叫“服务商”还是“AI 服务” | 中文 UI 用“服务商”，页内动作使用“服务” |
| P0 首批原生适配清单 | 依据当前真实 Adapter 与用户占比确定，不按竞品 Logo 数量追赶 |

| 添加流程采用整页路由还是大 Sheet | 建议设置内容区整页路由，保证长目录与云平台表单空间 |

| 是否允许保存未验证连接 | 允许草稿，但不可标为可用或进入模型选择器 |
| 服务模板更新来源 | P0 随版本内置；P1 再做签名的远端目录更新 |
| 多个默认模型策略何时加入 | P1 之后，先保证单默认模型稳定和可解释 |

## 26. 最终产品口径

Peer Agent 这块能力最终应呈现为：

```text
服务商中心
  管理所有已经接入的账号、API、云平台、中转与本地服务

添加服务
  让用户按真实接入方式发现服务，并只填写必要内容

服务详情
  解释一个连接是否健康、有哪些模型、如何维护与修复

模型中心
  统一管理 Peer 真正可使用的模型、能力和默认项

诊断系统
  用可验证的事实说明为什么可用、为什么失败以及怎么恢复
```

产品的成功不以 Provider 下拉框里有多少名称衡量，而以以下闭环是否成立衡量：

> 用户能找到正确的服务入口，在不理解底层协议的情况下完成连接；Peer 能验证它是否真的可用；出现问题时能指出影响和修复动作；所有模型和任务始终引用同一份可靠的连接事实。

这才是从“Provider 配置”升级为“AI 服务接入与治理系统”的完整产品形态。
