## 1. 问题与结论

用户的问题是：很多 Goal 已创建、执行并验证，为什么 UI 修改没有自动启动产物、截图检查、发现问题后继续修复，而经常停在内部代码检查？进一步，希望向目标与边界给定后的自主交付推进。

核心判断：应补强的是“对真实产物持续观察并纠错”的闭环，而不是增加更多计划或仅增加截图工具。截图是观察手段，不能独自证明目标实现。这里的“更全自动”指授权范围内减少人工接管，并不声称通过工程模块即可实现 AGI。

本文承接 [Agent 默认模式与自适应规划](agent-mode-default-and-adaptive-planning.md) 和 [Goal 质量评审与自我修复环](goal-quality-review-repair-loop.md)。后者已经提出对照产物的质量评审，状态仍为目标方案；不能把设计文档当作实现证据。其“用户确认验收”边界保持不变，自主质检不代替用户意图确认。

### 对聊天中过强结论的修正

- “没有 visual 类型，所以契约禁止视觉验收”不成立。command/test 可以运行端到端、截图和图像对比测试；枚举类型不是根本障碍。
- “截图存在就验证过了”也不成立。有 PNG、模型真正收到图片、图片足以证明要求，是三个不同层次。
- 不应把“runtime auto-verify”的工具文案理解为所有检查都由 Runner 自动执行；需要区分工具执行、结果回写、证据检查与内容复核。
- 不能由关键词未命中证明整个产品没有预览、记忆或恢复能力；本文不作这种全局否定。
- Codex 仅是用户期望的交互体验参照，本轮未审计其内部实现，不能把对比描述当成已证实架构事实。

## 3. 诊断假设与待验证事项

**问题重写**：UI 任务的执行与完成治理已有基础，但真实运行产物的观察、要求覆盖和失败修复没有被证明能稳定闭环。

**约束**：只在用户授权范围内运行；网页默认使用可见 Browser；Appshot 不绕过用户手势和权限边界；测试实例与承载当前任务的宿主分离；保留既有用户确认验收语义。

**主要假设**：规划容易选择代码侧标准，而产物启动、目标状态准备、观察与新版本证据更新依赖模型临场安排，造成结果验证缺失。证伪方式是抽样真实 UI Goal，检查是否已有这些步骤与有效产物证据，统计遗漏发生在哪一层。

**建议的事实来源**：用户原始要求、当前构建版本、实际观察及其可解析证据；不是任务打勾数或助手总结。

**建议关注链路**：要求 → 运行实例 → 状态准备 → 观察 → 判定 → 修复 → 重验 → 交付。本文不修改链路实现。

**后续验证**：先记录当前基线，再验证网页及桌面测试实例的正例、失败恢复、旧证据失效和权限阻塞。尚未启动 App、执行截图或运行这些场景，不能报告其已通过。

**非目标**：取消权限、静默扩大授权、绕过 Appshot、删除用户确认、无限重试、用“多拍一张图”替代结果判定。

尚需核对：实际宿主是否继续调度 verifier_failed；图片在各提供方与上下文压缩后的可达性；测试实例的版本识别与就绪协议；经验检索是否已有可用集成。代码协议存在不等于产品路径已打通。

## 4. 建议补强的七项能力（未批准方案）

### 4.1 用户结果与验证方法分离

例如“弹窗不被遮挡”是结果，“进入指定状态截图并点击按钮”是验证方法，“typecheck 通过”是实现检查。每个关键要求应映射到观察证据，不能挑选容易通过的测试来重新定义用户目标。

UI 验画面与交互，API 验真实响应和状态变化，文档验内容及必要的渲染；不是所有产物都必须截图。

### 4.2 受控运行与状态准备

知道启动命令、就绪条件、版本身份、进入目标状态的方法、测试数据和资源清理。后台任务 ID 不代表服务就绪。修改后截到旧进程不能算验收。

网页优先复用现有 Browser；桌面应评审受控测试实例或预览能力，区分 Agent 宿主和被测 App，避免测试把承载当前任务的宿主关闭。不要直接把 [Appshots](appshots-window-context-capture.md) 接入聊天工具。

### 4.3 多通道观察与证据时效

组合截图、DOM/可访问性、日志与操作后状态。记录要求、版本、实例、状态和观察时间的关联。变更后使受影响的旧证据失效，而非复用旧截图结案。是否新增 visual kind 应由这一语义需要决定，不是先加枚举再找用处。

### 4.4 有限自动修复

区分可恢复执行失败、需要新假设的方法失败、必须询问的权限或产品决策。每次重试应有新的观察或理由；反复同样失败应换方法或停止。修复后重验受影响要求，不得降低标准求通过。

### 4.5 结果进展与预算

任务数和证据数是活动信号，不是结果进展。建议追踪要求满足、根因排除和阻塞消除，同时限制时间、成本、重复失败与副作用范围。不得把增加最大轮数当作自主能力提升；具体预算政策需另行评审。

### 4.6 验证执行与独立复核

执行者修改产物；受治理的验证工具产生真实证据；复核者对照原始要求判断是否充分。复用现有 Verifier 的只读定位，不让其自己编造证据。是否每次启动独立模型应按风险与成本决定。

### 4.7 范围授权与可验证经验

用户一次授权工作区内编辑、测试、本地预览及测试实例操作；发布、生产数据、破坏性操作仍需既有许可。权限由执行层控制，模型不能自行扩张。

经验应记录有效启动方式、状态复现方法、失败原因和验证过的修复，并附适用版本与过期条件。不能把聊天总结直接当作长期事实；先核对已有记忆能力再决定增量设计。

## 5. 分期路线与交叉验收建议

优先做一条端到端 UI 交付闭环，而不是直接建设通用桌面控制平台：

1. 抽样 UI Goal，记录真实任务成功率、人工介入、假完成、恢复率和成本基线。
2. 网页产物打通启动 → 就绪 → 目标状态 → 截图和交互 → 修复重验 → 清理。
3. 桌面受控测试实例复用结果与证据语义，单独评审能力、权限和宿主隔离。
4. 将可证明有效的结果验证方式扩展到 API、文档和数据任务。

以下是后续实现必须覆盖的“宿主 × 结果状态”矩阵，**均为待执行场景，不是本轮测试通过记录**：

| 产物宿主 | 正常交付 | 发现真实缺陷 | 版本或证据过期 | 缺权限/环境 |
| --- | --- | --- | --- | --- |
| 网页 | WEB-PASS：启动目标版本、观察交互、交付与清理 | WEB-REPAIR：故意遮挡，发现并修复后重验 | WEB-STALE：修改后旧截图不能关闭要求 | WEB-BLOCK：明确阻塞，不伪造通过 |
| 桌面测试实例 | DESKTOP-PASS：隔离实例并验证目标 UI | DESKTOP-REPAIR：布局或交互缺陷闭环 | DESKTOP-STALE：旧实例截图不能证明新构建 | DESKTOP-BLOCK：保留权限门和运行宿主 |

只有图片不够，还应覆盖“看起来正常但操作无效”。所有场景应保留可追溯证据；测试运行不能破坏日常用户数据。用户确认验收与自主质检分别记录，不混成一种完成状态。

## 6. 本轮交付与未做事项

本轮克隆知识库、整理固定版本代码事实、修正过强推断，并接入已有设计导航。没有修改 Agent 代码，没有启动产品或验证视觉闭环，没有批准新工具/权限，没有提交或推送文档。

衡量下一步收益应看真实任务成功率、每任务人工介入次数、假完成率、自主恢复率、时间与成本，而不是 Goal 数、工具调用数或 Evidence 数。
