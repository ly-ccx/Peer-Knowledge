## 0. 一句话

Peer 是一个人把真实工作交给本机代理、只在关键节点回来拍板的**任务委托系统**。代理自己把结果验证到位再交还；人听结论，想看细节时再追问。

面向用户：

> 把工作交给 Peer，只在真正需要你的时候回来。

工作关系：

> 用户负责目标、边界与关键判断。Peer 负责持续推进，并在交还之前证明结果。

聊天是表达意图和处理例外的介质，不是主语，也不是状态真源。

---

## 1. 为什么存在

今天绝大多数 Agent 仍建立在「人推动每一轮」上：

```text
用户提出要求
  → AI 回答或执行一段
  → 用户阅读、判断遗漏
  → 用户发送下一条
  → 再等
```

即使用户已经能在本地跑工具，他仍然自己当项目经理：拆下一步、记做到哪、判断是不是真做完、中断后再解释一遍。这不是委托，是「借助 AI 亲自完成工作」。

Peer 要换的是工作关系，不是再做一个更会跑工具的对话框。基本单位不是一条消息、一次工具调用或一张待办卡，而是：

> **一段可托付、可推进、可交接、可证明的真实工作。**

多数桌面 Agent 优化关系连续性，或「能在本地跑工具」。Peer 额外优化三件事：

1. **责任与注意力**：现在该处理什么。
2. **完成的可证明性**：Done 是闸门，不是模型口头完成。
3. **本地权力的可审计性**：Manifest → Projection → PermissionGrant → Evidence。

---

## 2. 为谁

第一人群：

> 同时维护多个本地 Workspace、每天推进代码、文档、研究和发布工作的独立开发者、技术负责人和技术型创作者。

他们通常同时压着许多长短任务，工作跨终端、代码仓、浏览器、文档和桌面应用，已经在用 Agent，要少盯守，怕误操作，重视本机数据与权限，经常跨天恢复。

「技术负责人」卖的是**个人工作方式**，不是企业采购主体。

首批要打透的委托：问题定位与修复、跨文件工程改造、发布与运维准备、研究与文档交付。它们都有明确结果、较长步骤、需要工具、可定义成功标准。

暂不优先：

- 只要轻量问答的人
- 追求无人监管高风险自动交易的人
- 纯 RPA
- 以企业复杂审批和团队排期为第一诉求的大型组织

顺序是：个人本机闭环稳定 → 小团队可信协作 → 更远的企业网络。团队治理不是当前主叙事。

---

## 3. 是什么，不是什么

Peer 占据的是模型与用户之间的**长期工作关系层**。模型、工具、执行器可以换；任务状态、Workspace 现场、已验证的证据、权限决策和被证明有效的做法，留在 Peer。

品类可以说 Delegation OS、任务闭环、本地工作委托系统。三个名字是同一件事的不同镜头，对齐时不要各说各的品类。

**不是：**

- 又一个 ChatGPT 桌面壳
- 单纯的 Coding Agent
- 多模型聚合器或 MCP 商店
- 多 Agent 角色扮演
- AI 版 Jira / Linear / Notion
- 通用 RPA
- 以无限白板为中心的协作工具
- 企业 Agent OS、工单台、Cloud CEO 的客户端、1688 宙斯员工版

**已作废、禁止再当论据的旧身份：**

- 客户端 Harness，不是本地大脑
- 工作台是唯一主入口 / 默认落地页
- 会话是一等公民
- 模型说做完就算完
- 任务是家，用户自己开任务、切任务（ADR 80 起由项目代理开任务）

桌面持有能力、授权与 Evidence。模型是认知角色，不是部署位置，更不是产品主语。Electron main 仍然只是组合层，不把认知塞进 UI。

每个项目有一个**项目代理**，它是用户在这个项目里的对话对象，只读 + 调度，不产生副作用（ADR 80）。它是委托层级里的一层，不是虚拟团队，也不是角色扮演。任务里的子 Agent、圆桌、Automation 仍只是一条任务里的执行手段。小团队转交、共同验收是第三阶段。

## 4. 责任怎么分

```text
模型负责认知。
本地负责能力。
界面负责表达。
契约负责边界。
证据负责治理。
```

| 层 | 持有什么 | 禁止什么 |
|---|---|---|
| 模型 | 为什么做、做什么、选哪个能力 | 假装拥有用户的机器；口头完成替代 Evidence |
| 本机 Runtime | 发现、授权、执行、Evidence | 旁路能力链；把权限真值只放在界面 |
| 界面 | 任务现场、行动权、对照与确认 | 自己执行高权限能力；用聊天气泡冒充工具结果 |
| 契约 | 跨层对象与不变量 | 临时 payload 代替协议对象 |
| Evidence | 一步或结果是否发生过 | 摘要、助手文本、生成了文件 ≠ 证明 |

三拍贯穿产品与运行时：

> 目标带着边界被签收 → 能力在授权下执行 → 完成用证据关闭。

Desktop、TUI、CLI 是同一套本机 Runtime 的三个入口，不另起执行真相。

## 5. 价值点

用户要感到五个变化：

| 价值 | 含义 | 若做不到 |
|---|---|---|
| **少解释** | Workspace 已经知道现场、规则和验证方式 | 每次都从零交代 |
| **少盯守** | 能自行推进的步骤持续推进 | 人仍是每一轮的项目经理 |
| **少切换** | 雷达告诉你现在谁该动 | 靠翻会话找未完成的事 |
| **少怀疑** | 结果有可对照的 Evidence | 「声称完成」无法关掉 |
| **越用越顺** | 被证明有效的做法可以留下 | 每次委托都从零开始 |

守住的竞争力：

1. Task Flow，而不是 Tool Chat
2. Evidence 一等公民（摘要 ≠ 证明）
3. 一条受治理能力链
4. 完全开源 + 可嵌入的同一套 runtime 真值

最重要的产品变量不是「待办 / 进行中 / 完成」，而是**下一步行动权在谁手里**：

```text
轮到用户：待批准 / 待确认 / 待补充 / 结果需要你确认（例外） / 失败要你处理
轮到 Peer：规划中 / 执行中 / 验证中 / 自动修复中
一轮交还：这一包结果已签收（策略代签并告诉了你，或你确认过）
家还在：可以继续住，也可以暂时没有行动权
```

产品原则：

1. 目标优先于消息
2. 交接优先于状态名
3. 证据优先于声明
4. 例外打扰优先于过程打扰
5. 真实对象优先于展示副本
6. 恢复优先于并行炫技
7. 治理优先于自治口号
8. 复利优先于功能数量

加任何能力只问一句：

> 它是在强化「任务被正确签收、正确授权、正确证明」，还是只是多干一件事？

## 6. 对象：五层不要互相冒充

```text
Workspace     执行世界：仓库、源头分支、权限、能力家园
项目代理      这个世界里你唯一默认的对话对象：理解、拆解、开任务、汇报、递卡片
任务          项目代理替你开出的一件事：目标、证据、验收的单位
Goal Thread   这件事上的多轮目标
机器人列表    跨项目的行动权：每个机器人行上的需要你 / 进行中，下一步谁该动（ADR 84）
```

| 层 | 对象 | 回答什么 | 真源 |
|---|---|---|---|
| 世界 | Workspace | 工作发生在哪里 | 工作区配置、文件系统、源头分支 |
| 对话 | 项目代理 | 你在这个项目里跟谁说话 | 每个 Workspace 一条 `role: project_agent` 的 Conversation；它的文本不是任何状态的真源 |
| 心智 | 任务 / 目标线 | 托付的是哪一件事 | 无独立 Task 表；Conversation + GoalPlan 族投影 |
| 流转 | 行动权 | 下一步谁该动 | `TaskOverviewItem.actionRight`，main 聚合 |
| 执行 | GoalPlan / Runner | 怎么推进、证没证完 | GoalPlan store，不是聊天文本 |
| 载体 | Conversation | 双方说了什么 | 会话库；主键仍是 `conversationId`；任务会话以 `parentConversationId` 挂在项目代理下 |
| 事实 | Evidence | 声明是否发生过 | Evidence，不是摘要 |
| 认知 | 记忆 | 这个项目和这个人有什么值得记住的 | `~/.peer-agent/memory/`，带来源与证据引用；不是指令，不是证据 |
| 交付物 | Artifact | 人可以打开什么 | 文件、截图、报告；生成了文件 ≠ 完成 |

口诀：

> **存 Conversation，做 GoalPlan，连 Goal Thread，看行动权，说任务。**

产品面只说**任务**。代码里的 `conversation` 可以继续当实现名。

不要把这些升成首页或产品主语：Conversation、RunTrace、GoalPlan 编号、任务内的子 Agent、Canvas、圆桌。项目代理是例外：它就是产品面的对话对象。Canvas 若存在，只投影真实对象，不成为第二份真相。

Goal、Plan、Run 不要压成一张进度卡：Goal 是结果与标准，Plan 是当前路径，Run 是一次实际执行。一次 Run 失败不等于 Goal 失败。进度由叶子步骤和 Evidence 聚合，不能让模型手填百分比。

Artifact 与 Evidence 必须分开：前者是可消费结果，后者是证明。一份截图可以同时是两者，语义不同。

## 7. 委托链路：完成只是其中一个节点

整张产品不是围绕「完成」长出来的。主语是委托。人经过的是一条链路，完成是链上交还结果的那一站。

```text
0  Workspace（世界，不是步骤）
1  委托成不成立（项目代理判断）
2  项目代理开出任务
3  目标和边界
4  意图签收（准你做）
5  授权下执行（内环，对用户多数时候可离开）
6  需要你（例外交接）
7  机器做完 + 代理验证（执行结束，结论由运行时算）
8  签收结果              ← 「完成」只在这里（默认策略代签，例外由人签）
9  可选：货交回源头
10 家还在（派生下一轮，或暂时安静）
```

### 0. Workspace

切换 Workspace 是换执行世界，不是筛选列表。真正执行前必须明确落在哪个世界。源头主开发分支属于这个世界，不是任务自己发明的。

### 1. 委托成不成立

说一句话不等于任务。你对项目代理说的话，轻量问答由它用只读能力直接回答，不开任务、不进雷达。有副作用、要交付、要验收，代理才开任务，执行前必须有持久化 GoalPlan。无 Plan 的写文件等副作用必须被拒绝；项目代理自己在投影层就拿不到写能力。

这是入口闸门，比完成更靠前。滑回聊天窗，通常是这一站没守住。

### 2. 项目代理开出任务

主区默认是当前项目的代理对话。代理开出任务时说清目标和成功标准；需要先批计划的，递批准卡给你。任务有自己的现场（对话、Goal 面板、分支），你随时可以点进去直接介入。机器人列表不是工作台页面：行上的角标告诉你哪个机器人现在要你出门一趟（ADR 84）。

同一时刻一条任务上只应有一份在执行的 GoalPlan。并行发生在项目代理开出的多条任务之间，或一轮内部的步骤，不发生在同一条任务里并排两份根目标。

### 3. 目标和边界

这一轮要什么结果、不能越过什么、怎样算成功。Goal 原则上稳；Plan 可以随事实改，改必须可解释。没有这一站，执行是在猜。

### 4. 意图签收

计划批准、接受目标、将写仓库则拉任务子分支。这是「准你做」，不是「做完了」。与节点 8 是两次不同的签：这里需要批准的计划由人签，节点 8 默认由策略代签。

### 5. 授权下执行

复杂度全在这里：等人、暂停、失败重试、自检纠偏、计划修订、质量自检、Verifier 打回。对用户多数时候是「Peer 正在推进」。产品不要把这个内环摊成首页或验收页。

### 6. 需要你

权限、缺信息、冲突、失败、交回停住。这是例外交接，不是完成的预告。雷达上这是最响的一格。滑回工单台，通常是把这里做成了排队系统。

### 7. 机器做完 + 代理验证

叶子终态 + 自动标准过线 + Evidence。验证是代理的活：开任务时定好怎么验证，结果回来觉得不够就追加核验；运行时按改动类型有不可下调的验证下限。验证结论（通过 / 部分 / 未通过）由运行时从验证闸门、独立复核、视觉验证、质量自检汇总，代理不能改写。

### 8. 签收结果

对照**本轮**标准 × **本轮**证据，过关闭闸门才写 `resultAcceptance`。这是「完成」这个词该占用的节点。它不批准计划，不继续推进，只承认这一包结果。

签收默认由**验证策略代签**：结论通过、副作用只在工作区内、没有人工标准、没有外部或破坏性操作、用户没要求过目时，代理向用户汇报结论的同时写下 `acceptedBy: 'policy'`。其余情况由**人签**：代理递「需要你确认」，说明原因。

代签不是「模型说做完就算完」：代签的前提是运行时算出的结论和关闭闸门，代理的文字关不掉任何东西。用户随时可以说「不对」，代理开派生任务修正，代签记录保留。

汇报遵循分层披露：默认一两句结论（做成了什么、验证了什么、还有什么没验证）；用户追问才给细节；要证据才给证据本体。没过线或没验证的地方必须出现在第一句，不能藏在细节里。

### 9. 货交回源头（可选）

只有绑过任务分支、改过代码才有。签字不等于已经进当时的 Workspace `baseBranch`。交回失败回到节点 6，不要假装委托已经结束。

### 10. 家还在

签完可以继续住：追问、派生下一轮、或暂时没有行动权。雷达安静 ≠ 房子拆了。主题跳开才是新任务。

Memory / Skill 沉淀是复利，不是主路径上的必经站。未验证的经验不能自动变成系统指令或共享认知。

项目代理的记忆（ADR 81）是带来源的事实记录，只作为事实上下文进入模型：已验证的事实和用户亲口说的自动生效，推断出来的要攒够证据才生效；记忆只能让权限与签收更严，不能更松；用户随时能看、能改、能撤。

## 8. 壳怎么表达这条链路

壳层由**原型 A：任务壳 + 工作台雷达**迁移到**项目代理壳**（ADR 80，改造总纲阶段 F）。迁移完成前原型 A 仍是线上壳。不做工单台。

| 人看见 | 服务哪些节点 | 禁止做成 |
|---|---|---|
| 项目代理对话（主区） | 1–4、6、7 的汇报、10 | 会话管理器、过程刷屏 |
| 机器人档案（任务 / 目标 / 记忆，按需滑出） | 5、7 | 工单列表；常驻占位 |
| 任务现场（介入时） | 2–5、10 | 第二套调度入口 |
| 代理对话里的「需要你」卡 | 6 | 代理替你批 |
| 代理回复里的验证结论标记 | 7→8 | 代理口头宣布完成；标记由运行时渲染 |
| 代理对话里的「需要你确认」卡 | 8（人签的例外） | 把每个结果都做成待验收 |
| 验证详情（原验收抽屉，按需打开） | 8（本轮） | 整条线的传记；必经步骤 |
| 机器人列表（行角标 · 「需要你」筛选 · 搜索） | 6、8 的例外，跨项目 | 独立的工作台页 |
| Git 合入 / 打开现场 | 4 与 9 | 「完成」的全部含义 |

必须遵守：

1. 每个项目一个项目代理，它是默认对话对象；它只读 + 调度，不产生副作用。
2. 任务由项目代理开出；用户可以点进任务直接介入。
3. 从卡片或角标点进去，必须落到原来的任务 + Plan 或验证详情，禁止另起无历史工单页。
4. 轻量问答由代理直接回答，不开任务，不进签收。
5. 代理的文本不是状态真源，也不是证据；卡片与结论标记绑定 main 里的同一份事实。
6. 验证归代理，签收按策略，细节按需：用户默认听结论，追问才展开。

规划深度 L0–L3 是运行时深度。项目代理输入框不再暴露 Agent / Plan 切换器；要不要先批计划由代理判断后递批准卡。L0 不进签收。

## 9. 「完成」在图上的尺寸

完成不是产品高潮。它是节点 7 之后、节点 10 之前的一次交还：

- 证明这一轮结果成立（代理验证，运行时出结论）
- 默认由策略代签；例外时把行动权交给人确认
- 若有代码，打开交回闸门（合入默认仍需一键确认）

它管不了：这话算不算任务、计划批没批、执行里卡没卡、下一轮还做不做、房子还住不住。那些是别的节点。

四层谓词不要揉成一个「归档」：

| 谓词 | 谁说了算 | 成立之后 |
|---|---|---|
| 机器完成 | 叶子 + 自动标准 + Evidence | `status = completed` |
| 签收结果 | 关闭闸门 + 验证结论 + 签收策略（策略代签或用户确认） | `resultAcceptance`（`acceptedBy: 'policy' \| 'user'`） |
| 货交进源头 | git handoff | `deliveryHandoff.delivered`，可失败 |
| 家暂时安静 | 无未处理行动权 | 雷达上可以消失；家还可以再住 |

空成功标准集合在实现上可以过闸门，不代表产品鼓励「没写标准也能完成」。复杂路径里这是快路，不是完成定义本身。

## 10. 对齐时可以用 / 不可以用的句子

**可以用：**

- 把工作交给 Peer，只在真正需要你的时候回来。
- 你只和项目代理说话；任务由它开出，证据由任务交回。
- 下一步谁该动。
- 目标带着边界被签收；能力在授权下执行；完成用证据关闭。
- 本地执行，信任显式。

**不可以用：**

- 我们是企业 Agent OS / 多人协作平台 / 工单台。
- 我们是多 Agent 角色扮演。
- 会话是一等公民。
- 模型说做完就算完。
- 工作台是唯一入口。
- 客户端只是云端大脑的薄壳。
