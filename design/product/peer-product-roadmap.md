## 1. 当前方向

Peer 是一个人把真实工作交给本机代理、只在关键节点回来拍板的任务委托系统。代理持续推进，交还前证明结果；验证归代理，签收按既有策略，细节按需披露。

体验主线是**安静委托，清晰交接**。六个判断标准：意图有回执、行动有归属、执行有边界、结果有依据、中断可恢复、注意力归用户。具体视觉、交互与动效规则以最新三份体验规范为准，不在路线图里另立配色、组件或状态机。

Desktop/TUI/CLI/远程表达同一套本机 Runtime 事实；模型负责认知，本机负责能力与 Evidence。手机/远程是入口扩展，不能提高授权范围或另起执行真相。

## 4. 近景：0.1.0 可信闭环收敛

| 顺序 | 重点 | 工作包 | 退出依据 |
|---|---|---|---|
| 0 | 对齐版本、规范与在途依赖 | E00/E01 | 唯一基线、准确 PR head、ADR 状态、已交付与缺口清单 |
| 1 | 保住输入，正确接收与恢复 | E02/E03 | 机器人草稿隔离；未确认发送、引用和附件可恢复；IME、回执、重试不混淆 |
| 2 | 决策与结果如实交接 | E04 | 列表/对话/详情同一行动权；批准、执行、验证、签收、Git交回分别表达 |
| 3 | 用户掌握阅读与焦点 | E05/E06 | 不抢滚动、最上层键盘、可见焦点、抽屉和拖动能退出 |
| 4 | 共享组件与日用入口 | E07–E12，按修复路径推进 | Frost状态统一；新建/模型/附件/记忆/目标/多入口/恢复可理解可控 |
| 5 | 最终组合候选与 GA | E13 | 全部 open PR 正常合并后全门禁、产品逐图审查、真实范围与七天日用/用户决策 |

这张表不等于“全部内容必须塞进下一版”。影响输入安全、决定真实性或核心可达性的确认缺陷优先修；不阻塞闭环的全面换皮、可选动效转 0.1.x。按依赖与结果推进，不按未经估算的日历承诺。

日常只做实现与内容/diff 审阅；测试、build/type/architecture/IPC、截图/交互回归留到版本/RC 发布，用户明确要求时才提前执行。必要的契约测试可以编写，但不得把自动运行变成每天的交接门槛。

## 6. 中景：个人闭环稳定后的增量

以下是顺序和条件，不是 0.1.0 的额外冻结范围。

| 顺序 | 增量 | 前提与边界 |
|---|---|---|
| M1 | 完成非阻塞体验收敛、结果时间线、证据/来源可定位性 | 先保住核心交接；过程按需，Canvas只是已有对象投影 |
| M2 | 更稳定的模型分工、质量自闭环与任务内部多角色 | 复用已有路由/Verifier/Runner；不改成虚拟团队，不重做协调内核 |
| M3 | 记忆与 Skill/playbook 的证据复利 | 区分已有记忆与新增候选/审核链；可查可撤，记忆不放宽权限、不默认上云 |
| M4 | Browser L1加固、L2 Profile/attach/下载与对话框治理、ACP外部接入 | 逐项核对已有代码与缺口；能力/权限/Evidence先行；L2不抢默认入口 |
| M5 | 可嵌入 Runtime 与本机数据面的按需加厚 | 公共Runtime包、现有存储已经存在；新拓扑先按ADR评审，不做全库迁移。会话读取窗口与列表预览以 [ADR 121](../../knowledge/decisions/121-desktop-session-windowing-contract.md) 为准，在现有 JSONL 与 Bot SQLite 上收敛接口 |
| M6 | 内网 Gateway、身份/设备配对、远程体验与手机伴随面扩展 | 先完成部署/身份/委派的契约；现有0.1.0远程看/发消息继续保留；远程批准/附件另行A 级设计 |

M4 与 M5/M6 是不同扩展线，不能为了遥控演示绕过稳定的本机闭环。新型 webhook/邮件/日历触发、跨目标依赖、模板等按实际需求单独评审，不借最新设计规范一并扩范围。

## 7. 远景与明确后置

个人闭环稳定后再考虑小团队转交/共同验收、共享 Skill 审查、企业身份与策略、云增强长时工作。模型和执行节点可以变化，但本机能力授权、任务身份与 Evidence 不能被云端聊天替代。

更晚的探索包括 L3 系统 UI Computer Use、多设备接力、多人实时 Canvas、Skill市场、有预算的 swarm 与多 Peer 网络。它们不成为当期主页或营销主语，不作为 0.1.0 发版的隐含前提。

继续守住：零账号本机默认；不默认同步工作区/密钥/Evidence；Gateway 不成为执行真源；知识仓不迁入业务数据库；不做旁路能力、无限白板中心、企业工单台、代理群聊角色扮演或静默高风险自治。

## 8. 更新规则

- 实现、集成、发布、验收分别记录；任何一项变化都更新首页当前事实，不只在页尾叠补记。
- 新事实带代码 SHA、PR/候选身份和覆盖范围；旧失败保留，不能直接沿用或抹去。
- 对应工作包被修复或明确后置时，同步本文、改造计划和交付状态；不要求每个像素修复改整个路线图。
- 改产品身份先北极星，改运行时边界先 ADR，改体验先对应规范，改批次顺序在本文与改造计划说明原因。
- 发版前重新盘点开放 PR，最终组合检查完成才推标签。Git commit 后同轮 push；用户工作区与运行实例保持完整。
