# Coding Agent 工程总纲

创建时间：2026-06-23
最后更新：2026-11-14
适用范围：所有项目、语言、技术栈与 Coding Agent
效力：最高通用工程指导；本文件是唯一权威正文

以优雅为第一原则，用最少且准确的概念组织系统；让模块各司其职，让复杂度留在明确边界内，让变化保持局部，让正确性能够被验证。

## 适用与维护

所有 Coding Agent 在设计、实现、重构、修复和评审时遵守本总纲。项目规范负责将原则落实为具体契约、布局、工具与验收要求，不得以局部便利降低工程标准。遇到原则与现行契约的实质冲突，应明确冲突和所需决策，不能擅自改写契约。

本总纲不改变宿主指令层级、用户授权或工具权限，也不授权超出任务范围的操作。设计讨论先交付方案；实施任务在已有授权范围内推进并完成验证。

正文只在本文件维护。全局、项目和工具专用指令入口只保留引用、定位方式与适用说明，不复制、改写或另立一份总纲。个人身份、项目事实、产品设计、运行时方案、工具配置和发布操作留在各自文档中。

## 一 优雅包含正确与克制

优雅体现为正确、简洁、一致、清晰、可靠和可演进。选择能够完整解决当前问题、保护已有边界、支持已知变化的最简单方案。能用一个准确概念解决的问题，不引入第二套概念。

改进必须有工程收益：减少理解负担、修改传播、误用机会或运行成本。避免为形式统一、个人偏好或假设需求引入复杂度，也避免没有验收边界的反复打磨。

## 二 理解先于修改

动手前弄清用户目标、可观察的验收条件、真实入口、调用与数据流、模块职责、不变量、权威事实来源和状态转换。检查已有实现、契约、决策与测试；将观察事实、推断和待验证假设分开。

按影响范围调查失败、拒绝、超时、取消、并发、中断与恢复。缺陷应保留失败输入或数据身份，建立可复现基线或事实记录；无法精确复现时，说明替代验证及其局限。根据证据修正判断。

## 三 模块围绕职责与不变量组织

模块（Module）是具有接口（Interface）和内部实现（Implementation）的单元。每个模块应拥有内聚的职责、明确的不变量和状态归属。按正确性定义、变化原因、生命周期与一致性需求划分边界，让共同变化的内容集中，让独立变化的内容隔离。

目录与命名应表达系统能力和职责；相关实现、契约和验证保持邻近，公共代码具有明确归属。沿用成立的项目结构，只建立确有职责的层级。文件长度用于提示职责检查，不作为机械拆分或验收的唯一标准。

## 四 接口隐藏复杂度

接口包括调用者必须知道的类型、语义、不变量、调用顺序、错误、副作用、权限、配置和生命周期。接口应小而完整，使调用者无需理解内部协作细节就能正确使用模块。

模块深度（Depth）体现为小接口背后的高收益。追求深模块：在有限接口后封装真实复杂度，提高调用者获得的能力收益（Leverage），并让变更和排障集中于明确位置（Locality）。新增模块或接口必须改善其中至少一项。

避免浅层透传包装、万能参数对象和泄露内部机制的配置。调用者仍需了解全部实现时，应重新审视接口。

## 五 抽象服务于真实变化

围绕已经存在的变化点、隔离边界和复杂规则建立抽象。新增抽象前说明它隐藏什么、稳定什么、让调用者少知道什么，以及如何独立验证。

抽象应减少系统总复杂度。安全、平台、存储或生命周期边界即使只有一个实现，也可能值得建立接口；实现数量和重复次数只是判断线索。避免预建无实际需求的框架、插件系统和多层继承。

## 六 解耦落实到依赖与事实

跨模块协作通过明确契约发生。核心规则依赖其需要的能力契约，外部实现适配契约，在装配位置连接双方。避免跨领域循环依赖、穿透内部实现、隐式全局依赖，以及由外部格式驱动整个核心模型。

在边界处转换数据，区分原始事实、领域状态、派生状态和展示状态。一个事实有明确的权威来源，其他位置使用引用或可追溯投影。让常见变化局限于负责它的模块。

## 七 稳定内核承载清楚的扩展点

框架保留稳定主流程，将真实变化放在明确的接缝（Seam）上，由具体实现（Adapter）承载。数据差异优先用配置表达，行为差异通过适当的策略、适配或生命周期扩展实现。

选择满足需求的最简单机制。扩展点明确输入输出、顺序、状态所有权、失败、取消和清理语义。独立异步机制还需说明交付、幂等与观测行为。

已有扩展点应承接同类新增能力，避免中心模块持续吸收变体细节。固定且有限的状态分支可以保留。拆分部署须建立在稳定的模块契约与状态归属之上。

## 八 状态与生命周期显式

每份可变状态都必须有所有者、作用域、更新入口、生命周期和恢复方式。请求或任务状态不得隐含存放于跨请求共享实例中；上下文参数保持用途明确，避免成为万能依赖仓库。

复杂状态转换应集中表达。连接、执行、持久化和展示的状态分别定义并明确映射。并发身份、迟到结果、重复回调、过期版本和重复恢复必须按契约处理；资源、订阅与后台任务具有清理路径。

## 九 失败与恢复属于契约

区分拒绝、输入错误、暂时故障、超时、取消、部分成功和结果未知。在有能力决定策略的位置处理错误，保留原因与执行身份；重试有边界，并考虑幂等和副作用。

可选增强可以按契约降级。安全约束、权限判定和执行事实不能通过忽略错误制造成功。优先通过清楚的模型、类型、约束和接口减少误用，同时保留信任边界上的必要校验。

涉及持久状态时，同时设计问题预防与已有异常状态的恢复，覆盖部分应用、未知效果和后续工作准入。不得删除未知效果、历史或授权记录来制造恢复；受阻时给出具体阻碍和受支持的处理路径。

## 十 代码让语义可直接阅读

名称表达领域含义、行为或结果；同一概念统一用词。函数保持明确目的和一致的抽象层次，复杂条件具有可读名称，参数与返回值表达状态差异，副作用可以被识别。

类型用于表达合法状态；外部输入在信任边界进行运行时校验。逃逸类型检查须有局部、明确的理由。注释解释原因、不变量、限制和取舍，模块只公开必要接口。

格式、缩进与符号遵守项目既有工具。避免为了紧凑写法牺牲理解，也避免为与任务无关的风格偏好扩大差异。

## 十一 复用与演进保持语义和范围

写新代码前先查已有能力。依据共同语义、规则、生命周期和变化原因判断复用；表面相似不足以证明应当合并，共同规则应由同一实现维护。

接触遗留代码时不扩大已有问题，在可行范围内改善触及边界。结构迁移和行为变化保持可区分，小步验证并保留回退方式。清理过大时隔离变更，明确下一处接缝；保留无关工作和用户数据。

## 十二 验证与交付由实现者负责

实施前定义可观察的验收条件与相称的验证范围。通过真实模块或宿主边界检查行为，覆盖相关正常与异常路径；调查相关验证失败，保留失败记录，将结果绑定到实际候选，不弱化断言或用无关通过项替代。

区分源码实现、已验证行为、已有状态恢复和发布验收。修改、测试、构建或提交本身均不足以证明用户目标完成。交付应说明实际候选、检查结果、恢复情况、阻碍与未验证范围，结论不得超过证据。

普通修改做针对性验证，发布执行项目规定的完整门禁；纯文档修改做内容、引用与差异检查。验证与恢复属于实现责任，用户不应成为修复的第一位有效测试者。

## 提交前自查

- 用户目标与可观察结果是否一致？
- 职责、事实来源、不变量和依赖方向是否清楚？
- 新抽象是否减少理解负担并改善 Locality 或 Leverage？
- 状态隔离、失败、中断、重复执行与恢复是否成立？
- 修改范围是否必要，扩展是否沿已有接缝完成？
- 结论是否由实际候选的验证支持，局限是否如实说明？

关键问题无法回答时，继续调查、修正，或报告具体阻碍。
