## 本轮结论

记录器还没有修到合格。`eb1de652`、`d166929f` 和用户明确追加一个功能槽的 `63bd98bd` 均在第一根记录业务查询后超过 2ms，分别为 2.587551、2.336985、2.387123ms。全部保留 passed=false/CLI exit1，不相减为因果改善，不补实例，不进入现场。三个不同新进程各只有一个根，不能把进程状态、冷调用与实现差异混成某个补丁的 CPU 效果。

## 源码事实与三个小对照

初版每次生成完整 Error 栈字符串再查重。第一修正版改为先取得结构化位置链、确认整链相同后才复用展示；同时把漏计的 span 入队尾段计入 self。Node 的固定 16 块、每块 120 次对照并未支持“结构化天然更快”：两组各 960 次，字符串 CPU 20.260ms、结构化 23.618ms。它只有 30 帧普通递归栈，不能代表真实 Electron/Inspector 中的冷元数据工作。

第二项诊断只改变测量协议，固定 16 块、每块 240 次，保留所有块和用户/内核 CPU。6 次快照组每遍 CPU 0.0238875ms，4 次组 0.0214325ms，2 次业务快照加 self wall 上界组 0.0210625ms。按 12 遍计算，收益约 0.034ms，远不足以解释超额；不能归因成时钟主因。最终候选只采用可精确核对的 4 快照边界复用，保留每遍用户/内核 CPU，没有采用 wall 组替换 self 口径。单元检查确认相邻 span 恰好 4 次快照、入队仍在计费段内。

第三项比较 Error 结构化路径和现有 `util.getCallSites(96,{sourceMap:false})`。960 次的 CPU 分别为 22.144/18.368ms，25 层递归 JS 调用全部保留，但 Error 共 30 帧、内建接口共 28 帧，运行时尾帧不同。只说明该同步 JS 入口可用，不能称 native/异步栈完全等价，也不能由这个普通 Node 暖对照推断真实 Electron 首根过门。

使用的接口和限制依据 [Node24.15.0 util 文档](https://nodejs.org/download/release/v24.15.0/docs/api/util.html#utilgetcallsitesframecount-options)与 [V8 stack API](https://v8.dev/docs/stack-trace-api)。当前记录同步 JS 位置链，实际映射的异步 parent 仍由 ALS 记录；未映射异步与 native 尾部不补造。它没有触碰 heap getter、强制 GC、新 native 库或 VM 设置。

三个小对照各用一个固定 Node 进程、零生产读取；CPU 79.823/118.002/76.327ms。它们属于工具诊断，不是新的 F0、现场或产品根因资格。全部负结果和限制保留，不能只引用较快的一组。

## 当前候选保留了什么、删掉了什么

代码候选 `63bd98bd8ae04b34d9112d1b4f92a5fa0cd53a24` 每次仍采集完整当前同步位置向量；functionName、scriptId、行列和每次核对的 scriptName 都保留。脚本字典只去除重复资源名，整条向量确认相同才引用已有 stack ID，不复用 first-kind 栈。96 帧、32KiB 和字典/未确认/输出帽不变，另按展示文本的保守字节上界拒绝超长栈。

主线程不再创建/保存展示文本，`fr1-stack-display.mjs` 在外部从耐久事实还原；当前 plan/index RLE run 使用直接引用，顺序和计数保持；输出 JSON 只进行一次 UTF-8 编码，用同一 buffer 算字节数和原 SHA。没有删除调用链、降低 frame 数或跳过慢根来减成本。

封存的 `d166929f` 数据可直接证明表示转换无损：7 个栈、14 个 script ID 均可还原为逐字相同的原展示文本；root 加 12 遍共 13 次采集的签名序列化字节从 77437 降为 10637，减少 86.2637%。唯一栈事实从 35019B 降为 4625B，另有脚本表 1257B。这些是字节工作量，不能换算成 CPU 毫秒；当前真实失败已经否定“这些字节减少足以让首根过门”的充分原因说法。

## 仍缺什么以及为什么停在这里

当前能证实冗余表示与测量操作，不能给剩余 CPU 超额指定唯一函数、冷 JIT/GC 或 Inspector 状态。实际宿主里还缺 callsite 原生采集、位置归档/编码、计时时钟、源 stamp 和输出编码/散列的独立分段证据；普通 Node 暖微基准不能代替这些冷现场段。下一次工具诊断应先把这些阶段的 wall 上界与既有 CPU 边界并排记录，保持原计费和真实失败，不再先猜补丁、再开完整功能槽；任何分段 wall 也不能冒称精确 CPU。

本轮追加授权已经用尽，没有新的执行额度，不继续开实例，也不借零查询装配绕过“通过后才进入现场”的条件。当前开发版原进程保持，现场 fast→slow、剩余30–40ms机制和原3.95秒证据缺口均未新增证据；RI-00未闭合、不重构。代码实现、原件完整、单位检查和恢复均不算产品根因进展。
