## 1. 比较对象与方法

产品代码仍为 `b05b7afbf26b43444635f77710397c3a658d6a0f`。诊断工具在独立工作树演进，逐次保存工具文件哈希；Electron 41.7.1 / Node 24.15.0 的隔离子进程读取真实生产 Module。用户的运行实例没有由代理重启或替换。

“190ms”是漏掉 Desktop 核验依赖的旧裸宿主；“约430ms”是补全 Store 和核验后的只读源宿主；“约500ms”是安装现场。它们不是三个修复版本。此前不同窗口还混合了数据代次、读取节奏、探针及进程状态，不能直接将均值差当成某一项开销。

本轮先建立同一物理 Evidence 索引的 main-A → fresh-child → main-B 对照，再用冻结的三类 Store 和一致 SQLite 备份做因素实验。线程用户/系统 CPU 用 `process.threadCpuUsage`；进程 CPU、GC 重叠和内存分别记录。嵌套的 Evidence inclusive CPU 不与根 CPU 重复相加；并发线程 CPU 可以大于墙钟余量，不能当成串行停顿相加。

## 2. 同源夹测确认差额存在

G 组九次完整 Supervisor 读取的会话投影摘要相同；同一索引均为69266条，物理版本和内容摘要不变。各次23个会话、3859次 getPlan、12遍 Evidence 归一化。主宿主约485–527ms，隔离宿主两次暖读约446/453ms；子进程首次约2秒的冷读单列，不混入暖比较。

Evidence 段用户 CPU：主宿主约331–350ms，子进程两次暖值约292/298ms。GC 重叠时长相近；少量无 GC 重叠的单遍读点，主宿主约26–27ms，子进程约22–23ms。这确认差额包含 CPU 成本，不能全部写成异步等待，也不能仅按暂停式 GC 时长补齐。

H/I 组在同一进程内比较生产 reader、原缓存的直接归一化、新解析等值记录的直接归一化。原始记录与完整归一化输出摘要均一致，生产缓存引用没有被替换。第一轮出现 GC 相位与读取顺序相关的偏差，不能用“旧数组较慢”归因；后续平衡所有六种顺序，并以4096条一块交替比较，未证明原缓存记录本身是形成原因。J 组复制相同函数体及部分纯辅助函数，也没有稳定消除主宿主差额，不能据此补写 JIT 原因。

L 组仅检查具名缓存的统计元数据。主宿主 `jsonReadCache` 1408项、源文件字节合计192738209；同源隔离宿主1387项、192558419。另一个 JSONL 缓存在主宿主为1464行/785849字节，隔离宿主未加载。源文件字节数不是留存堆大小；单点 used heap 还包含尚未回收的临时对象。这里没有支持“主宿主多缓存了大量计划”的证据，亦不能用 WeakMap 没有 size 推断其条目数为零。

N 组将索引内容散列移到控制器，避免68MB散列 buffer 进入被测堆；相同 probe 在每宿主连续读取8次，间隔150ms，原生校准放在读取之后。24个投影摘要一致。主宿主首点约498/510ms，随后约446–470ms；隔离暖点约410–419ms。密集主宿主 Evidence 用户 CPU 约301–314ms，隔离约269–277ms。密集节奏能减少首点停顿，却仍有约30–40ms归一化 CPU 上下文差额；不能把它全部归到空闲 GC。

O/Q 组读取具名函数编译状态、数组保护状态及立即分配代际样本。只使用经[相同 V8 版本源码](https://raw.githubusercontent.com/v8/v8/14.6.202.34/src/runtime/runtime-test.cc)核对的读取型 intrinsic；同步临时开启 parser gate，退出前恢复并用新源文本与 flags 身份校验。没有调用优化、反优化、强制 GC 或 allocation-site 修改 intrinsic。隔离 canary 先通过，再在实际宿主夹测，所有恢复校验通过。

两边 reader 均为 baseline；`normalizeEvidenceIndexRecord`、retain 和主要辅助函数均已 TurboFan；数组 species/iterator/no-elements 等保护状态均为 true。raw 数组都为 packed、非 dictionary，256个分层样本的 raw/输出均为 fast properties；raw 及新归一化 record 的立即 young 样本都为0，artifactRefs数组均为165/165在young。没有支持“主宿主已热编译、子进程未热编译”或该抽样下“只有主宿主 record 直接分到 old”的证据。相同 tier 标签也不证明机器码、全部反馈或整个堆状态一致。

P 组500µs CPU 栈覆盖相同的 main-A → child → main-B 完整读图，具名25ms标记将两套时钟对齐到0.123–0.386ms的区间。热点仍在 `readEvidenceIndex` 的 map/filter、逐条 normalizer、optional string、retain 与 `parseInteractiveArtifactRef`。但 profiler 下隔离暖归一化 CPU 上升到约300–321ms，而无 profiler 的N组约269–277ms，且 regexp 栈分布发生差异。因此P组只定位代码段，不代替无 profiler 基线，亦不以采样 self time 拼出一个假精确的30ms原因。

R 组补了查询后的固定整数运算对照。结果 checksum 一致，但主宿主控制出现41/43ms尖点，预热尾部也不够稳定；所有原值保留，不用这套控制给主线程频率或整体 JS 速度下结论。SHA 与整数控制都不能单独替代真实对象分配读图。

## 3. 因素实验与负例

冻结索引为69199条、68627752字节，三类 Store 和协调备份在每次实验前后绑定内容身份。测量入口覆盖直接生产归一化流水线、生产 Evidence reader、GoalPlanStore 和完整 SessionSupervisor。记录过渡读点、暖读、每点 CPU、GC、语义摘要和恢复阶段。

筛选条件预先固定为：每12遍归一化的线程用户 CPU 增加至少15%且至少40ms，输入/输出/代码身份不变；命中后要求新进程处理/对照复验，并在完整生产只读 seam 检查。原始失败和未命中结果保留。

未命中的短时隔离因素包括：字典形状/冻结对象、函数作用域检查、完整宿主装配先后、生产预览索引先行、128MiB额外堆、保留归一化输出、轻量观察器、CPU profiler、已安装/工作区 Module 布局、写入端字段顺序、共享字符串强制转换类型、真实索引记录的纯合并重放，以及对废弃输出的改写后恢复。这些结果只排除所测试的负载，不概括为所有寿命状态均已排除。

有两个明确的机制阳性对照：在子进程临时改写后恢复 Array species，12遍 CPU 从约310ms升到约573ms；临时加入后删除数组原型元素，约升到710ms。输入/输出摘要一致，恢复描述符后仍慢。但没有找到产品中的对应触发路径，且增幅与现场不符，故不采用它们解释现场。

## 5. 线程与 GC：已观测到的相互作用

旁路 Python 只读 libproc 进程和线程计数，不向 Peer 加载原生代码，不改变优先级、功耗或运行参数。rusage 时间为 Mach absolute ticks，已用本机 timebase 和独立 CPU 负载核对；不能把原始 ticks 当纳秒。线程 CPU 与 Node 的同步计量相符。进程指令/周期包含并发 GC 等后台线程，不能直接解释为主线程频率。

T1–T3 的额外线程 CPU 从每次约56–69ms升到238–251ms，主要集中在另外三条线程；GC 事件也增多。相同64MiB原生 SHA 对照的指令/周期接近，主宿主 CPU 时间约28ms、子进程约25ms，说明相同工作不保证相同 CPU 时间；这并不单独确定调度或频率原因。

隔离 GC 原因日志进一步显示：空闲中 memory reducer 发起回收，部分读点前新生代空间从64MiB收缩到0.25MiB；旧生代分配阈值降到约300–380MB。随后的全量读取包含 `finalize incremental marking via stack guard`、`GC in old space requested`，并启动并发标记任务。GC JSON 日志保存分配阈值、暂停、后台 marking 等原值，不只看 PerformanceObserver 的暂停时长。

M组在实际进程补采120秒自然读取，不启 CPU profiler、FS/JSON 包装或旧 timer 接管。8个完整目标查询为488–514ms；每次 getPlan3859/命中3859，Evidence12遍/831192行，Evidence 用户 CPU 约324–332ms。每根其他线程 CPU 约244–279ms；根开始 used heap 约361–449MiB，新生代空间交替出现0.25/1MiB与64MiB，并在读取中扩展。资源采集错误为0，所有 owned wrapper 恢复，GC observer停止，Inspector关闭。这个窗口没有新增多秒事件，不能把0.5秒读点称为补到了新的多秒峰值。

关闭隔离子进程的 memory reducer 后，主动收缩消失，但大部分慢化和后台 CPU 仍在。再固定旧生代增长规则，可减少分配阈值变化和并发回收的额外 CPU，却没有改善绝对查询延迟；部分密集基线反而更慢。二者是机制控制，均不是产品修复方案。带 GC trace 的数值仅用于解释运行状态，不作为无探针性能验收。

另一个隔离控制在相同8次初始全索引读取后，分别丢弃或强引用8份输出（共553592条归一化记录）。首轮保留组密集约427ms、空闲点约481/500/480ms，Evidence 用户 CPU 中位291→335→298ms；丢弃组293→318→294ms。该图是合成 live set，没有证明实际宿主恰好留着8份结果。其后按预先固定的40ms且15%门做三个新进程处理与三个对照，所有点保留；逐组结果与是否通过见机器回执，不能用单个500ms点宣布稳定复现或现场所有权已闭合。

三组保留处理最终只有R2通过该门：R1为288.670→322.233ms，R2为296.040→340.819ms，R3为298.712→320.768ms；三个丢弃对照的增量为31.866、31.133、16.723ms。因此“多留8份输出解释整个差额”没有通过稳定性复验，不能选择R2或某个500ms点作为结论。

延后开启 Inspector → 同一具名 read-port 闭包发现 → 关闭 Inspector 的独立源宿主对照，没有复现持续的密集慢化；四阶段归一化 CPU 大体约261–281ms，个别点另列。它只排除所测激活顺序，不恢复旧进程已经遗失的 VM 状态。

## 6. 新取得的部分触发条件：初始读取顺序

上述“丢弃8份”对照本身比直接完整读图的密集基线慢，提示初始读取历史是独立变量。新增严格顺序对照：I组先独立读取索引8次，再完整读取会话1次；S组先完整读取会话1次，再独立读取索引8次。总调用数相同、结果均丢弃、无额外保留图、默认VM参数；随后都用同一完整生产Supervisor seam做固定预热与7个密集计量点。

首轮冻结输入 pilot 的I/S归一化差约17ms，未通过预先设定的20ms CPU且20ms完整读取门；不降低原门。三个新进程配对的冻结副本为CPU差21.092/28.062/18.264ms、完整读取差21.316/35.097/25.662ms，第三对CPU未通过。

再用与N组相同的现场物理索引、计划、对话与只读协调源做三对新进程复验（顺序I1/S1/S2/I2/I3/S3）。六进程内外的索引内容身份、查询投影摘要均一致；每个进程零读取失败/源写拒绝，所有owned方法恢复，代码哈希不变。该组全部通过原20ms CPU/墙钟门：

| 同源新进程对 | I组归一化 CPU | S组归一化 CPU | CPU差 | 完整读取差 |
|---|---:|---:|---:|---:|
| 1 | 296.504ms | 270.039ms | 26.465ms | 26.948ms |
| 2 | 300.360ms | 275.791ms | 24.569ms | 27.032ms |
| 3 | 299.115ms | 277.113ms | 22.002ms | 28.947ms |

这是可重复的**部分形成条件**：在相同生产Module、相同输入与相同总调用数下，交换初始读取顺序可使后续密集归一化持续多约22–26ms。它解释了此前实验口径中的一个隐藏变量，但还没有证明实际进程经历了I组顺序，更不表示其余差额或旧Path形成已被解释。

两组查询后的编译tier、保护状态和立即代际抽样仍相同。编译/反优化/预分配日志保留了具体事件，不能从都有wrong-map或allocation-site变化便宣称是唯一原因。release Electron的DebugPrint仅提供brief引用，没有详细map布局，未把缺失信息当一致。另在**独立冻结fixture**所有计量结束后取堆快照，只输出64个分层样本的self size/类型摘要；原始/归一化对象、属性backing及相关字符串大小逐位置摘要相同。快照会GC，未对实际应用取快照，快照后状态不冒充计量时状态；也不从self size推断全部map/机器码一致。

上述快照约束依据[V8同版本的GenerateSnapshot回收路径](https://raw.githubusercontent.com/v8/v8/14.6.202.34/src/profiler/heap-snapshot-generator.cc)与[Node24.15.0的writeHeapSnapshot文档](https://raw.githubusercontent.com/nodejs/node/v24.15.0/doc/api/v8.md)：同步快照及版本相关schema只用于计量后隔离样本分析。

为了补实际形成链，启动读取观察器已准备并验证：在新Electron入口前挂接，按数据类别计数，首个索引前计划文件读分别为0与1662；两fixture都为2851次计划文件读/1次索引文件读，零读取失败/源写拒绝。该观察只证明FS读取与raw缓存准入顺序，不把1次文件读写成1次归一化，更不声称8次合成调用就是现场实际次数。用户已明确授权安全退出后的一次临时采样启动；尚须确认旧实例退出再启动，不由代理结束现用任务。

本轮收尾时原实例仍在运行，授权启动尚未发生；有界等待器已退出，无后台启动watcher遗留。用户的一次启动授权保留，待安全退出后继续取证；不是再次请求确认，也不把等待状态写成实际启动结果。

## 7. 当前边界与剩余门

自然查询的主/后台 CPU 与堆状态已补到；隔离15秒节奏可重复增加归一化 CPU，但完整增幅复验没有全部通过；初始读取顺序可在同源新进程重复形成约22–26ms CPU增量，而实际进程的形成顺序尚未取得。当前不能把不同窗口的节奏差、顺序差直接相加，宣布30–40ms密集上下文差或全部430/500ms已闭合；也不能归结为单一GC、缓存老化、编译tier或分配代际。

原3.949秒的原事件继续保留证据缺口；旧进程 Path/getPlan 额外成本的形成过程仍未证明，不能从新进程样本补造。既有自然5.417秒 CPU 闭合窗口与新进程自然6.57秒记录仍分别成立。它们与受控八请求及本轮因素实验不是同一个事件。

已确定的架构问题没有改变：轻量展示与调度读取进入完整执行/核验图；单次可反复读取全部计划、12遍归一化全部 Evidence；同步工作留在 main，多个入口及微任务可串行放大。新增 GC/堆状态证据说明固定一次暖耗时不足以描述这张读图，不授权用 VM 开关代替有界查询、缓存归属与执行位置治理。
