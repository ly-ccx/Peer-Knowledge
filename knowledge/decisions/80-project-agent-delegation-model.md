# 80. 项目代理委托模型：一个项目一个代理，任务由代理开出

创建时间：2026-09-24
最后更新：2026-09-26（P0-2 评审通过）

## 状态

Accepted（2026-09-26，P0-2）。实现未开工。

落地修订见 ADR 85：宿主租约与持久输入队列、待批准持久化与 `stale` 恢复、系统通知只来自送达策略、后台任务不投影 L1 内嵌浏览器。落地版本为 0.1.0（`design/product/v0.1.0-release-plan.md`）。

评审关闭了运行时契约 §13 与分层文档 §13 里和本 ADR 有关的点，结论如下。与任务卡冲突时以任务卡为准。

1. **只读范围。** 代理白名单含本机只读文件工具（`list_files`、`read_file`、`search_files`、`batch_search`）。`web_fetch` 与外网搜索不进白名单；需要上网的事开任务。
2. **能力不够就开任务。** 只读工具答不了的问题，代理直接 `spawn_session`，不先问「要不要开任务」。仍须确认的只有：签收策略判为 `confirm` 的结果、空白机器人建 README、不可逆操作、需要你批准的权限。
3. **不碰 Goal 工具。** 代理不调用 `goal_*` 与 `request_user_input`。查任务用 `list_sessions` / `get_session`，问用户用 `post_reply` 的问题卡。任务回合仍用 `request_user_input`。
4. **编排。** 单线程 actor，用户消息抢占唤醒回合。`spawn_session` 结构化建 GoalPlan，任务里不再跑 intake。
5. **调度。** 模型回合与任务条数是两件事：全局同时最多 4 个 Provider 回合；每个项目同时最多 1 条原地写任务 + 2 条只读任务，worktree 里的写任务不占原地写槽。事件 2 秒合并。非用户唤醒最短间隔 30 秒。熔断按 B4-07：代理回合连续失败 5 次后停 10 分钟。
6. **插话。** 拿不准并入还是取代时，代理规则默认并入；运行时只执行实际调用的工具。被取代的任务进 `paused`，不直接取消。引用插话在执行层强制限定范围。
7. **签收与合回。** 代签发生在代理汇报之后。策略代签不自动合入源头分支；现有交付流程里的确认保留，`autoHandoffOnPolicyAccept` 默认关闭。
8. **TUI。** 当前目录已有机器人时，`peer` 默认打开该机器人；`peer --classic` 保留直接任务。谁来跑见 ADR 85。

## 级别

A 级。改变用户的对话对象、任务的创建者、能力暴露（新增调度能力与 `project_agent` 模式）、权限冒泡路径、System Context 新增来源、会话存储的父子关系。

## 背景

原型 A（ADR 67）把「任务」当成用户的家：用户自己新建任务、在任务里对话、切换任务、到工作台雷达看哪条线要自己处理。实际用下来有三个问题：

1. **用户仍在当项目经理。** 拆成几条任务、哪条先做、哪条卡住了，都要用户自己判断和切换。这和对齐文档「用户负责目标、边界与关键判断，Peer 负责持续推进」相反。
2. **工作台雷达是补丁。** 因为用户分散在多条任务里，才需要一个跨任务页面告诉他「现在谁该动」。入口越多，雷达越重要，界面越像工单台。
3. **多 Agent 能力被埋在单任务里。** Goal Runner 已经能派只读 Explorer、Verifier，但并行推进多件事只能靠用户手动开多个任务。

参照对象是 Grok Bot：一个常驻的总管负责和人交流，按需派专职执行者，只在需要判断时把人拉进来。以及 Grok Build 的子会话模型：`spawn_subagent` 开独立子会话，嵌套深度固定。

## 决策

1. **每个项目（Workspace）有且只有一个项目代理。** 项目代理是一条常驻对话，是用户在该项目里的唯一默认对话对象。不做「总管 + 多个专职代理」的团队结构；专职角色以后做成任务模板，不做成第二个常驻代理。
2. **项目代理只读 + 调度，不产生副作用。** 它可以读文件、搜索、查看任务状态、向用户提问、开任务、给任务追加指令、取消任务、开临时只读调研子 agent。它不能写文件、跑 Shell、调用有副作用的 MCP / 浏览器动作。这个限制在 Runtime Projection 层强制（`project_agent` 模式严格白名单），不靠 prompt。
3. **任务由项目代理开出。** 代理调用 `spawn_session` 开出的子会话就是现有意义上的「任务」：一条 Conversation 载体 + 一份 GoalPlan + 可选任务分支 / worktree，由现有 Goal Runner 推进。验收、关闭闸门、Git 交回全部不变。
4. **用户可以直接进入某条任务介入。** 默认经过项目代理沟通；需要时可以点进任务，在任务里直接发消息。介入走任务自己的对话与 Goal 生命周期，不新开通道。
5. **嵌套深度固定为三层。** 项目代理 → 任务 → 任务内临时子 agent（Explorer / Verifier / 以后的 Implementer）。任务不能再开任务；临时子 agent 不能再开任何东西。项目代理自己开的临时子 agent 只能只读。
6. **仍不建 Project 表或 Task 表。** Workspace 就是项目；项目代理和任务都是 Conversation，用 `role` 和 `parentConversationId` 区分与关联。
7. **交互是锚定回复模式**（用户 2026-09-24 追加）。每条用户消息都被代理接住并有可见处置。要干活的消息，代理锚定这条消息开任务：任务带用户原话、代理写的任务说明、截至该消息的对话上下文快照。任务交回结构化的关键信息，代理重新整理后发一条引用原消息的回复。任务跑着时用户随时可以插话；代理自主决定回答、并入、取代（停旧开新）、并行、停止或排队，处置写在用户消息上，取代可以一键恢复原任务。用户引用某条消息再插话时，处置范围在执行层限定到该消息对应的任务。代理不能停止或取代已经待验收、已验收的任务。
8. **验证归代理，签收按策略，细节按需披露**（用户 2026-09-24 追加）。用户不再逐条走验收流程：
   - **代理决定验证到什么程度**：开任务时声明验证要求，结果出来后可以追加核验；运行时有不可下调的验证下限（按改动类型）。
   - **结论由运行时算，不由代理说**：任务的验证结论（`VerificationVerdict`）来自已有的验证闸门、Verifier、视觉验证与质量自检，代理不能改写。
   - **签收按策略**：结论通过且风险低时，由验证策略代签（`resultAcceptance.acceptedBy = 'policy'`），代理的回复就是交付；结论未过线、有人工标准、涉及外部副作用、用户要求过目等情况，才需要用户一键确认。合入源头分支默认仍需用户一句话确认，可按项目设置改为自动；推送远端永不自动。
   - **分层披露**：代理默认只用一两句话说结论、验证了什么、还有什么没验证；用户追问时再给细节（标准逐条、改动、测试结果），再追问才给证据本体（测试输出、截图、diff、验证报告）。
   - 这不是「模型说做完就算完」：代签的前提是运行时判定的结论与关闭闸门，代理的文字不能关闭任何东西；用户随时可以说「不对」重新打开。
9. **主动开口要过「值得打扰」评估，用户可调主动性档位**（用户 2026-09-24 选定，参考 Muse 调研）。代理每次准备主动告诉用户什么（任务汇报、目标信号、点子），先由纯函数 `SurfacingPolicy` 决定送达方式：`interrupt`（系统通知 + 对话消息）/ `message`（只进对话）/ `digest`（进每日小结）/ `silent`（只更新档案，ADR 84）。
   - **必达，不受档位影响**：需要你（权限、决策、计划批准）、需要你确认、需要决策的失败、临近截止的目标风险。
   - **你问的事要回**：用户发起的任务结束时至少 `message`；是否 `interrupt` 看档位。
   - **代理自己发起的**（目标触发、观察、点子）：先看是否有实质新内容（与上次送达的摘要比较），再按重要度与档位决定。
   - **档位**：关 / 少 / 标准（默认）/ 多，外加可选的免打扰时段；用户说「少打扰点」「这类别告诉我」由代理调用 `set_proactivity` 改设置（必须锚定用户消息），设置页可见可改。档位只影响打扰方式，不影响权限、签收与必达项。
   - **每日小结**：`digest` 项在用户设定的时间合并成一条「今日小结」，复用 ADR 82 的共享 Scheduler。
10. **四条治理不变量**（详见运行时文档）：
   - 副作用必须先有 GoalPlan：`spawn_session` 必须带目标与成功标准；需要批准的计划照旧要用户批准。
   - 权限只降不升：任务的授权面不超过用户对该项目已授予的范围；任务的权限请求以结构化卡片冒泡到代理对话，由用户批准；代理不能替用户批。
   - 代理的汇报不是证据：代理说「做完了」不关闭任何东西；签收只由关闭闸门 + 验证结论 + 签收策略决定，无论代签还是人签。
   - 代理的对话不是状态真源：任务清单、状态、行动权来自 main 进程的 store 投影，不从代理文本里解析。

## 被取代与保留

| ADR 67 条目 | 本 ADR 之后 |
|---|---|
| 产品面只说任务 | **保留**。项目代理之外，用户看见的执行单位仍叫任务 |
| 主区默认当前任务 | **取代**：主区默认当前项目的项目代理对话 |
| 侧栏工作台常驻计数 + Workspace 下挂任务树 | **取代**：侧栏是项目列表，每个项目带「需要你 / 待验收」角标；任务清单移到项目代理旁的右栏（**已被 ADR 84 改写**：即时通讯式机器人列表 + 按需滑出的档案） |
| 工作台不是唯一入口、不是默认落地 | **保留并加强**：跨项目雷达降级为角标与全局收件箱，独立工作台页进入退场评估（**ADR 84 进一步取代**：工作台不再是页面） |
| 从雷达点进去落回原任务 / 验收对照 | **保留** |
| 点工作区只激活落点 | **改写**：点项目就是打开该项目的代理对话 |
| 轻量问答不进待验收 | **保留**：纯问答由代理直接回答，不开任务 |
| `result_ready` 先看依据，确认验收只出现在看过之后 | **取代**：验证通过且低风险的任务由策略代签，不进待验收；只有需要确认的任务出现「需要你确认」，依据按需展开 |
| 不做原型 B（工单台） | **保留** |

## 后果

- 用户的日常动作从「开任务、切任务、看雷达」变成「和项目代理说话、处理代理递过来的卡片」。
- 每句话多一跳模型调用，延迟和 token 成本上升；项目代理对话常驻，压缩与项目记忆从可选变成必需。
- 对齐文档里「子 Agent 不当产品主语」收窄为「任务内的临时子 agent 不当产品主语」；项目代理本身成为产品面主语。「不是多 Agent 角色扮演」保留：项目代理是委托层级，不是虚拟团队。
- Agent / Plan 模式切换器从项目代理的输入框退场：是否需要先批准计划，由代理在 `spawn_session` 时按复杂度决定并交给用户批准卡。任务内部仍保留 Plan / Goal 的执行语义。
- 旧会话迁移为该项目下的「历史任务」（`parentConversationId` 为空）。
- 「待验收」从日常主路径退为例外：工作台 / 角标里的待验收只剩需要确认的任务；验收抽屉改为按需打开的「验证详情」，复用已有的自动验收报告。
- 签收事实多了一种来源：`acceptedBy: 'policy'`。它与 `acceptedBy: 'user'` 一样必须过关闭闸门，且不允许 `userOverride`。
- 手机与远程入口（路线图中景 #4 / #4b）只需对接项目代理一条对话。

## 不做什么

- 不做多个常驻专职代理、代理之间互相发消息的群聊。
- 不让项目代理拥有任何写能力，哪怕是「很小的改动」。
- 不让代理改写验证结论、下调验证下限，或在结论未过线时代签。
- 不为项目代理另开执行通道：调度能力同样走 Capability Provider → Manifest → Runtime Projection → Tool Call → PermissionGrant → Evidence。
- 不把任务报告、代理摘要提升为系统指令。
- 不因为引入项目代理而新建 Task / Project 存储实体。
