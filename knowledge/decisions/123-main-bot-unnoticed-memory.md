# ADR 123：主 Bot 会话的无感记忆

创建时间：2026-11-06
最后更新：2026-11-06（补入 soft 判定、分类摘要和多页情节）

状态：Proposed（方案；未授权实现，也未验收）

级别：A（主 Bot 下一轮模型上下文的投影、存储和双宿主入口）

关联：

- `knowledge/decisions/17-local-context-compaction.md` — 现有阈值、摘要和保留轮次。主 Bot 不再把这次压缩演给用户看
- `knowledge/decisions/52-unified-next-request-context-accounting.md` — 触发仍看下一请求投影，不另造一套 token 真值
- `knowledge/decisions/56-provider-observed-context-accounting.md` — 供应商实测只作诊断和强制进入摘要的条件，不覆盖投影
- `knowledge/decisions/57-canonical-conversation-history-projector.md` — 分界之后的原文才进请求。主 Bot 的分界改到情节记录，不插入假用户消息
- `knowledge/decisions/111-project-agent-duplex-supervision-and-continuity.md` — `prepare_context_handoff` 仍只服务某个工作，不承担主会话记忆

代码事实（起草时，`PeerAgent/dev/0.1.0`）：主 Bot 下一轮从交互记录读取全部 `user_input` 与 `agent_reply`，没有条数上限。桌面在请求前走普通对话压缩，可能写回一条带 `_compaction` 的用户消息。命令行把记录收成 `role` 和 `content` 后再送，标记丢失，下一轮仍是整段。子会话在 `goal` 模式使用有界 keep 和 `resuming_after_compaction`。这不是主 Bot 的路径。

---

## 背景

人在长谈里不会宣布「我现在开始压缩记忆」。刚说过的话还在，更早的事变成能接着用的印象，需要时再去回想原话。主 Bot 现在做不到这一点：窗口一满，压缩横幅、进度和一条插进记录的交接消息会让用户感觉对话被工序打断；命令行甚至下一轮又把全文带上，压缩没有留下来。

目标只覆盖主 Bot 与用户的那条会话。里面派出去的任务、子会话和 `prepare_context_handoff` 保持原契约。

---

## 决策

用户看见的主 Bot 记录保持原样。模型看见的是一份投影，不是第二份聊天记录。投影在桌面和命令行的 `executeTurn` 上是同一个模块。两边都不准再各自拼一段历史。

投影分三层，从近到远：

| 层 | 给模型什么 | 存在哪 |
|---|---|---|
| 逐字尾 | 最近若干完整来回，以及尚未回答的用户回合 | 不另存。每次从交互记录切出来 |
| 情节 | 更早对话的短事实：谁决定了什么、还没做完什么、指过哪些对象 | 会话旁的情节记录。不写入 `user_input` / `agent_reply` |
| 回读 | 用户指向尾部之外的原话或原结果时，本轮取回的有界原文 | 只在这一轮的事实上下文里，不晋升为系统指令 |

界面不出现压缩横幅、进度、百分比，也不插入「已压缩 N 条」的系统句。输入框、草稿、焦点和阅读位置不因整理情节而改变。

### 1. 什么时候整理

整理不是每收到一句用户输入就记一笔，也不是在对话旁边说话的旁白。它发生在一轮主 Bot 回复已经落成 `agent_reply` 之后，不在用户打字或输入法组字期间。

soft 判定沿用 `packages/runtime-core/src/context-projection.ts` 的 `decideContextCompaction`，不另定百分比。

| 名字 | 现有值 | 含义 |
|---|---|---|
| `triggerRatio` | 0.8 | soft。`softLimit = floor(contextWindow × 0.8)` |
| `hardRatio` | 0.92 | hard。`hardLimit = floor(contextWindow × 0.92)` |
| 窗口 | 当前模型的 context window | 窗口未知时不整理 |

拿去比较的是下一轮投影的 `pressureTokens`，不是气泡条数。估算使用同一份配置：中文约 1.7 字一个 token，其余约 4 个字符一个 token；每条消息加 4，每个工具块加 8，每张图按 2000。供应商已经回过真实用量时，用那次用量做压力，不用偏低的本地估算取消这次触发。

| 条件 | 行为 |
|---|---|
| `pressureTokens` 低于 soft | 不写情节。逐字尾就是交互记录本身 |
| 达到 soft，且最老的一段已经有回复、工具调用和结果成对、没有未答卡片 | 在后台把这一段收成一条新情节。下一轮起这段离开逐字尾 |
| 达到 hard，或大于整个窗口 | 同一轮请求里同步整理到能发送为止。仍不切掉当前这条还没回答的用户消息 |
| 整理失败、超时或摘要为空 | 这一轮用上一份已提交的情节加上仍然放得下的逐字尾。不向用户报压缩失败，不把失败写成 Bot 回复 |

### 2. 先分类，再写事实

一次整理只处理已经结束的来回：从一条 `user_input` 到回答它的 `agent_reply`。先给这段里的记录贴来源，再决定能不能写进情节。不把整段混成交给模型写一篇读后感。

| 来源 | `kind` 或对象 | 进情节正文吗 |
|---|---|---|
| 用户的话 | `user_input` | 可以。事实必须带这些消息的 id |
| 主 Bot 给用户看的回复 | `agent_reply` | 只收结论和未完成项，不收内部思考 |
| 工具 | `tool_call` 与 `tool_result` | 不进正文。逐字尾之外收成一条引用：工具名、一行结果、引用 id。调用和结果必须在同一边 |
| 子 Session 内部 | `work_session` 自己的日志 | 不读、不摘要。只有已经写进主会话 `agent_reply` 的那一句可以入账，并带上回复里出现的会话编号 |
| Agent 来信 | `agent_message` | 留在现有有界信箱。未关闭的卡片留在逐字尾，不抄进情节 |
| 工作笔记和交接 hint | `prepare_context_handoff` | 留在那个工作自己的记录里，不并进主会话情节 |

能入账的内容先抽事实，再允许一次短的模型压缩。事实只包括决定、未完成事项、用户点名的路径或对象。对不上本段源消息 id 的句子丢掉。秘密和凭据沿用现有记忆脱敏，命中则这条情节不提交。不写「根据摘要」这种说法，不写权限、批准或 Evidence 结论。

### 3. 情节记录的形状

记事本是多页，不是一页盖掉一页。新的一页不把旧页再收成一段没有源编号的话。

```text
episode {
  id: "ep-1"
  revision: 1
  conversationId
  range: { from: "m1", to: "m9" }
  facts: [
    { text: "支付不动", sourceIds: ["m1", "m2"] }
    { text: "按钮用现有绿色", sourceIds: ["m6"], sessionRef: "s1" }
  ]
}
```

`range` 是已经结束的来回的闭区间。同一范围重复写必须得到同一条情节。范围重叠或源 id 对不上时拒绝新写，保留旧情节。下一轮再过阈值时另写 `ep-2`，`ep-1` 的 `sourceIds` 不改。

窗口仍不够时，只缩短更老那页的 `text`。`sourceIds` 和 `sessionRef` 留下。不得把多页收成一份丢掉编号的总摘要。

发给模型的投影按这个顺序排：

```text
较早的 episode.facts
较新的 episode.facts
逐字尾里的最近原文
本轮按需回读的原文
工具引用
```

逐字尾里的新原话压过旧页上的事实。较新的情节压过较老的情节。旧编号仍指向当初那句原文，不因后来的说法被改掉。

### 4. 回读

交互记录里的原文不删除。几轮压缩之前的信息按这个顺序回答：

1. 记事本上还留着那句事实，就用事实。
2. 事实不够，或用户要原话，就按 `sourceIds` 回读对应消息。一次回读有条数和字数上限，只覆盖被指向的那几条。
3. 事实和原文都没有，就明确缺源，不编造。

回读结果只放在这一轮的事实上下文里，不晋升为系统指令，下一轮不自动留下，除非它被写进后来的新情节。

### 5. 工具痕迹

逐字尾之外的工具调用和结果不进情节正文。投影里只留调用名、一行结果和可再取的引用。引用对应的 Evidence 和原始结果仍在原存储。整理不得把一次调用和它的结果拆到分界两边。缺结果时，包含这次调用的整段留在逐字尾。

---

## 临界点

这些情况必须在实现前有测试，不能靠提示词碰运气。

1. **未答完。** 用户刚发来的话、打开的提问卡片、还没提交的草稿，都留在逐字尾。整理任务看到新输入就放弃这一段，下一轮再看。
2. **工具成对。** 只有调用没有结果，或结果还没落盘，这段不能收成情节。
3. **决定不能丢。** 用户明确否定或指定的做法，必须出现在情节或逐字尾之一。只留摘要套话、丢掉这个决定，视为整理失败。
4. **两扇窗。** 桌面和命令行同时整理同一会话时，用情节的预期版本。写输的一方保持旧投影，不覆盖。
5. **崩溃。** 情节要么连同源范围一起提交，要么完全不存在。不允许只写下半段摘要。进程重启后按已提交的情节投影，不重放未提交的摘要请求。
6. **摘要更长。** 摘要加逐字尾仍放不进窗口时，先折工具痕迹，再缩短更老情节的 `text`。`sourceIds` 不删。不得把多页收成一份没有编号的总摘要，也不得删除当前用户回合来腾位置。
7. **摘要说错。** 用户纠正后，下一轮逐字尾包含纠正。旧情节保留源 id，但不能压过逐字尾里的纠正。
8. **命令行和桌面一致。** 同一份交互记录和情节，两边 `executeTurn` 送进模型的投影相同。禁止命令行再把标记裁成纯文本后整段重送。
9. **界面不动。** 整理前后，交互记录的消息 id 和顺序不变。用户滚动位置、草稿和焦点保持原状。
10. **不是子会话。** 主 Bot 不进入 `resuming_after_compaction`，不使用 `goalKeepPolicy`，也不调用 `prepare_context_handoff` 来代替情节。

---

## 工程落点

新增一个主 Bot 上下文投影模块，只被两边的 `executeTurn` 调用。它读取交互记录和情节，输出本轮 messages 与事实块。现有 `projectConversationHistory` 继续服务经典对话和已经写有 `_compaction` 的旧记录；主 Bot 新回合不再依赖那种用户角色的交接消息。

情节存在会话数据根下的旁路记录，带版本、源范围和内容哈希。它不是 Conversation 的 `user_input`，也不是系统提示。进入模型前走现有事实上下文准入，不新增一条可以改写规则的系统指令通道。

预检和供应商计数继续包住这份投影。投影变了，计数指纹必须变。后台整理使用现有模型通道，但不占用户这一轮的回复，不抢焦点，失败不重试成循环。

旧的主 Bot 会话没有情节时，第一轮仍发送现有交互记录，并在回复落地后按本文补第一段情节。不迁移历史时把旧 `_compaction` 用户消息改写成情节；那些消息继续按 ADR 57 只作经典分界。

---

## 明确不做

- 不把压缩过程画进主 Bot 界面。
- 不把摘要伪装成用户说过的话。
- 不改子会话、Goal Runner 和 `prepare_context_handoff`。
- 不把情节当成权限、批准或 Evidence。
- 不新写触发百分比。soft 与 hard 继续用 `decideContextCompaction` 的 0.8 和 0.92。
- 不把旧情节再摘要成丢掉 `sourceIds` 的一页。
- 本文被接受之前不实现。

---

## 验收

桌面和命令行用同一段长交互记录：界面消息 id 不变；模型请求不含已被情节覆盖的原文；未答用户回合仍逐字存在；工具调用和结果没有被拆开；整理失败时用户仍能收到回复；第二宿主不能用旧版本覆盖新情节。
