## 1. 测试与发布顺序

开发者先完成 Beta1–5、RC01–05、自测与问题修复，给你一套确定版本的可安装 RC 包、本文和自测报告。你再做全面测试与七天日用。任何 P0/P1 尚未修好，或你未明确批准，都不发布正式版。模型一句“完成了”不是通过；核对结构化任务状态、实际文件、验证结果与 Evidence。

### 版本与结果填写

| 项目 | 必填内容 |
|---|---|
| 候选版 | RC版本、代码提交、安装文件、SHA256（开发者填） |
| 环境 | OS/架构、内存、模型渠道/模型名称（不填密钥）、CLI/Gateway版本 |
| 用例 | 编号、项目、开始/结束时间、实际结果、Pass/Fail/Blocked、不适用理由 |
| 证据 | 截图、任务ID、脱敏诊断JSON、最小测试文件差异、问题编号 |

未执行不要填Pass；网络/模型/平台条件缺失填Blocked，并写清条件。本文的“预期”不代表开发者已测通过。每一组都有自测证据范围，完整候选报告把自动化、真实模型、UI、安装、网络、跨版本分别列出。

## 2. 测试准备（约20分钟）

### 三个项目

- A：可以删除的Git项目，README.md写“验收标记 PEER_ACCEPT_A”，src/sum.js提供加法函数，package.json的test脚本运行test/sum.test.js；初始提交并保持干净。用于写入、并行、隔离与合回。
- B：可以删除的普通文档目录，README.md写“验收标记 PEER_ACCEPT_B”，放两份不含个人信息的短文本。用于只读研究、记忆和非Git拒绝。
- C：由“新建机器人”创建的受管项目。用于身份、新建、管理和连续日用。

至少设置一个支持工具的模型与一个快档模型。视觉项目需要一个支持图片的模型；缺条件时只标该用例Blocked，不把它误记为通过。使用你的账户接入远程Gateway；电脑在线，同版本桌面/CLI/Gateway。不要把生产仓库、凭据或个人文件当写入测试夹具。

### 项目A的可复制准备步骤

macOS/Linux终端执行下面命令，创建一次性的目录；不需要安装npm依赖。Windows可在Git Bash执行相同步骤。需要Node.js和Git已安装。

```sh
TASK_PROJECTS_ROOT=$(mktemp -d "${TMPDIR:-/tmp}/peer-acceptance.XXXXXX")
mkdir -p "$TASK_PROJECTS_ROOT/A/src" "$TASK_PROJECTS_ROOT/A/test" "$TASK_PROJECTS_ROOT/B"
cd "$TASK_PROJECTS_ROOT/A"
cat > README.md <<'EOF'
验收标记 PEER_ACCEPT_A
测试命令：npm test
EOF
cat > package.json <<'EOF'
{"name":"peer-acceptance-a","private":true,"type":"module","scripts":{"test":"node --test test/*.test.js"}}
EOF
cat > src/sum.js <<'EOF'
export const sum = (a, b) => a + b;
EOF
cat > test/sum.test.js <<'EOF'
import test from 'node:test';
import assert from 'node:assert/strict';
import { sum } from '../src/sum.js';
test('sum adds two numbers', () => assert.equal(sum(2, 3), 5));
EOF
npm test
git init
git add README.md package.json src/sum.js test/sum.test.js
git commit -m "Acceptance fixture"
git status --short
```

首次提交若提示缺少Git身份，只为该目录运行 `git config user.name "Acceptance"` 和 `git config user.email "acceptance@example.invalid"`，然后重试提交。基线要求npm test退出0、Git已提交且状态为空。记下终端变量 `TASK_PROJECTS_ROOT` 指向的路径，绑定其中A目录；不要将临时变量的字面名称填入界面。在B目录建立README.md及两份短文本后绑定B；C从产品“新建机器人”入口建立。

### 数据隔离与备份

关闭全部Peer宿主后备份整个数据目录。macOS/Linux示例（把候选版实际路径替换进去）：

```sh
TASK_BACKUP_DIR="$HOME/Peer-Acceptance-Backup-$(date +%Y%m%d-%H%M%S)"
mkdir -p "$TASK_BACKUP_DIR"
cp -a "$HOME/.peer-agent" "$TASK_BACKUP_DIR/data"
```

备份含私密配置，仅自己保存，不上传问题单。新数据验收可用单独目录启动安装候选版：

```sh
TASK_ACCEPT_HOME="$HOME/Peer-Acceptance-RC"
mkdir -p "$TASK_ACCEPT_HOME"
PEER_AGENT_HOME="$TASK_ACCEPT_HOME" "/候选安装路径/Peer Agent.app/Contents/MacOS/Peer Agent"
```

窗口Chromium数据不是项目事实；如需独立窗口配置，另传 `--user-data-dir` 指向新的测试目录。Windows在PowerShell中设置 `$env:PEER_AGENT_HOME` 后启动候选exe。不要删除原 `.peer-agent`。恢复时先完全退出全部宿主，把失败数据目录保留下来，再从备份复制回去；不要把旧/新宿主同时对着同一数据目录运行来“恢复”。升级/降级专用用例允许轮流用同一个隔离数据目录。

### 验收用语

- “已收到”：持久输入回执；不表示任务已完成。
- “任务完成”：执行结束；核验/签收/合回仍可能待处理。
- “已接受”：签收通过；需要合回的隔离写任务仍看合回状态。
- “需要你”：确有未答问题、批准或确认；数量和卡片同步。
- “可能已送达”：不要编辑正文或生成新输入ID；在当前网页用原输入重试。

## 3. 最短主流程（先跑，约40–60分钟）

1. 安装候选版，确认“关于”和CLI版本一致，首次打开无白屏。
2. 接入模型，绑定A和B、新建C。三台机器人身份与头像独立；颜色可选，头像状态随思考/等待变化。
3. 在B发送“读取README.md，告诉我验收标记；只读，不开写任务。”核对真实read_file Evidence和唯一回复。
4. 在A发送“新增减法函数及测试，修改仅限本项目；先给出计划与成功标准。”完成计划批准、执行、核验、签收、合回。亲自运行test并查看Git diff。
5. 做两件独立写任务，检查不同worktree、同时运行和各自报告；故意制造冲突，确认等待决定且不覆盖文件。
6. 保存项目记忆，重启后询问；关记忆后再问，确认上下文不再使用该条。
7. 创建文件或CI观察目标，变化通知一次、不变不通知；暂停后不继续开任务。
8. 桌面开着时在A目录运行peer并发消息；桌面退出后终端接管，同一输入只一条。
9. 远程按机器人授权，手机读对话/发消息；批准提示回电脑。电脑离线后发消息明确失败，没有隐藏排队。
10. 导出诊断，确认无对话原文、密钥或绝对路径。完成后再按下面分组全面测试。

## F 批准、回答与签收

使用可丢弃项目。拒绝操作时不需要提供任何真实凭据。

|---|---|---|
| F01 | 将计划批准策略设为每次批准；发写任务；先查看计划，再批准；刷新/重启后继续核验。 | 批准前没有文件写入；批准对应可见计划；之后开始真实执行。批准历史保留，核验不应因缺少同次批准记录而再次要求批准；这不等于文件权限或结果签收。 |
| F02 | 触发文件/命令权限请求；第一次拒绝，第二次对新请求批准。 | 拒绝被记录，工具不执行；批准后只执行授权操作，结果有 Evidence。 |

| F06 | 同任务连续调用相同能力；再创建另一任务执行同能力。 | 合法的任务级授权可复用；另一任务、不同参数或不同能力不能继承超出范围的批准。 |

## I 模型分工与用量

先记录四档的模型名称和渠道，不记录密钥。GPT订阅目录应可选GPT-6.1 Sol（精确id gpt-6.1-sol），提供low/medium/high/xhigh/max和400K/1M档位；原默认保持。选择该模型、重启读回后，分别在经典对话和机器人请求读取项目文件并回复。空文本/无工具即失败；RC2曾出现经典low/default通过而机器人空响应失败；RC3修复post_reply终结后实际默认签名助手、一次HTTP200/唯一canonical回复通过，保留前后证据。RC4本轮未重跑该模型流程，不能把旧候选结果当RC4实测。API参考价格不能作为订阅账单。复核模型与工作模型来自不同源的场景需要两条可用渠道；只有一条时如实记为环境未具备。

## 六条必须逐步通过的端到端流程

### 流程 1：绑定项目 → 熟悉 → 真实来源

1. 使用夹具 A 干净 git 项目，绑定目录，记录机器人名称、workspaceId（从脱敏诊断）、初始文件 hash。
2. 点击先熟悉一下，打开档案任务；记录研究任务 ID。重复点击一次。
3. 等待实际读取 README，查看工具与 Evidence；检查没有 write/edit/bash 写入。
4. 打开报告，核对 README 中的验收标记、实际 npm test 命令；任务仅一条。
5. 重启；报告、任务来源与 ID 保留，目录 hash 未改变。

通过依据：唯一任务、真实读取、正确报告、重启保留。仅看到“我已了解”不算通过。

### 流程 2：批准 → 修改 → 测试 → 核验 → 签收 → 合回

1. A 项目提交干净基线，将计划批准设为每次，签收设为手动。
2. 发指令：“在 src/sum.js 导出 subtract(a,b)，在 test/sum.test.js 新增 subtract(5,3)=2 的测试并保留原sum测试；只改这两个文件，运行 npm test，成功标准为两项测试都通过且退出码0。先给出计划与成功标准。”
3. 计划待批准时先看 git diff。未授权前不应执行。拒绝一次；新发当前有效请求后批准。
4. 工具权限请求检查命令/范围，按需批准；观察真实独立 worktree。
5. 查看实际测试 Evidence（命令、退出码、输出/读回），并确认核验结果；不以模型文字代替。
6. 签收前应保持待签收；从一处签收，另一处状态同步。
7. 用产品合回入口交付；核对主目录diff仅含src/sum.js和test/sum.test.js，亲自运行npm test确认两项测试通过；重启保留已接受和交付事实。

通过依据：批准前无执行、权限拒绝无副作用、唯一任务、真实变更和测试、核验/签收/合回各有依据。

### 流程 3：三任务并行 → 插话取代 → 恢复原任务

1. 槽位设为3，分别授权只改 a.txt/b.txt/c.txt 的三任务，每项标准为文件含指定标记。
2. 记录三任务 ID、隔离目录和开始时间；确认主目录未提前污染。
3. 对 C 明确发替代只读任务；记录原计划暂停/替代开始。
4. 完成替代后恢复原 C，核对原 ID/计划/标准/现场未重建。
5. 三项核验签收并逐项合回；主目录只有预期内容。
6. 重启后检查状态，没有重复执行/创建任务。

通过依据：真实重叠执行、互不污染、取代可逆、原任务身份不变、三项实际交付。

### 流程 4：目标变化 → 一次信号 → 用户决定 → 真实任务

1. 建立提示型 git 或 CI 目标，先无变化探测三次；记录没有通知/模型流。
2. 在测试分支制造明确变化/失败，探测；记录实际观察 Evidence 与卡片。
3. 相同状态再探测三次，并完全重启后探测；不会重复同一信号。
4. 用户批准目标提议，打开真实任务；它仍沿计划/工具批准链。
5. 修复后观察恢复事实一次；暂停目标后不继续触发。

通过依据：变化来自事实、去重跨重启、用户决定后沿正常执行链、不越权。

### 流程 5：Desktop + TUI + Remote → 单宿主 → 电脑批准

1. 桌面先启动 A；同版本 peer 在 A 目录打开，确认客户端状态。
2. 手机登录/配对，给 A 可看+可发；B 默认关闭。
3. 三入口各发唯一只读标记输入，记录 inputId 和三条 canonical 输入；每条唯一回复。
4. 远程发需要批准的任务，手机只显示“需要在电脑批准”，电脑出现同一待批准项。
5. 在电脑拒绝/批准，验证手机无批准执行接口。
6. 完全退出桌面，让 TUI 接管，发只读文件请求，检查实际 Evidence。
7. 再开桌面检查租约，无双执行，无输入丢失或重复。

通过依据：同项目单宿主、三入口同一真源、真实只读结果、远程不能批准、接管后真实执行。

### 流程 6：0.0.18 → Beta → 旧版 → RC

1. 用隔离目录生成真实旧版设置/会话/Goal/自动化/远程数据，记录文件 hash 和所有 IDs。
2. 逐版升级，读取历史和新增机器人身份；再次启动验证迁移幂等。
3. 装旧版读取同一目录，打开旧/机器人/任务会话，不启动旧 CLI 推进。
4. 再装 RC，核对 ID、记忆/目标/档案与 canonical 行。
5. 与自动化矩阵报告比对，记录安装包版本和实际启动情况。

通过依据：旧文件未被无故重写、降级可读、再升级身份稳定、没有数据丢失。不要在用户原目录进行首次演练。
