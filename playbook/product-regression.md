# AI 产品回归流程

适用：Peer Desktop 的用户界面、文案、交互与 RC 候选。更新：2026-10-10。

产品判断沿用 [Peer 产品理念](../design/product/peer-product-alignment.md)：用户交代目标，机器人推进工作并交付结论；细节按需披露。此流程不改变 Runtime、权限或 Evidence 契约。

### 待处理事项与旧提问收尾（2026-10-20）

按 ADR100，机器人角标和明细共用宿主 Attention 投影。窗口验收使用标准 200 个机器人 / 1 万条主对话消息 / 10 万事件 / 1 万条记忆夹具，检查重复旧问题只保留当前决策、角标等于明细、机器人间隔离、从原文入口实际定位当前问题、读取与提交失败可重试、回答经生产输入队列入档后移除事项，以及新提问到来时替代旧提问。另检查明确截止时间自动刷新与到期旧按钮拒绝。

真实图片读取须从该明细面板批准，继续沿生产 Runtime Projection、PermissionGate、LocalImageProvider 与 nativeImage 返回像素、Grant 和 Evidence；处理后该项从明细移除，晚到操作仍不能重开终态。人工完成检查继续先打开完整报告，不能用待处理摘要跳过核对。

深色宽窗、浅色窄窗、处理后空态、到期空态、真实看图授权面板五张截图加入标准审查包。原有权限/任务事实不得为让清单归零而被测试自动批准或改写；只在当前隔离夹具内回答测试问题。个人记录仅做只读事实重放，保留其原始权限、任务和消息。

### 完全授权的多图执行（2026-10-12）

按 ADR92 §9，在宿主实际 `full_local` 下读取多张不同项目外 PNG；主 Bot、子执行者、Verifier 和恢复应继承当前访问策略，不逐图弹权限卡。真实 Runtime Projection / ToolHost / PermissionGate / nativeImage 读取和像素 SHA-256、PermissionGrant、Evidence 仍须成立。宽窗深色、窄窗浅色及恢复后的无权限卡完成态进入标准包，检查没有静态“等待你的授权”或多张批准回执占据主对话。截图不得代替像素与审批记录的机器核对。

旧六分支权限卡用例明确使用 ask_before_local；Full 无卡与需要批准的拒绝/取消/超时分支分别保留。不能为让测试继续出现卡片而把 Full 的 Bot/Verifier 排除重新写回权限门。

### 活跃图片请求的权限生命周期（2026-10-11）

按 ADR 92 §8，从生产 `view_image` Runtime Projection → ToolHost → PermissionGate 实际发起项目外 PNG 读取，让权限事实自动生成主 Bot 卡片；不以注入预制卡片代替。生产 CardView → IPC → ApplicationService 决定后，同一调用继续通过 LocalImageProvider 与 Electron nativeImage 返回视觉侧带。验证返回字节的 SHA-256、尺寸、PermissionGrant 与 Evidence，以及本轮同一图片再次读取复用原 grantId。

交互必须覆盖允许一次、本轮此图片、拒绝、取消本次读取、停止回复和等待超时。未批准的分支不得返回像素，活跃等待应清空；迟到 / 重复批准不能重开终态，另一项独立请求仍需单独决定。等待时显示等待授权，结束后卡片关闭旧操作，历史展示回执与宿主事实一致。

标准包加入 7 张必查截图：深色宽窗与浅色窄窗等待、允许后续跑、拒绝、卡片取消、停止回复、超时。逐图检查具体路径、模型使用说明、等待期限、四种操作、长路径换行和最终状态。UI 测试注入短期限，生产默认等待期限为 5 分钟；使用受控认知执行器提出调用，证明真实本地读取与原生解码，不证明云模型理解或安装版 RC 的长期运行。

### 等待跟进任务的直接取消（2026-10-10）

主对话后台任务条目和侧栏任务详情必须提供直接“取消任务”动作，沿用既有取消 IPC，由宿主决定状态；不能要求用户再发消息才能结束等待。两处入口共用提交状态，提交期间禁用重复点击，失败保留任务并可重试。成功读取宿主最新状态后，从待跟进列表移除目标任务；历史回复和详情显示“已取消”，不能继续引用旧报告的“等待你的选择”。历史结果与其他任务保留。取消后原按钮卸载时恢复键盘焦点，不抢走用户已移动的焦点。

标准窗口包增加取消失败、成功后的历史与其他工作、760px 浅色任务详情三张必查图；验证聊天与详情两处动作、共享等待态、失败重试、重复点击去重、最新状态、无关工作保留、窄窗布局及键盘焦点。窗口测试在应用服务 seam 使用受控取消回执；真实宿主 Supervisor 的取消持久化、重复取消和历史保留另以隔离存储测试验证。两者都不能宣称已取消用户个人数据中的任务。

### 主 Bot 的连续表达（2026-10-06）

调度让出后的反馈（2026-10-16，B 级修复）：用户输入的本地“已收到”仅证明入队，不能当作回复完成。用户回合主动让出执行时，沿用 `agent_turn.publicUpdates` 保存真实公开段落及原输入锚点；内部 `rounds[].text`、思考和自动 wake 仍不得升成公开正文。尚无正式回复关联的公开段落须在历史中保持可读、可打开该切片的过程；正式回复或活动预览接管同一回合时去重。后台内部记录、其它输入的答复均不能清除本条输入的等待提示；有实际锚定回复、失败或停止卡时才收束等待。此修复沿用现有消息、Activity、权限和执行契约，不把展示状态变成任务状态。

仅询问当前进度时，项目代理先按最新任务事实回答阻塞与下一步，不把进度查询扩成阻塞答复的新一轮独立核验。后续授权范围内的工作仍须经原协调入口，给等待中的子 Agent 发信息不等于恢复执行。该认知规则进入既有 project-agent Context Source；不以关键词分流或降低验证闸门强制实现。

标准窗口包增加深色 1280、浅色 760 两张调度让出截图：受控模型经真实 Runner、预算及原生检查点让出，再继续等待正式答复，验证公开开场白仍出现且只有一次、真实续跑可停止、最终答复出现后前段保留、私有思考不可见。隔离 Runtime 测试另覆盖让出、无关 wake、重启和输入锚定；渲染测试反证“任意内部消息就算回答”。这不证明云模型回复时延或每次遵循先答进度规则。

多步用户请求可以先收到简短计划，推进时收到重要发现，再收到结论。公开进展来自现有 `chat:stream:delta`，由 Activity 保存到用户回合的 `agent_turn.publicUpdates`；工具后的新文字成为独立段落。思考事件、唤醒回合与旧内部 `rounds[].text` 不进入聊天。进展不是 Tool Result、Evidence、问题卡片或任务完成事实；结论、可操作问题和完成声明仍由经过宿主校验的 `post_reply` 交付。规则进入现有 `project-agent` Context Source，层序、权限和执行不变；新增公开投影存储契约已先记入工程治理 §十四（A 级）。

回归必须逐阶段推进流：首段在模型未结束时可见；后续段落真实到达后出现，首段节点不重建、不重播动画；公开文字默认可读，工具参数仍折叠。正式回复到达及下一回合开始后，早先公开段落保留且顺序一致；兜底结论、停止时的重复末段只显示一次。切换 Bot 后恢复，阅读历史时不抢滚动；减少动态效果时仍可读。不能把最后一整块文字拆成延时动画来冒充中途对话，也不能给简单回答强制添加过程播报。

### 输入框比例与重排（2026-10-06）

手动重试的可见进度（2026-10-06）：用户点重试后，原 wake 也经既有 Activity 立即展示等待和公开段落，停止动作可用，完成后公开段落保留；自动 wake 仍隐藏中间正文。窗口包从真实持久化的 wake 失败卡点击重试，经生产 IPC、宿主 Runner 与 Executor 跑到正式回复，加入深色宽窗、浅色窄窗两张必查截图。模型为受控执行器，此项不能代替真实服务响应时长和质量验收。

输入框属于 C 级表达调整。参考控件的视觉关系，沿用主题色板：灰色底面、轻边缘、连续圆角；附件在左，模型、思考档位与发送集中在右。空输入不保留过多空白，正文与工具栏有共同内边距；按钮用 border-box，避免高度再次叠加 padding。长文自然增高至上限后内部滚动，窗口变窄或打开侧栏时已有草稿也须重排，不等待下一次输入。

标准包必须包含深浅色空态、窄窗口、长草稿和真实附件截图，并验证控件不重叠、垂直居中、工具分组、发送禁用态、长文滚动、宽度变化重排与模型菜单键盘打开/关闭。原有档位保存与失败回退检查继续执行；不要只验空输入或通过文本断言判断视觉比例。

### 机器人消息与技术详情（2026-10-06）

主对话的公开进展以完整段落气泡逐条出现；正式回复使用完整消息气泡，保留原有 Markdown 与结构化问题。气泡只表达现有公开文本，不生成新的回合、执行事实或人工延时。工具过程、任务执行记录、证据、记忆与通知元数据统一进入消息末尾的小字“查看详情”；点击直接打开右侧回复详情栏，不在聊天下方展开。详情栏绑定当前回复，运行时保留简短状态，后台任务仍显示宿主真实运行状态。问题和权限卡不能藏进技术详情。

表达指导沿用现有 project-agent Context Source（B 级）：先用日常语言说明目标、进展、结论、下一步或具体问题，不把原始参数、内部标识、模型与验证机制堆进普通聊天。失败、未经验证的结果与用户必需动作仍须清楚说出；明确请求技术解释时直接回答。Context 层序、PermissionGrant、Evidence、post_reply 校验和存储契约均不变，不用关键词删改历史正文。

主 Bot 的委托表达（2026-10-07，B 级）：主对话以用户的目标为主语，开头只做一次简短回应，之后只汇报新发现、明显的路径变化和真实阻碍。检查旧任务、安排执行、验证结果等常规步骤在后台进行。尚在执行时以简短 `post_reply` 结束发起回合，等待结果或异常事件继续处理；若开头已经完整回应且没有新情况，沿用同一句回应，由现有相同末段去重呈现一次。排队、受阻和必须用户决定的情形仍须如实说明。后台启动和普通进度事件仅确认已回应的工作时，不重复查工具或播报状态；完成事件仍读取真实结果、经过必要验证并附真实来源。结论优先说发现与实际意义，不列旧会话状态或转抄执行报告。普通失败需说明已知原因、机器人可做的下一步或具体待答问题，不只说“执行受阻”，也不要求用户去子会话维持流程。

规则与提示资源测试检查用户回合、后台唤醒和完成事实仍在原有 Context 层。标准窗口包用受控公开段落验证自然开头、具体发现和详情分层；该包验证表达载体，不证明真实模型每次遵从语气与进展频率。真实模型的回复质量与重复程度必须单独说明覆盖情况。

失败消息同样由命名机器人用简短气泡说明回复未完成；重试动作继续直接可见，原始 HTTP / JSON 诊断保留在末尾详情中，不靠字符串猜测错误类型或删掉诊断原文。

回归增加深浅色气泡背景、完整文本边界、末尾详情位置与字号、默认隐藏技术记录、键盘打开侧栏与展开嵌套参数、流式到历史的详情状态保持、关闭回到该回复入口且保持阅读位置、证据返回同一条回复详情，以及公开段落节点不重建。完成态深浅色和回复详情侧栏截图须逐张检查；长报错默认简短、详情保留完整诊断，并检查窄窗口和停靠面板下的换行，不能仅凭 DOM 包装判断聊天感。

会话引用（C 级表达）：用户发送的显式引用嵌入新消息气泡，代理回复的来源引用置于正文上方；两处均使用紧凑淡底、较小的真实来源名字及最多两行原文摘要，不加前导装饰竖线。用户于 2026-10-06 明确表示不喜欢竖线引用，认为其显得 AI 化；后续会话引用设计沿用此偏好，以底色、字号和间距表达层级。输入框待发送引用沿用同一层级并可取消。视觉摘要不能截断存储原文或改写来源；普通相邻回复不增加引用。保留点击及键盘定位原消息、原文高亮、完整可访问名称与提示、取消后草稿和附件保留。深浅主题的已发送引用、窄窗口发送前/后引用四类截图加入必查包；检查引用和新正文的边界、换行、焦点及真实来源，不能仅用颜色断言替代视觉审查。高对比模式可提供完整轮廓及键盘焦点，不以单边装饰线替代。

## 1. 为什么机器测试通过仍会出问题

选中文字引用（2026-10-07，C 级）：真实长回复包含 Markdown 列表与问题选项时，旧 Bot 引用按钮被插入整条回复底部，距离选区约 344px。按钮应浮在实际正文 Range 附近，不占用消息流高度；滚动和窗口/侧栏宽度变化后重算位置，选区离开会话可视区域、清除、跨入问题卡或来源卸载后撤掉。保留原有引用正文与来源回调，不修改执行或权限契约。窗口回归使用长回复与问题卡复现，修复前断言失败；检查实际间距、深浅色与 760 窄窗、侧栏展开、鼠标点击与键盘 Tab/Enter/Escape、滚动跟随和保留草稿。鼠标松开不得在 click 派发前撤掉浮层。三张选区浮层截图加入必查包，不能只检查发送后的引用样式。

2026-10-06 的任务详情把来源消息 UUID、冻结模型和空字段直接展示给用户；完整报告已读取，但渲染优先使用列表的简略数据。旧窗口测试覆盖了工作状态、概况和记忆，没有打开任务详情，也没有检查用户能否理解下一步。

因此验收分为两层：确定性交互回归验证行为；AI 使用本轮真实截图与操作证据，检查信息层级、文案、操作主体和视觉表现。截图数量和测试数量均不能直接替代产品验收。

## 2. 一次完整执行

从代码仓运行，输出目录使用仓库之外的临时目录：

```sh
pnpm qa:product:test
pnpm qa:product:capture --output /tmp/peer-product-review
```

Capture 会构建正式组件，然后在隔离 Electron、隔离数据与受控模型执行器中运行现有窗口验收。生成：

- `machine.json`：实际交互与状态断言、执行范围、错误。
- `screenshots/`：必须审查的本轮截图，涵盖任务详情、工作状态、Bot 概况、记忆与过程。
- `packet.json`：源码指纹、运行 ID、截图 SHA-256、审查标准与未覆盖范围。
- `review-template.json`、`review-instructions.md`：AI 审查入口；模板默认 `not_checked`。
- `result.json`：此时只能是 `awaiting-ai-review`，不是通过。

AI 读取机器报告与所有要求的图片，逐张填写 `review.json`。不能只读文件名或断言日志，也不能给没看过的图片预填通过。每条判断写具体观察；发现阻断问题，修复后重新 capture，绑定新源码和新图片。

```sh
pnpm qa:product:verify --output /tmp/peer-product-review
```

Verify 检查本轮源码指纹、运行 ID、全部图片哈希和审查完整性。缺少审查、`not_checked`、模糊结论、图片替换、源码变更或未解决阻断问题均失败。重新运行先撤销旧通过标记。

## 3. 用户视角的必查项

| 问题 | 必须能从页面或真实交互中回答 |
| --- | --- |
| 这是什么工作？ | 有自然语言标题和任务说明；目标不能标成已完成结论。 |
| 现在怎么样？ | 当前状态来自宿主事实；运行、等待、失败、完成、不可用明确区分。 |
| 需要我做什么？ | 默认动作有明确去向；回主对话与机器人沟通，不要求用户理解子进程机制。 |
| 默认展示什么？ | 进展、说明优先；内部 ID、模型机制和原始记录按需展开，无重复空字段。 |
| 视觉是否可读？ | 标题、正文、说明层级明确；说明小而轻；返回导航不过度突出；无裁切和横向溢出。 |
| 交互是否完整？ | 键盘可用、展开收起可返回、失败可恢复、状态更新不跳变；截图不能单独证明动画。 |

当前确定性新增场景：任务详情 9 种状态；列表无报告而详情有报告；最新状态覆盖旧报告状态；默认隐藏技术标识；键盘展开；主动作回到主 Bot；1280/760 两种宽度与浅/深色。

真实任务核对还发现：`result_ready`（待你确认）原被归入“已完成”。已修正为“需要你”，并加入各状态从列表分组到详情的关联断言；“已签收”仍与“待你确认”分开。终态分组改为“已结束”，不再让失败和取消也看起来像成功完成。

本轮 AI 截图检查额外发现：记忆筛选框的局部 `min-width: 0` 被通用下拉框样式覆盖，窄侧栏里两个控件相互贴合并超出各自列。已修正样式作用域，并加入两种窗口宽度、两种主题的列边界和控件间距断言。

后续用户指出：主对话中的真实 HTTP 400 错误 JSON 仍越出卡片，上一轮审查只覆盖短错误文案，漏看了实际窗口中已有的长错误。用户反馈涉及的真实内容必须纳入审查；合成数据需保留对应的长度和无空格字符串特征。现加入长 JSON、长 URL 和连续标识，检查深浅主题、1280/760 宽度及展开档案后收窄的主对话。断言文字片段实际边界，而非仅检测容器宽度或用裁切掩盖溢出；要求完整文本保留。两张错误截图成为审查包的必查项。

服务商页面也纳入必查：默认使用平铺服务行，协议、凭证和模型管理按需展开；图像识别设置默认收起，右侧显示持久化的模型及服务摘要。说明采用面向用户的短句，字号小于标题、字重较轻；文字组与摘要垂直居中。在 1280/760 宽度与深浅主题下检查实际中心线、列边界和字号，四张设置行截图及默认/展开的服务页面截图必须逐张审查。测量展开与收起过程中实际渲染的中间高度，验证键盘展开、模型切换后重新进入仍保留选择、关闭备用模型，以及编辑连接和添加服务入口。配置的模型来自隔离数据，不写入系统凭证库，窗口回归不请求真实 Provider；协议问题另用生产适配器进行有界的实连验证。

现有 CI 的 `--work-surfaces` 路线会运行这些新增检查。其他流式、粘贴/附件、模型切换、推理强度与无障碍用例仍走原有窗口验收。

输入框上方的后台任务摘要必须与输入框共用内容列。检查 1600/1280/760 三种窗口宽度、深浅主题以及收起/展开两种状态的左右实际边界；正文与展开内容也必须留在该列内。宽窗口收起与窄窗口展开的两张截图加入必查包，避免只在窄窗口验收而漏掉居中最大宽度与整页边距不一致的问题。

子任务进入 `waiting_user` 时，回复内和输入框上方共用的条目只表达“等待跟进”及宿主进展，不把它直接变成“需要你处理 / 查看并处理”。展开后用主机器人名称说明主对话负责跟进；“查看任务详情”只用于了解情况，详情的主动作返回主对话。`result_ready` 保留“结果待确认”，确认与权限真值不因文案改变。窗口用例覆盖两处等待条目、键盘打开详情与回主对话、等待到结果返回和已签收的通知更新；等待截图加入必查包。实际用户决策仍由主对话中的结构化卡片和机器人说明承接。

用户继续点击详情后，不能只看见“执行受阻”与泛泛的“回到对话”。详情须分开表达宿主当前状态、下一步的负责人、主机器人已有的相关说明。`SessionReport.summary` 读取实际 worker 消息或已完成叶子的结果；`taskBrief` 承载原始派工目标，不能把目标、验收标准或未验证的模型结论当成宿主已完成事实；原始派工指令与标识按需展开。相关说明只通过宿主的来源、消息锚点或卡片引用关联，不猜测正文。存在未答的结构化问题时，展示具体问题并定位主对话中对应的选项、交付键盘焦点；没有问题时，不制造确认要求。可选询问应准备带任务上下文的草稿并聚焦输入框，保留用户已有草稿及附件，不自动发送、批准或恢复任务。回归必须检查真正的目标消息与问题按钮，不以“抽屉关闭、输入框可见”代替交互闭环；主对话定位、询问草稿、具体问题及其定位四张截图加入必查包。

已签收或取消的任务显示可选追问，不暗示仍在等待机器人跟进；追问草稿询问结果和依据。输入框已有正文或附件时，仅定位并聚焦，不替换正文、附件或引用上下文。问题卡有明确任务引用时，以卡片引用为准，不把同一回复中另一个任务的问题借过来。

相关回复预览必须用实际长内容检查。短的两行合成回复没有暴露嵌套 Markdown 段落无法被父层行数限制的问题；详情现在提供有限长度的纯文本摘录，最多三行，完整原文仍可定位到主对话。窗口用例加入多段 Markdown、内联代码和末尾标记，检查预览实际高度、无隐藏交互，以及完整源文保留。消息、问题和询问草稿的落点截图都应等待侧栏退出完成。

## 4. AI 审查的真实性与范围

目前是 **AI 编码代理驱动的标准回归**：代理执行自动窗口测试，再读取图片审查，Verify 阻止缺失/过期验收。没有新增后台模型调用或定时任务，CI 尚未接入无人值守视觉模型，不能宣称已经建成无人值守 AI 测试服务。

实现者自审必须记 `independent=false`。独立审查需要确实由未参与实现的审查者执行，不得仅换一个报告字段。

受控模型只验证应用交互与结构化数据路径。真实 Provider 协议、网络故障、模型交付质量、安装包、升级迁移、所有平台、读屏和长时间使用另按 [发布验收手册](v0.1.0/acceptance-test-guide.md)执行。当前包通过不代表这些范围通过。

## 5. 修复闭环

中断历史收束（2026-10-18）：在真实 Runner / 原生检查点 / retry IPC 上模拟首次失败、继续再次失败、再次显式继续成功。旧卡被宿主结束后不得继续显示本地失败回执；纯历史中断默认折叠且没有重复机器人气泡，真实公开进展保留。键盘展开可读原始诊断，关闭详情回到该历史入口；当前失败、问题和授权卡保持可用。断言正式答复交付、三次受控认知仅一次 read_file 派发，不能用自动重放或仅改错误文案通过。深色宽窗、浅色窄窗两张截图和完整机器断言成为必查项。上游空响应的生成原因与 UI 错误回执残留分别记录，不把展示修复解释为 Provider 质量修复。

1. 收集用户目标、当前界面和具体操作。
2. 找出数据或表达根因，修改真实组件。
3. 把漏测状态或路径写入窗口回归，先确保用例能暴露原问题。
4. Capture → AI 审查 → 修复 → 新 Capture → Verify。
5. 交付时给出本轮报告、修复内容与覆盖限制。发布前再执行候选构建对应验收；不复用旧候选的通过结论。

完成前人工核对与完成后签收必须分别验证（2026-10-06）：以真实的 manual DoD 宿主阻塞事实投影核对项，主对话展示核对内容、查看报告侧栏和确认已达成动作；不得用模型文本冒充人工确认。窗口回归检查旧签收卡点击失败时的可读提示、最新快照撤掉失效卡、键盘打开完整报告侧栏，以及窄窗口浅色布局和 typed manual_completion IPC 分派。三张截图加入必查包。宿主测试覆盖尚未结束的 runner 不可签收、暂时 completed 后仍等待核对、过期报告令牌、重复点击、持久化失败与恢复失败；确认只记录本机用户决策并恢复验证，不直接写入结果签收。窗口用例为隔离合成数据，不替实际用户确认报告。

工具耗时（2026-10-06）：宿主事件已知的毫秒操作显示“少于 1 秒”，多秒操作显示真实整秒，旧历史缺失时间不显示伪造的 0 秒。窗口包加入深色与窄窗浅色过程截图，验证 Tool Call/Result 时间经过真实 Executor、Runner、持久化、历史投影仍可见。运行时另测试主 Bot 剩余轮次/工具预算传入内层 Provider Loop，超额批次不执行，已有结果保留，预算耗尽不自动重试；核验失败、异常、不可用及结论写入失败均退出 verifying。受控模型用例不能宣称覆盖真实模型的长时间重复行为。
