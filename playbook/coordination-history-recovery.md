# 协调历史分叉的保全与离线恢复

创建时间：2026-10-28
最后更新：2026-10-28

契约：[ADR 104 渐进读取与协调存储的分叉恢复补充](../knowledge/decisions/104-progressive-interaction-and-coordination-storage.md)。本卡是设备本地存储维护，不是模型工具、授权或执行证据。

## 范围与禁止事项

目标：保住历史任务、输入、检查点和已有成果，恢复可核对的任务状态，防止旧版本继续制造分叉。恢复可读与准许继续执行分开。

禁止删除旧日志、按 revision/时间拼接两分支、重置 head/manifest、清空任务、回退旧版写入目录、重放未知/已完成写入。不能通过改一个错误文案、清缓存或反复重启宣称恢复。

## 保全和核对

1. 在线阶段只读采集。建立独立且访问受限的保全目录；拷贝整个目标项目 runtime、关联 profile/父会话和必要交付资料；SQLite 用只读源的 backup 接口获得一致派生快照。保全清单记录字节数、SHA-256 和源前后检查。不要复制凭据、不要提交真实用户数据。
2. 确认原宿主仍活跃时，不提交任何修复，不伪造/抢租约。离线候选必须使用独立文件副本，候选中的 lease 副本显式移出，仅供隔离恢复；这不授权修改在线源的 lease。
3. 在代码仓运行 `node scripts/repair-coordination-fork.mjs --inspect <离线候选项目目录>`。输出共同基线、两分支终点、冲突对象、检查点摘要、全来源指纹与旧前缀摘要。原始差异保存在本机维护包，不放进产品回复或知识仓。
4. 核对 manifest 固定的旧文件字节前缀：逐条 reducer 回放、行边界与 revision；独立回放 v2 分段及 payload，核对哈希链、持久 head；旧尾从共同基线另行回放。检查点按 `workId + 换行 + 原文` 验证其内容地址，并将存在/缺失情况绑定来源指纹。无历史 seal 的前缀明确记为人工审阅基线，不补造历史证明。
5. 同输入 ID、较新时间、较大预算不表示两个分支是可直接续接的同一执行。用量 observation、原生 provider checkpoint、Tool Result 和实际派发回执需要分别核对。不能在恢复时把不同预算、预备交付或状态合成一次成功。

## 生成恢复候选

使用 inspect 输出的精确参数：

```sh
node scripts/repair-coordination-fork.mjs --recover <离线候选项目目录> <source-fingerprint> <reviewed-prefix-sha256>
```

- 有任何 host.lease（包括过期文件）立即拒绝；这条命令不会关闭应用、抢租约或启动执行。
- 同一次计划绑定来源摘要、检查点和人工审阅前缀；来源变化、缺失分段、hash 错误、符号链接和损坏候选均失败关闭。
- 两条原始日志及选择的检查点先 fsync 归档到 `.coordination-recovery/<fingerprint>/original/`，`inspection.json` 保留两版本差异。持久 intent 为 `coordination-recovery.json`，包含来源、候选与状态；归档、移开旧源、路径屏障、发布和收尾可中断重入。
- 恢复候选是新 generation，采用最低 reader/writer 3。旧的 `coordination.jsonl` 是目录屏障；规范基线在 `coordination-v2/baseline.jsonl`。旧二进制按固定文件路径 append 被操作系统拒绝；旧已打开 fd 只能影响移出的旧 inode，不能改新基线。
- 不冲突记录保留原含义；冲突的两个版本都在归档中。已送达/取消/coalesced 不复活。18 个历史未终结 work 并不等于18个当前运行子任务，数量按实际投影解释。
- 候选的 `lastRecovery.executionBlocked` 保持 true。启动恢复在 consume inputs、任务激活和模型执行之前拒绝；因此这一步恢复“可读并可核对”，绝不等于允许继续工作。未证明的冲突不得解除该屏障，不能手改 JSON 绕过。
- 实际目录应用必须先有正常关闭宿主的授权，重新确认无 lease 和来源未变化。当前工具只处理离线候选；本轮不替换运行中的已安装 RC27，也不发布。重新加载修复代码与现场最终对账仍是明确的后续操作，不能把副本验证称作在线修复已生效。

## 防止再次分叉

生产 Runtime Host 在健康恢复之后、执行准入之前启用 `fenceLegacyWrites`。已有 v2 和新空项目都安装物理路径屏障。健康项目不导入恢复状态、不改任务事件，不停止正常任务；只用已验证相同字节的新 inode 保存旧基线，保持分段哈希/修订和任务事实，新的物理锚点、head/manifest 和 seal 通过 `coordination-fence.json` 绑定的发布 intent 一起前进，原标记与旧文件留在 `.coordination-fence/<id>/`。

所有阶段重检 lease；中断先由同一 Store 恢复发布再允许读取。新代码 legacy Adapter 每次读与提交前检查 v2/维护标记；最低 reader/writer 3 加物理路径屏障约束不认识新字段的旧二进制。恢复旧版本只能使用完整独立的旧备份。

## 用户反馈

- 未恢复的分叉：“历史任务记录冲突，已暂停执行；已接收的消息会保留。”
- 恢复可读但未完成对账：“历史记录已恢复读取，执行仍暂停，需先核对已有任务与写入结果。”
- 其他恢复失败：明确尚未开始回复和输入持久接收边界。
- 主界面不再给不可修复冲突一个无效的“重试”按钮；读取历史的继续入口仍独立可用。诊断详情显示共享协议的错误码与阶段。
- 空的 assistant 等待占位不画头像；已有正文、进展、输入身份、草稿和阅读位置不删除、不重播。后台恢复状态改变通知现有 changed 通道，重复相同错误不反复刷新。

## 本轮证据和限制

真实历史副本：基线13659；v2推进598条到14257；旧尾1条handled和36条work推进到13696。核对到1个同输入但不同检查点/用量回执的 work 冲突。234项检查点引用通过内容地址核对。恢复副本可读取79个work，其中31个保持delivered；执行屏障保持关闭。真实 Runtime Host 在副本验证：模型调用、输入消费、任务激活、消息追加均为0。

用户本轮要求补回归：脱敏夹具使用同样598/37结构，并覆盖缺seal、已完成/未知写入凭据、输入归属、阶段中断重入、活动lease拒绝、来源/候选变化、符号链接、分段缺失、旧二进制append失败、健康/空项目写保护、恢复准入及前后端错误投影。完整版本/RC门禁、真实安装包交互、外部模型与读屏验收未运行；不发布、不自动重启，原本地在制修改保留。

本次最终定向验证：112项通过、0失败、0跳过；Desktop类型检查与所需protocol/runtime-node/i18n依赖构建通过。早期扩展夹具的检查点API名错误已修正并复跑；副本驱动以普通.mjs运行以避免--input-type继承到Worker。保留失败与最终通过日志，不隐去首次尝试。上述验证是实现者自审，未替代完整发布验收。在线应用恢复时禁止用候选整目录覆盖真实目录；必须关闭旧宿主、重读最新来源并在原位执行绑定计划，原输入队列/父会话/GoalPlan不移动。
